## Why

Issue #586 asks whoever triages parity/testing work to confirm or refute a scoping call made in `update-bloommcp-resultstore-fake-parity`'s design.md: that `SupabaseReader`/`FakeReader` has no analog to the partial-write/collision hazards PR #465 hardened `ResultStore` against, so no fake-side failure-injection parity work is needed.

That call is **refuted** — but not by the exact hazard shape #586's own wording anticipates ("a partial-read/retry contract a fake could silently misrepresent"). What was actually found is narrower and more concrete: a plain uncaught-exception leak on a multi-step read. `experiment_utils._resolve_one_class`'s `analysis_dir.get_version(version)` call (`bloommcp/src/bloom_mcp/experiment_utils.py:404-407`) is wrapped in `except ManifestSchemaError` only, while its two sibling failure points in the same function (`list_prefix` at `:431`, `download_file` at `:449`) already catch `Exception` generally. `get_version` reaches `read_manifest()` (`bloommcp/src/bloom_mcp/manifest/manifest.py:45-51`), whose own `list_prefix`/`read_json` calls carry no exception handling anywhere in that chain. A transient storage failure during manifest lookup — which runs on effectively every `load_experiment(name)` call, since `version="latest"` is the default — escapes as a raw, unwrapped exception, violating the `ExperimentReadError` contract's own documented promise ("Adapters MUST NOT leak... a storage traceback," `bloommcp/src/bloom_mcp/data_access/ports.py:23-26`) and the `bloommcp-experiment-read` spec's existing "Unknown experiment is reported through the contract" scenario. See design.md's Context for the full trace, including why `load_experiment_data`'s tool registration path has no sanitizing layer left to catch this.

The test that actually matters is not "does this match #586's literal wording" but "can a fake-only test prove the real adapter is failure-safe here" — and it fails that test exactly as `FakeResultStore` did before PR #465: `FakeReader` has zero failure-injection surface (`bloommcp/src/bloom_mcp/data_access/fake_reader.py`), unlike `FakeResultStore`'s `fail_next_commit`/`seed_collision`/`seed_v2_run`, and no `test_reader_parity.py` exists to extend.

`LocalReader.load_experiment` reaches the same shared `_resolve_versioned_cleaned` via `experiment_utils.load_experiment_data`, so it carries the identical latent bug — verified with its own direct test in this change (task 1.3), not left as an untested inference.

## What Changes

- Broaden `_resolve_one_class`'s exception handling around `analysis_dir.get_version(version)` to also catch a general read failure surfacing from `read_manifest()`'s unguarded `list_prefix`/`read_json` calls, converting it into the same `(None, None, error_string)` hard-error contract its two sibling failure points in the same function already use — **without changing the existing `ManifestSchemaError` message** (`test_storage_backend.py` asserts its exact text; the new general case is a second, additive `except` clause, not a replacement of the first). This is the actual bug fix — it closes the leak for every adapter that reaches `_resolve_versioned_cleaned` (`SupabaseReader` directly, `LocalReader` via `load_experiment_data`), from one shared call site. **This new branch's own error string still embeds the original exception's text verbatim** (same as its two siblings) — this fix's contribution is "no crash," not "no backend detail in this intermediate string"; the caller-facing redaction is a separate, pre-existing layer at the `load_experiment` call sites (see design.md's Risks).
- Add a direct unit test against `_resolve_one_class`/`_resolve_versioned_cleaned` (alongside `test_storage_backend.py`'s existing same-shape tests) proving: (a) the fix converts the previously-uncaught exception into the hard-error tuple, red before / green after; (b) critically, that a hard error on the higher-priority `outliers` class still propagates rather than silently falling through to a valid, seeded `qc` entry — mirroring `test_latest_schema_error_on_outliers_propagates_first_iteration`'s existing pattern for the other two failure points, so this fix is held to the same "never silently serve different, lower-priority data" invariant.
- Add a `LocalReader`-level test (using `test_storage_backend.py`'s local-backend fixture pattern) proving the same fix covers `LocalReader.load_experiment`, since it reaches `_resolve_versioned_cleaned` via a separate call path (`load_experiment_data`) — not left as an untested inference from the `SupabaseReader` case.
- Add a one-shot failure-injection hook to `FakeReader` — `fail_next_load(name, *, version="latest")` — mirroring `FakeResultStore.fail_next_commit`'s pattern: the next matching `load_experiment` call raises `ExperimentReadError`, then clears itself; a retry for the same `(name, version)` afterward resolves normally. This is the actual scope of "fake-side failure-injection parity work" #586 asks to add if a divergence is confirmed.
- Add `bloommcp/tests/data_access/test_reader_parity.py`, mirroring `test_store_parity.py`'s structure: one shared scenario parametrized over `fake`/`supabase`, proving both adapters convert a mid-read storage failure into a caller-safe `ExperimentReadError` rather than a raw exception. This is the cross-adapter parity coverage #586 asks about, distinct in scope from the direct unit test above (which pins the fix's own correctness against `SupabaseReader`/`LocalReader` internals; this one only asserts the externally-observable contract both adapters must share).
- Add a `logger.warning(..., exc_info=True)` call on the new `except` branch so the original storage error remains visible in server logs (the function returns an error string rather than raising, so there is no `raise ... from e` to chain — logging is what closes the gap here) — today a transient storage outage during manifest lookup is indistinguishable from a genuinely missing experiment in both the response and the server logs; this closes that for the newly-guarded path (the two pre-existing sibling failure points are left as-is, out of scope here).
- `update-bloommcp-resultstore-fake-parity` (PR #465, already merged) is not reopened; #586 is resolved as its own follow-up, on its own branch/PR, per the repo's established pattern (see #420→#585).

## Impact

- Affected specs: `bloommcp-experiment-read` (MODIFIED: `ExperimentReader Port` requirement gains a scenario for the hard-error-during-resolution case; `FakeReader Adapter` requirement gains a scenario for the new injection hook and extends the existing fake/Supabase-parity scenario's coverage)
- Affected code:
  - `bloommcp/src/bloom_mcp/experiment_utils.py` (`_resolve_one_class`'s exception handling)
  - `bloommcp/src/bloom_mcp/data_access/fake_reader.py` (`fail_next_load` hook)
  - `bloommcp/tests/test_storage_backend.py` (new direct unit tests: the fix + the qc-fallback-safety invariant + the `LocalReader` case)
  - `bloommcp/tests/data_access/test_reader_parity.py` (new: cross-adapter parity scenario)
  - `bloommcp/tests/data_access/test_fake_reader.py` (fake-only unit test for the new hook)
- Verified unaffected: `SupabaseReader`'s raw tier (RPC-backed; every step already wrapped in `try/except` → `ExperimentReadError`, confirmed by the existing `test_rpc_failure_surfaces_as_experiment_read_error_not_raw`) — no bug there. `ExperimentReader`/`ResultStore` Protocol signatures — the new hook is additional public surface on the concrete `FakeReader` class only, same pattern as `FakeResultStore`'s hooks. `test_storage_backend.py`'s two existing tests asserting the literal `ManifestSchemaError` message string — preserved unchanged (see What Changes' first bullet).
- Not affected: the pre-existing, deliberate collapsing of every `_resolve_versioned_cleaned` hard error (schema error, missing output key, unlocatable version dir, failed download, *and now* an unguarded manifest-read exception) into `ExperimentNotFoundError` at the `load_experiment` call sites — that conflation predates this change (it already applies identically to the three previously-wrapped failure points) and redesigning the not-found/read-error distinction is out of scope here; see design.md Non-Goals. Also not affected: `result_store/supabase_store.py`'s independent calls into the same `AnalysisDir.get_version`/`read_manifest` chain (`list_runs`, `get_run`, `create_run`) — a real but separate ripple, documented (not fixed) in design.md's Risks, since each is either already independently guarded by its own caller or has no production caller today.
