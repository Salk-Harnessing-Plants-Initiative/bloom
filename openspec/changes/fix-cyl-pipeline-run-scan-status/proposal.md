## Why

`cyl_pipeline_runs.done_count`/`failed_count` have existed since Phase 1 (`20260730120000_create_cyl_pipeline_runs.sql`) but nothing has ever populated them — confirmed live on 2026-08-24/25's first fully-successful real batch run, whose own `cyl_pipeline_runs` row read `done_count: 0, failed_count: 0` the entire time despite every scan genuinely completing (filed as bloom #716). The only thing that touches per-scan `cyl_pipeline_run_scans.status` today is dispatch outcome (`fail_cyl_pipeline_batch`, when Kubernetes rejects an Argo Workflow submission) — no code path ever writes `'predicted'`, `'written'`, or `'reused'`, so a scan whose batch dispatches fine stays `'queued'` forever regardless of whether its prediction/write-back actually succeeded (bloom #696). These two gaps are the same problem: `done_count`/`failed_count` can only mean "pipeline outcome" if something first records real per-scan pipeline outcomes to roll up. Fixing #716 without #696 would mean deriving the counts from dispatch-level or Argo-phase-level signals, which are batch-level and submission-level, not scan-level — a naive implementation would silently produce numbers that look like progress but aren't (e.g. counting "K8s accepted the batch" as `done`, before any prediction has run). This blocks bloom #15's UI progress panel, whose core "N/M scans done" display depends entirely on these two fields being real.

## What Changes

- Extend the `insert_cyl_result_envelope` write-back RPC to accept a new optional `p_argo_workflow_name text DEFAULT NULL` parameter (the existing `envelope` parameter's name is unchanged — every caller, including the documented `cyl-ingest-cli` RPC call shape, keys on it by name via PostgREST, so renaming it would break every existing caller). When non-null, in the same transaction as the existing trait/source/blob writes, it atomically sets the matching `cyl_pipeline_run_scans` row's `status` to `'written'` and its `source_id`, guarded by `AND status != 'failed'` (matching `complete_cyl_pipeline_batch`'s existing convention, so a genuinely late/out-of-order delivery can never resurrect a scan already closed out as failed). The join key is `(argo_workflow_name, scan_id)` — `argo_workflow_name` is already stored per scan by the existing dispatch machinery (`complete_cyl_pipeline_batch`), and `scan_id` is already resolved inside the RPC from `provenance.inputs.image_ids`, so no new plumbing is needed to know which run/batch a write-back call belongs to. `bloomctl cyl ingest-result`/`batch-ingest-result` already run inside a pod where Argo sets `ARGO_WORKFLOW_NAME={{workflow.name}}` (`sleap-roots-write-back-template.yaml`, pre-existing) — this parameter is optional so manual/ad-hoc invocation with no pipeline-run context (the existing standalone `cyl ingest-result` use case) is unaffected. This RPC's own idempotent re-delivery is always recorded as `'written'`, never `'reused'` — `'reused'` remains reserved exclusively for the separate, still-unimplemented pre-dispatch skip-if-done mechanism the `cyl-pipeline-runs` capability already documents.
- Add a new `SECURITY DEFINER` RPC, `fail_cyl_pipeline_run_scans_without_result(p_argo_workflow_name text, p_error_message text DEFAULT NULL) RETURNS integer`, granted only to `bloom_workflows`. It marks every `cyl_pipeline_run_scans` row for that workflow name still `'queued'` as `'failed'` (idempotent: a row already `'failed'`/`'written'`/`'reused'` is left untouched) — covering scans whose prediction failed before write-back was ever attempted, or whose envelope was otherwise never produced (including the pre-existing "manifest-declared scan_key with no matching file" case). `bloomctl cyl batch-ingest-result` calls this once at the end of a batch, after processing every discovered envelope, only when `ARGO_WORKFLOW_NAME` is set (skipped for manual/local invocation, matching existing behavior).
- Extend `update_cyl_pipeline_run_status` to accept `p_done_count integer DEFAULT NULL, p_failed_count integer DEFAULT NULL` and, when supplied, `SET done_count = p_done_count, failed_count = p_failed_count` alongside the existing `status`/`completed_at` write.
- Extend `services/workflows/status_poller.py`'s `sweep_once` to compute, from each candidate run's already-fetched `cyl_pipeline_run_scans` rows, `done_count` (rows with `status IN ('written','reused')`) and `failed_count` (rows with `status = 'failed'`), and pass them on every `update_cyl_pipeline_run_status` call. **BREAKING (internal)**: this removes the existing "computed status matches known `'running'` status → skip the RPC call" optimization, since a still-`'running'` run's counts can advance every cycle even when its overall status doesn't — the call must now happen every cycle a run has candidate rows, not only on a status transition. This requires updating roughly a dozen pre-existing `test_status_poller.py` tests whose mocks assume the old call shapes, and deleting/inverting the one test that specifically asserts the removed skip.
- Both new/changed RPC signatures are added via `DROP FUNCTION` + `CREATE FUNCTION` (not `CREATE OR REPLACE`, which cannot add a parameter to an existing signature without leaving the old overload live) — each drop/create pair re-issues that function's existing grants, since a drop discards them.

## Impact

- Affected specs: `cyl-trait-writeback` (write-back RPC signature + a new RPC), `cyl-pipeline-status-polling` (poller behavior + `update_cyl_pipeline_run_status` signature), `cyl-pipeline-runs` (the "columns default to 0, never updated" language becomes "updated by the status-polling capability"), `cyl-ingest-cli` and `cyl-batch-ingest-result` (both thread `ARGO_WORKFLOW_NAME` through; the latter also gains the reconciliation call).
- Affected code: `supabase/migrations/` (two forward migration + rollback pairs, split by concern — see `design.md` Decision 5 — so either half can be rolled back independently), `services/workflows/status_poller.py` and its test suite, `bloomcli/src/bloomctl/cyl/ingest.py` and its test suite, pre-existing integration tests that hardcode the old RPC signatures in grant-check assertions, `services/workflows/README.md` and `bloomcli/README.md`/`CHANGELOG.md` (behavioral descriptions that would otherwise go stale), and the tracked `database.types.ts` files (regenerated, not hand-edited).
- No changes needed outside `salk-bloom` — `sleap-roots-pipeline`'s write-back `WorkflowTemplate` already sets `ARGO_WORKFLOW_NAME`, and `dispatch_worker.py`/`k8s_client.py` are unchanged (confirmed by investigation: `run_id`/`batch_index` reach the submitted Workflow only as K8s labels today, and joining on the already-known `argo_workflow_name` avoids needing to promote either to a real Argo parameter).
- Does not implement `cyl_pipeline_run_scans.status = 'predicted'` (a pre-write-back "prediction succeeded, not yet written" state) — no code path in this program currently reports that intermediate outcome, and no consumer of `done_count`/`failed_count` needs it; scans go `'queued'` → `'written'`/`'failed'` directly. `'predicted'` remains defined in the schema's `CHECK` constraint but unused, matching its current status.
- `failed_count` can overcount relative to "real pipeline failures": a scan intentionally skipped by a mechanism this change doesn't touch, or otherwise never producing a result for a benign reason, is indistinguishable from a real prediction/write-back failure under this scheme (this ambiguity is bloom #704's already-filed, separate concern) — `failed_count` means "produced no result," not strictly "failed."
- Deploy-ordering and rollback have real, documented constraints — see `design.md` Risks.
