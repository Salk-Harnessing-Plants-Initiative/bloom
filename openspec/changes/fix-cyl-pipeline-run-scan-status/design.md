## Context

`cyl_pipeline_runs.done_count`/`failed_count` (bloom #716) and `cyl_pipeline_run_scans.status` past `'queued'` (bloom #696) are two ends of the same gap: today nothing records a real per-scan pipeline outcome anywhere, so there is nothing correct to roll up. This design covers both together, scoped entirely inside `salk-bloom`.

Ground truth this design relies on (verified by reading the actual code, not the archived design docs' descriptions of intent):

- `insert_cyl_result_envelope` (`supabase/migrations/20260630180000_add_cyl_writeback_rpc.sql`, re-pinned `20260706170000_cyl_writeback_contract_a3.sql`) already resolves `scan_id` internally from `provenance.inputs.image_ids` and never touches `cyl_pipeline_run_scans`/`cyl_pipeline_runs`.
- `complete_cyl_pipeline_batch` (`20260817120000_add_cyl_pipeline_dispatch_functions.sql`) is the only thing that sets `cyl_pipeline_run_scans.argo_workflow_name`, at dispatch time, before the Argo Workflow's pods have run at all.
- `sleap-roots-write-back-template.yaml` (in the separate `sleap-roots-pipeline` repo) already sets `env: ARGO_WORKFLOW_NAME: "{{workflow.name}}"` on the write-back container — the same mechanism `bloomcli/src/bloomctl/cyl/download_for_predict.py`'s `resolve_pipeline_run_id()` already reads for an unrelated purpose (naming a `RunManifest`).
- `bloomctl cyl ingest-result`/`batch-ingest-result` (`bloomcli/src/bloomctl/cyl/ingest.py`) send only `{"envelope": envelope}` to the RPC today; there is no `run_id`/`batch_index` anywhere in scope at the call site, and `dispatch_worker.py`/`k8s_client.py` only ever fold `run_id`/`batch_index` into K8s object **labels** on the submitted Workflow (`build_workflow_body`, `services/workflows/k8s_client.py:178-229`) — never into `spec.arguments.parameters`, which is the only mechanism a step's container args/env can actually consume.

## Goals / Non-Goals

**Goals:**
- `done_count`/`failed_count` on `cyl_pipeline_runs` reflect real per-scan pipeline outcomes (prediction + write-back), not dispatch/submission outcomes, and update continuously as scans complete — not just once at the run's final settle.
- Close bloom #696 far enough to make bloom #716 correct: `cyl_pipeline_run_scans.status` transitions to `'written'`/`'reused'` on real write-back success and `'failed'` when a scan never produces a result.
- No changes outside `salk-bloom`.

**Non-Goals:**
- Implementing `'predicted'` as a distinct, observed intermediate state. No current producer reports "prediction succeeded, write-back not yet attempted" as a discrete event, and no consumer needs it — `'queued'` → terminal is sufficient for `done_count`/`failed_count`. If a future phase adds real-time per-stage progress (e.g. a live "predicting vs. writing" UI distinction), it can add that signal then; this change does not block it since `'predicted'` stays a valid, unused `CHECK` value.
- Disambiguating *why* a scan produced no envelope (traits genuinely failed vs. an Argo DAG race meant traits never ran at all vs. intentional skip) — bloom #704 already flags this as a known, separate ambiguity inside `bloomctl`'s own envelope discovery. This change's failure-marking RPC records "no result was produced for this scan by the end of write-back," which is the correct granularity for a `done`/`failed` *count*; a richer failure taxonomy is out of scope here.
- Any change to `dispatch_worker.py`, `k8s_client.py`, or any Argo `WorkflowTemplate` (in this repo or `sleap-roots-pipeline`) — the `argo_workflow_name` join key avoids needing any of that.

## Decisions

### Decision 1: Join per-scan write-back to its run via `argo_workflow_name`, not a new `run_id` parameter

**Alternatives considered:**
- **Thread `run_id`/`batch_index` through as a new Argo Workflow parameter.** Requires promoting them from K8s labels to real `spec.arguments.parameters` in `k8s_client.py`'s `build_workflow_body`, *and* a change to `sleap-roots-write-back-template.yaml` (a different repo, outside this branch's control) to consume that parameter and pass it to `bloomctl` as a new CLI flag or env var, *and* a new `--run-id` option on the CLI. Three points of plumbing across two repos for information Bloom already has.
- **Infer the run from `scan_id` alone** (e.g. "the most recent `'queued'` row for this scan"). Rejected: `cyl_pipeline_run_scans` has no application-level constraint preventing the same scan from being enqueued into two different runs concurrently (the schema only enforces uniqueness per `(run_id, scan_id)` pair, not one-active-run-per-scan) — "most recent" is a heuristic that can silently attribute a result to the wrong run.
- **Join on `argo_workflow_name` (chosen).** Bloom already stores this per scan at dispatch time, and Argo already injects it into the write-back pod as `ARGO_WORKFLOW_NAME` (confirmed in the actual template file, not assumed). `(argo_workflow_name, scan_id)` uniquely identifies one `cyl_pipeline_run_scans` row without ambiguity, since one Argo Workflow name corresponds to exactly one batch dispatch. Zero new plumbing, zero cross-repo changes.

### Decision 2: Success is written inside `insert_cyl_result_envelope` itself; failure is a separate RPC

A successful write-back can update `cyl_pipeline_run_scans` atomically in the same transaction as the trait/source/blob writes it already performs — if the transaction rolls back (a validation failure), the status update rolls back with it, so nothing spurious is recorded. But a scan whose **prediction** fails never reaches `insert_cyl_result_envelope` at all — there is no envelope to call it with. That failure can only be recorded by a separate statement, called after the fact.

This is why `fail_cyl_pipeline_run_scans_without_result` is a batch-level reconciliation call, not a per-scan one: `bloomctl cyl batch-ingest-result` doesn't have a manifest of "which scans were *supposed* to produce an envelope and didn't" available on disk (confirmed: `RunManifest.scan_keys` scopes *discovery*, not expectation-vs-actual reconciliation, and carries a string Argo-workflow-name-shaped `pipeline_run_id`, not a Bloom `cyl_pipeline_runs.id`). The reconciliation instead runs entirely in the database: after every discovered envelope for this batch has been ingested (each moving its scan to `'written'`), one call marks every remaining `'queued'` row for this `argo_workflow_name` as `'failed'` — the CLI doesn't need to know which scans those are, only that write-back for this batch is done.

**Idempotency, and why the success path needs a guard too**: like `fail_cyl_pipeline_batch`'s existing precedent, `fail_cyl_pipeline_run_scans_without_result`'s `WHERE status = 'queued'` guard makes a repeated call (e.g. `retryStrategy: {limit: 2}` on the write-back step) a no-op for scans a prior attempt already resolved — it can never re-fail an already-`'written'` scan or double-count. The reverse direction needs guarding too, and an earlier draft of this design missed it: `insert_cyl_result_envelope`'s own success-path `UPDATE` (step 7) has no natural reason to skip a matching row on its own, but if a write-back call for one scan is genuinely late — arrives *after* `fail_cyl_pipeline_run_scans_without_result` has already closed that scan out as `'failed'`, e.g. a stray retried pod finishing after the reconciling pod already ran — an unguarded `UPDATE` would silently flip it back to `'written'`. Since the parent run may have *already gone terminal* by that point (a `'complete'`/`'failed'`/`'partial'` run drops out of `status_poller.py`'s candidate-run query for good — see `_fetch_candidate_runs`), nothing would ever re-poll it and recompute `done_count`/`failed_count` to reflect the resurrected row: the per-scan table and the run-level rollup would permanently disagree. Fixed by adding `AND status != 'failed'` to step 7's `UPDATE`, mirroring `complete_cyl_pipeline_batch`'s own existing use of the identical guard for the identical reason (`20260817120000_add_cyl_pipeline_dispatch_functions.sql`).

**Corrected `'reused'` semantics**: an earlier draft of this design had a no-op re-delivery of the *same* envelope (this RPC being called twice for one already-ingested run) set the scan's status to `'reused'`. That was a mistake — `cyl_pipeline_run_scans`'s own schema comment already assigns `'reused'` a specific, different meaning: the pre-dispatch "cluster-side skip-if-done" check deciding a scan needs no new work *before it is ever dispatched at all*, a mechanism this change does not implement and does not touch. An idempotent re-delivery of the write-back RPC is not that — the scan's pipeline genuinely ran and produced a real result; the second call is just a retry-safety no-op on the *write*, not a skip of the *work*. Both the first delivery and any idempotent re-delivery now record `'written'`. `done_count`'s formula (`status IN ('written', 'reused')`) still includes `'reused'` for forward compatibility with that other, already-designed mechanism, even though nothing in this change produces it.

### Decision 3: `done_count`/`failed_count` are computed by `status_poller.py`, not by a trigger

The poller already fetches every candidate run's `cyl_pipeline_run_scans` rows each cycle to build its Argo-phase rollup (`_fetch_effective_phases`). Computing `done_count`/`failed_count` from that same fetch is a few lines, not a new subsystem. A DB trigger on `cyl_pipeline_run_scans` would keep counts fresher (no poll-interval lag) but adds a second, independent code path that must itself be tested for the same idempotency/race conditions the poller's isolation model already handles per-run — not justified by the marginal freshness gain given the poller's default 15s interval.

**Consequence — the `'running'`-status skip optimization is removed.** `sweep_once` currently skips calling `update_cyl_pipeline_run_status` when the computed status exactly matches an already-`'running'` known status (no new evidence). Under this change, a run can stay `'running'` for many cycles while `done_count` climbs as individual scans finish — skipping the call would freeze the UI's "N/M" display at whatever it read on the first `'running'` cycle. The call must happen every cycle a run has candidate rows, whether or not `status` itself changes. `update_cyl_pipeline_run_status` remains cheap and idempotent (a plain `UPDATE ... WHERE status IN (...)`), so this is a documented behavior change, not a regression — see the `cyl-pipeline-status-polling` spec delta's `MODIFIED` scenario.

### Decision 4: `done_count` counts `'written'` and `'reused'` together; not `'predicted'`

`'predicted'` is a defined-but-unreachable status (see Non-Goals) — never produced by any code path in or after this change, so it is excluded from `done_count` for symmetry with "we don't emit it," not because a predicted-but-not-written scan would be wrong to exclude. `'reused'` counts as done for forward compatibility with the separate, still-unimplemented pre-dispatch skip-if-done mechanism that is its sole intended writer (see Decision 2's corrected semantics above — this change itself never produces `'reused'`, only `'written'`), distinct from `reused_count` (the pre-existing, separately-populated column tracking scans skipped **before dispatch** by the trigger route's own dedup preview — a different concept this change does not touch).

### Decision 5: Two migration/rollback file pairs, split by concern

The per-scan write-back changes (`insert_cyl_result_envelope`'s new parameter + guard, and the new `fail_cyl_pipeline_run_scans_without_result` RPC — both touching `cyl_pipeline_run_scans` and consumed by `bloomctl`/Argo write-back pods) go in one migration/rollback pair; the run-level rollup change (`update_cyl_pipeline_run_status`'s new parameters, touching `cyl_pipeline_runs` and consumed only by `status_poller.py`) goes in a second, separate pair — matching this repo's own precedent of splitting same-PR migrations by concern rather than by change (e.g. PR #684 shipped `create_cyl_scan_latest_source.sql` and `rewrite_get_experiment_summary_counts.sql` as two files for one proposal). This matters beyond style: the two halves have independent failure modes (see the deploy-ordering and rollback risks below) and independent consumers, so a problem isolated to one (e.g. `status_poller.py`'s increased call volume) can be rolled back without forcing a simultaneous revert of the other (write-back's success-path recording, which has no analogous concern).

### Decision 6: `status_poller.py` is a backstop reconciler for scans `bloomctl` never got to reconcile (found in post-implementation `/review-pr`)

A first implementation round (2 adversarial `/review-openspec` rounds pre-implementation, then a full implementation pass) still left three real gaps once `/review-pr` ran against the actual diff:

1. **`ingest_one_envelope`'s per-envelope isolation had a hole.** Its catch-all (`except Exception`) wrapped only the blob-construction/RPC-call block, not the earlier `load_envelope`/`validate_envelope` calls, each guarded only by a narrow `except EnvelopeError`/`except EnvelopeValidationError`. `load_envelope`'s `Path(source).read_text(encoding="utf-8")` can raise `UnicodeDecodeError` — a `ValueError`, not `OSError` — on a truncated/corrupt file (exactly what an OOM-killed producer pod can leave behind), which propagated uncaught out of `ingest_one_envelope`, out of `batch_ingest_result`'s list comprehension, and out of the CLI command entirely. Fixed by merging the three try/except blocks into one covering the whole per-envelope pipeline (read → validate → blob → RPC), so any exception at any step is isolated into a `ScanResult`, matching what the existing "batch isolation" comment already claimed it did.
2. **The new end-of-batch reconciliation call had no isolation of its own**, unlike every other RPC call in this file. A transient failure calling `fail_cyl_pipeline_run_scans_without_result` — after every envelope in the batch had already ingested successfully — crashed the whole command with an unhandled traceback instead of the batch's own summary, and its success-path return value (how many scans it closed out) was discarded, with no operator-visible signal. Fixed by wrapping the call and turning a failure into a synthetic `ScanResult` (`scan_key="<reconciliation>"`, `status="failed"`) that flows through the existing summary/`--json`/exit-code machinery like any other per-scan outcome — the batch summary still prints, the failure is visible in it, and the exit code reflects it — and logging the reconciled count on success.
3. **Both of the above only cover failures *inside* a running `bloomctl` process.** If the whole Argo Workflow fails upstream of the write-back step (every predict pod crashes, a DAG dependency short-circuits it) or the write-back container itself never gets scheduled, `bloomctl cyl batch-ingest-result` never runs at all — nothing ever calls `fail_cyl_pipeline_run_scans_without_result` for that workflow's scans. Meanwhile `status_poller.py`'s Argo-phase rollup correctly concludes the run is terminal (`'failed'`/`'partial'`) and, once written, the run drops out of `_fetch_candidate_runs`'s `'submitted'|'running'|'partial'` candidate set for good — so nothing ever polls it again to fix this. Net effect: those scans stay `'queued'` forever, and `done_count`/`failed_count` permanently undercount on exactly the run an operator most needs a correct count for (a fully- or partially-failed one) — reproducing bloom #716's original symptom in its worst case.

   **Decision:** `status_poller.py` becomes the backstop. Whenever a candidate run's rollup concludes a status other than `'running'` (i.e. every one of that run's non-404'd workflows already has a terminal Argo phase) and is not withheld by the existing `'complete'`-with-`any_unknown` rule, and that run still has one or more `cyl_pipeline_run_scans` rows with `status = 'queued'` and a non-null `argo_workflow_name`, the poller calls `fail_cyl_pipeline_run_scans_without_result` once per distinct such `argo_workflow_name` — **before** writing the run's terminal status via `update_cyl_pipeline_run_status`, not after. Ordering matters: if the reconciliation call itself fails, the run's `cyl_pipeline_runs.status` is left completely untouched (still `'submitted'`/`'running'`/`'partial'`), so it remains a candidate and gets retried next cycle — the same "isolate to this run, retry next cycle" discipline `sweep_once` already applies to every other per-run failure, rather than a new failure mode where a run goes terminal with rows left permanently unreconciled because there's no cycle left to fix them. On success, the reconciled rows are folded straight into this cycle's `failed_count` from the already-fetched row list (no second query) before the status write.

   A `'queued'` row under a *404'd* (Argo-forgotten) workflow is reconciled by this same rule, not treated specially: by the time a workflow 404s, Argo no longer has any record of it (TTL-expired/GC'd after it finished, one way or another) — it cannot still be silently running — so a row still `'queued'` under it can only mean write-back never resolved that scan, the same condition this backstop targets for any other terminal workflow.

   **Alternatives considered:** (a) Treat this as `bloomctl`'s problem alone and accept the gap — rejected: the failure mode ("write-back never ran at all") is by construction unreachable from inside a process that never started. (b) Have the poller reconcile unconditionally every cycle, regardless of rollup conclusion — rejected: a `'queued'` row under a workflow still genuinely `Pending`/`Running` isn't stuck, it just isn't done yet, and reconciling it would record a false failure; gating on "this run's rollup just concluded non-`'running'`" is what makes the reconciliation correct rather than premature.

   **Risk accepted:** this closes the "orphaned forever" case but not the "orphaned indefinitely slow" one — a run whose rollup never reaches a terminal conclusion at all (e.g. a workflow stuck `Pending` forever due to a scheduling problem) never triggers this backstop either, the same as it never let the run conclude before this change. That is an existing, separate concern (Argo's own TTL/GC and this poller's existing 404-handling), not newly introduced here.

### Decision 6 addendum: a second /review-pr pass on Decision 6's own fix found two more real bugs

A second round of `/review-pr` — run specifically against Decision 6's fix commit, to check the fix itself rather than re-litigating already-accepted risks — found two more real, if narrow, bugs, both fixed in a follow-up commit:

1. **Stale-snapshot undercount race.** `_fetch_effective_phases`'s `done_count`/`failed_count` are a snapshot taken from one `SELECT` at the very top of that function — before that cycle's `get_workflow_status` K8s calls, and before the backstop's own reconciliation RPC, even run. `sweep_once` was folding the reconciliation RPC's return value onto that stale snapshot (`failed_count += <reconciled count>`). If a scan's write-back genuinely resolves (`'queued'` → `'written'`) in the window between the snapshot and the reconciliation call, `fail_cyl_pipeline_run_scans_without_result`'s own `WHERE status = 'queued'` guard correctly leaves that row alone (no double-fail) — but the stale snapshot's `done_count` never gets credit for it either, so the run's written counts permanently undercount by one for exactly the scan(s) that raced, on a run that (if the conclusion is `'complete'`/`'failed'`, not `'partial'`) then drops out of polling for good. Fixed by adding `_count_done_and_failed(client, run_id)` — a plain, phases-independent re-read of `cyl_pipeline_run_scans` — and calling it to fully replace `done_count`/`failed_count` immediately after the reconciliation loop succeeds, rather than incrementing the earlier snapshot. Deliberately not folded into `_fetch_effective_phases` itself or re-using it wholesale: re-running that function would also re-run the K8s phase lookups and risk computing a *second, possibly different* rollup conclusion mid-cycle, which would be far worse than the bug being fixed.
2. **Wrong-RPC error hint.** `map_rpc_error` is documented as owned by, and hardcoded to, `insert_cyl_result_envelope`'s specific `RAISE EXCEPTION` messages (e.g. its `"permission denied"` branch names that RPC and suggests logging in as `bloom_writer`/`bloom_admin`). `_reconcile_unresolved_scans_result` (bloomcli) was reusing that same mapper for errors from `fail_cyl_pipeline_run_scans_without_result` — a different RPC, granted to `bloom_workflows` only. A real permission error on that call would have named the wrong RPC and suggested the wrong role. Fixed by returning the raw Postgres message verbatim for this call site instead of running it through `map_rpc_error`.

**Deferred from this round** (surfaced by `/review-pr`, consciously not addressed in this change): `insert_cyl_result_envelope`'s `EXECUTE` grant is broader (`bloom_writer, service_role, bloom_admin, bloom_workflows`) than the new per-scan status side effect strictly needs, since only `bloom_workflows` calls it with a real `p_argo_workflow_name` in practice — a caller already holding one of the other three roles could in principle fabricate a `p_argo_workflow_name` to flip an unrelated run's scan status, given the already-accepted absence of a uniqueness constraint on that column (see the risk below). Missing test coverage for a genuine full-success rollup and an all-failed rollup with real per-scan rows (today only exercised via the mixed partial case), and for `reconcile_unresolved_scans`/`_reconcile_unresolved_scans_result` (bloomcli) AND `_reconcile_unresolved_scans`/`_count_done_and_failed` (status_poller.py) at the unit level — every test on both sides monkeypatches these away wholesale rather than exercising their real RPC-call shape, so a typo in an RPC/parameter name would only surface in a live/E2E run. Stale generated `database.types.ts` mirrors (no live TypeScript caller of either changed RPC exists today, so not a live bug). A late envelope with a genuinely different idempotency_key arriving for an already-`'failed'` scan can still write real trait/blob data under a new `source_id` while the scan's own status stays stuck `'failed'` — the existing guard protects the status column, not the underlying data, from this specific resurrection shape. A synthetic `ScanResult("<reconciliation>", ...)` scan_key has no structural protection against colliding with a real producer-supplied `scan_key` of the same literal string (cosmetic only — never written to the DB).

### Decision 6 addendum 3: a third /review-pr pass, run specifically against the rebase fix, found the rebase's own test-side gap

The a3/a7 reconciliation above fixed the *production* function bodies, but missed that `repin-cyl-contract-a7`'s own test additions (three `test_a7_*` tests, merged in with the 234 commits) needed the same treatment `test_a3_*`'s tests already give themselves: `_call()` always issues a 2-positional-argument SQL call (`SELECT insert_cyl_result_envelope(%s::jsonb, %s)`), which Postgres can only ever resolve to the live 2-arg overload — never to a 1-arg overload a test's own `MIGRATION_A3`/`MIGRATION_A7`/`ROLLBACK_A7` just (re)created in the same transaction. The `test_a3_*` tests already knew this and roll back this change's own 2-arg signature first (`ROLLBACK_SCAN_STATUS`) before calling via a dedicated `_call_1arg` helper; the `test_a7_*` tests, added by a different PR against a version of this file that didn't yet have a 2-arg overload to worry about, did neither. Confirmed as a real, live CI failure (not just a hypothetical) once the branch was pushed rebased: `test_a7_cutover_guard_raises_on_a3_row`'s unguarded seed call raised `contract_version mismatch: got 0.1.0a3, pinned 0.1.0a7` (it was hitting the 2-arg overload, not the 1-arg a3 body it had just created), and `test_a7_rollback_restores_strict_a3` failed with "DID NOT RAISE" (its expected-rejection call likewise hit the unaffected, still-a7-pinned 2-arg overload instead of the just-rolled-back-to-a3 1-arg one). `test_a7_migration_body_is_idempotent` didn't fail, but only because it was vacuously exercising the same always-live 2-arg overload rather than what it had just applied. Fixed by giving all three the same `ROLLBACK_SCAN_STATUS` + `_call_1arg` treatment the `test_a3_*` tests already use.

### Decision 6 addendum 4: a fourth /review-pr pass, run after CI went fully green, upgraded one deferred risk to a fix and found two stale docs

With CI green after addendum 3's fix, a fourth round did a comprehensive fresh pass rather than re-checking the last fix alone. It found:

1. **Stale documentation of an already-rejected approach.** `services/workflows/README.md` and this same capability's own normative `cyl-pipeline-status-polling` spec requirement still described addendum 1's *rejected* "fold the reconciled count into `failed_count`" approach as if it were the shipped behavior, rather than `_count_done_and_failed`'s fresh recount. Both corrected to match the actual code.
2. **The late-delivery-resurrection risk (documented and test-covered since Decision 2, deferred as a low-probability edge case) is reachable via an ordinary flaky-network path, not an exotic one.** One scan permanently broken (e.g. a corrupt file) plus one scan merely timing out in the same batch is enough: the batch's own end-of-batch reconciliation call (running before Argo even decides to retry the whole pod) can close out the timed-out scan's row as `'failed'`, and the retry's later, genuinely successful delivery for that same scan then hits the guard silently — `was_noop: false`, real trait/blob rows written, but the status `UPDATE` affects zero rows. Before this round, the RPC's return object gave the caller no way to tell the two cases apart, so `bloomctl` reported a plain `"ok"` with no signal that `done_count`/`failed_count` would now permanently disagree with the data just written. Fixed by adding `status_update_matched` (`true`/`false` when `p_argo_workflow_name` was supplied, `null` when omitted — not applicable) to the RPC's return object on both the no-op and normal-delivery paths (`GET DIAGNOSTICS ... = ROW_COUNT` right after each guarded `UPDATE`), and having both `bloomctl` call sites (`ingest_one_envelope` and the single-envelope `ingest_result` command) treat a genuine `false` as a reportable failure instead of a silent success.
3. Two risks were re-examined and are now more explicitly documented rather than fixed, since neither has a concrete, actionable trigger yet: (a) a `'partial'` run's `status` can retroactively regress (e.g. to `'failed'`) purely from Argo TTL/GC aging a previously-`Succeeded` sibling workflow out of `get_workflow_status`'s answers on a later cycle — a pre-existing rollup/404 mechanism this PR doesn't change, but this PR is what attaches a hard, possibly-stale `done_count` next to that regressed status for the first time, which a scientist could read as directly self-contradictory; (b) the `argo_workflow_name` uniqueness risk's "vanishingly unlikely" characterization doesn't show its math and doesn't account for cumulative collision probability (a birthday-paradox-shaped problem) over the program's multi-year lifetime, as opposed to a naive per-event probability — worth actually computing before continuing to treat it as settled, but no reviewer round has yet had the real entropy figures for `sleap-roots-write-back-template.yaml`'s generated workflow names to do that computation.

### Decision 6 addendum 5: a fifth /review-pr pass found addendum 4's own fix could cascade one scan's unfixable mismatch into the whole run

Addendum 4's fix made `bloomctl` report a `status_update_matched: false` mismatch as a failed `ScanResult` instead of a silent `"ok"`. That's correct for the *summary/JSON* output, but it had a consequence nobody had traced yet: `batch_ingest_result` exits non-zero whenever `BatchResult.ok` is `False`, and a non-zero exit from the write-back container tells Argo's `retryStrategy` (`limit: 2`) to retry the *whole pod*. The guard this mismatch reports is permanent — the scan's row is already `'failed'` and step 9's `AND status != 'failed'` will never let a retry change that — so every retry reproduces the identical mismatch, burning the entire retry budget on something no retry can fix. Once exhausted, Argo marks the *workflow* `Failed`, and `status_poller.py`'s `rollup()` computes status per-workflow-phase, not per-scan: a single unfixable mismatch on one scan out of many drags the *entire run* — including every other scan that genuinely succeeded — to a terminal `status = 'failed'`. Before addendum 4, this exact case was silently reported `"ok"` (bad, but at least didn't cascade); addendum 4 made it correctly visible at the cost of introducing this cascade, which is a worse failure mode than the one it fixed.

Fixed by adding `ScanResult.retriable` (default `True`) and `BatchResult.needs_retry` (`True` iff `.ok` is `False` and at least one failure is `retriable`) to `_batch.py` — shared infrastructure also used by `download_for_predict.py`'s stage-in command, hence the default-`True`, purely-additive design: nothing already constructing a `ScanResult` needs to change, and `.ok`/`format_summary`/`format_json` are completely unaffected (a caller checking `.ok` or reading the printed summary still sees the real, unfiltered outcome — the mismatch still shows as `"failed"` there). `batch_ingest_result` now exits non-zero on `needs_retry`, not `ok`, marking the `status_update_matched`-mismatch `ScanResult` `retriable=False`. A batch mixing a genuine retriable failure with a non-retriable mismatch still exits non-zero (the retry might fix the retriable one). The single-envelope `ingest_result` command's own `ClickException` on this same mismatch is deliberately left as-is — it's the manual/ad-hoc invocation shape, run by a human who sees the failure directly, not something Argo automatically retries, so the cascade risk this addendum fixes doesn't apply there.

Also folded in a smaller round-5 finding: the mismatch's error message now explicitly says the failure is *already* reflected in the run's `failed_count` (not a new one), closing a minor UX ambiguity where a scientist reading both the run-level counts and the CLI log at different times could otherwise double-count the same underlying failure in their head — confirmed by tracing the guarded `UPDATE`: it only ever hits an already-`'failed'` row, so `status_update_matched: false` never corresponds to a *new* DB state change.

Two further round-5 findings upgraded the confidence (not yet the priority/action) behind addendum 4's two already-deferred risks with concrete numbers found in the repo: (a) `services/workflows/k8s_client.py`'s `WORKFLOWS_K8S_TTL_SECONDS` defaults to `3600` (1 hour) — combined with the `any_unknown` withholding only applying to a `'complete'` conclusion (not `'failed'`/`'partial'`), any multi-batch run whose batches finish more than ~1 hour apart has a real, non-theoretical window for the `'partial'`→`'failed'` regression; (b) the vendored write-back template's `generateName` suffix is Kubernetes' standard 5-character restricted-alphabet suffix (~27 characters, ~10-15M combinations) — birthday-paradox math over that space puts ~1% cumulative collision probability around 500-1,000 total workflow submissions over the program's lifetime, meaningfully undercutting "vanishingly unlikely." Neither has been actioned yet (no reviewer round has proposed a concrete fix, only sharper numbers for the existing "accepted" framing) — left for a follow-up decision, not blocking this change.

### Decision 6 addendum 6: a sixth /review-pr pass questioned whether `retriable` should generalize — deliberately scoped narrower

A sixth round argued addendum 5's fix was too narrow: `retriable` defaults `True` for every failure kind EXCEPT the one `status_update_matched: false` case it was traced from — including a corrupt/unparseable envelope file, a contract-validation failure, and every deterministic `RAISE EXCEPTION` branch inside `insert_cyl_result_envelope` (`"contract_version mismatch"`, `"no image_ids"`, etc.) — and that these can reproduce the identical whole-run cascade addendum 5 fixed, just via a different, more common trigger (`test_batch_ingest_cli_isolates_one_bad_envelope` already asserts the current, checked-in `exit_code != 0` for exactly this shape).

**Decision: do not generalize.** There are two philosophically different classes of failure here, and only one belongs in `retriable=False`:

- **A false-negative bookkeeping artifact** (addendum 5's actual case): the scan's data write *genuinely succeeded* (`was_noop: false`, real trait/blob rows committed) — reporting it as a failure reflects nothing wrong with the science, only a status-linkage guard that can never un-trip. Marking this `retriable=False` corrects a wrong signal.
- **A genuine per-scan processing failure** (a corrupt file, an invalid envelope, a real contract-version mismatch): the scan's data was *never* correctly written. The run reflecting a real, unresolved problem for that scan is the *correct* signal — retrying can't fix a corrupt file, but that's an efficiency complaint (wasted Argo retry budget, already raised as a non-blocking observation as far back as round 3), not a false-signal bug. Marking this `retriable=False` would make `batch_ingest_result` exit `0` — and the Argo Workflow step read as unproblematic — for a batch where a scan's data is permanently missing, hiding a real failure from the one signal (the step's own success/failure) that would otherwise show something is wrong.

Generalizing `retriable=False` to the second class would trade a real, currently-accepted UX gap (retries a corrupt file can't fix) for a worse one (a genuinely-failed scan silently reads as fine at the workflow level). Left as-is: `retriable=False` stays scoped to cases where the guarded outcome is *provably* a false negative, not merely a case where a retry is known to be futile.

The same round also traced a narrower, legitimately in-scope consequence of addendum 5's own mechanism: a transient network blip can let the batch's own end-of-batch reconciliation close a scan out as `'failed'` (its row was still `'queued'` when reconciliation ran) moments before that same scan's delayed-but-genuinely-successful delivery lands and hits the guard (`status_update_matched: false`, correctly `retriable=False`). If every other scan in the run succeeds, the run rolls up to `status: 'complete'` while `failed_count` still counts that one scan — a run reading `'complete'` next to a nonzero `failed_count`, which a scientist would naturally read as contradictory even though no data is actually wrong (the same "already counted, not a new failure" situation the addendum-5 message already explains). Accepted as a documented risk rather than fixed now: it requires a specific, narrow race window (a transient failure on the RPC call itself, not merely a slow one), and no reviewer round has proposed a fix that wouldn't touch `status_poller.py`'s rollup logic this late in the review process for a risk this narrow.

### Decision 6 addendum 7: a human review of the actual GitHub PR — after six automated `/review-pr` rounds — found two real bugs no automated round had caught, plus two message/UX gaps

After six full `/review-pr` rounds, the PR's author reviewed the real diff by hand on GitHub and posted five comments. Two were genuine correctness bugs in `status_poller.py` that every automated round had missed; one was a known-but-unfixed data-integrity gap, documented here rather than fixed; two were message/UX quality issues.

1. **The `any_unknown` withhold only ever gated a `'complete'` conclusion — never the backstop reconciliation block that follows it.** Decision 6's own reasoning (and `test_sweep_still_concludes_failed_or_partial_despite_an_unresolved_workflow`) correctly established that a `'partial'`/`'failed'` rollup is safe to *conclude* from confirmed-bad phases alone, even with an unresolved (404'd) sibling workflow this cycle — a confirmed non-Succeeded phase already rules out `'complete'` regardless of what the unresolved sibling turns out to have been. But that reasoning covers the STATUS conclusion only; it does not make it safe to *reconcile* a leftover `'queued'` row — an action Decision 6 itself describes as permanent (`fail_cyl_pipeline_run_scans_without_result` closes the row out as `'failed'` for good) — while a sibling workflow's real Argo outcome is still unconfirmed. Before this fix, `sweep_once` proceeded straight into the reconciliation block whenever `status != "running"`, with no `any_unknown` check of its own, so a run whose rollup concluded `'partial'`/`'failed'` while one workflow was 404'd this cycle could permanently mark that workflow's leftover `'queued'` scans `'failed'` even though the 404'd workflow might yet turn out to have genuinely succeeded on a later cycle (Argo GC timing is not synchronized with actual completion).

   Fixed by adding a check ahead of the reconciliation block: when there is at least one leftover `'queued'` row (`queued_workflow_names` non-empty) AND `any_unknown` is `True`, the poller withholds **both** reconciliation and this cycle's status write entirely (`continue`s, leaving the run a candidate for the next cycle) — mirroring the existing `'complete'`-withhold pattern, but scoped specifically to the case that actually needs it. This does not regress the already-tested "conclude `'partial'`/`'failed'` despite incomplete information" behavior: that test's fixture has zero leftover queued rows, so the new check's `queued_workflow_names` guard never engages for it — the status write proceeds exactly as before whenever there is nothing left to protect from a premature reconciliation.

2. **The reconciliation call had no `PGRST202` (signature-not-found) carve-out**, unlike the neighboring `update_run_status` call a few lines below it, which already treats a `PGRST202` `APIError` as an expected, transient condition during the deploy-ordering window (Migration A's app code going live slightly before its migration applies — see the Risks/Trade-offs section above) and deliberately does not mark the cycle unclean for it. The reconciliation call (also against a Migration-A-created RPC, `fail_cyl_pipeline_run_scans_without_result`) had only a generic `except Exception`, so the identical deploy-ordering window would have marked every affected cycle unclean and could trigger `run()`'s proactive reconnect during an entirely expected, self-healing condition.

   Fixed by adding an `except APIError` branch ahead of the generic handler, checking `exc.code == _SIGNATURE_NOT_FOUND_CODE` the same way `update_run_status`'s handler already does: log at `info` level and leave the cycle clean on a genuine `PGRST202`, fall through to the existing `warning`-level/`ok = False` handling for anything else (including a non-`PGRST202` `APIError` and any other exception).

3. **The no-op path's `source_id` join can, in one specific sequence, never link a later automated redelivery to its row — accepted as a documented risk, not fixed.** `insert_cyl_result_envelope`'s no-op branch (step 8, in the migration) only stamps `source_id` onto a `cyl_pipeline_run_scans` row when `p_argo_workflow_name` is supplied on *that specific call*. If the very *first* successful delivery for a given `idempotency_key` was made without `p_argo_workflow_name` (the manual/ad-hoc `ingest-result` invocation shape, or any caller that omits it), `source_id` is never stamped at all — so a later, automated no-op redelivery of the same envelope (now supplying `p_argo_workflow_name`, e.g. an Argo-retried write-back pod) has no `source_id` to join against, and its own status-linkage `UPDATE ... WHERE argo_workflow_name = ... AND source_id = v_source_id` can never match. The affected scan's row stays `'queued'` — until, eventually, the backstop reconciliation this addendum's fix #1 hardens (item 1 above) marks it `'failed'`, which is an *incorrect* outcome for a scan whose data was, in fact, already correctly written by the first delivery.

   **Decision: document as an accepted risk, do not fix in this change.** A candidate fix was considered — deriving `scan_id` (and from it, the row to update) from the already-committed trait/blob rows for this `source_id` rather than relying solely on the `argo_workflow_name` join — but this was explicitly declined: it would add a second, independent code path for locating the row to update, with its own correctness burden (which trait/blob table, which uniqueness assumption), for a case whose trigger (a no-`p_argo_workflow_name` first delivery followed by an automated no-op redelivery that *does* supply one) is narrow and not confirmed to occur in the actual write-back pipeline today — every current write-back invocation is either fully manual (never supplies `p_argo_workflow_name`, so no later automated redelivery of the *same* envelope would occur either) or fully automated (always supplies it, so the first delivery already stamps `source_id`). Left for a future change if a concrete trigger is ever observed.

4. **The reconciliation call's permission-denied error message named the right RPC (fixed by addendum 1 above) but never told the operator the right *role*.** `_reconcile_unresolved_scans_result` authenticates via the same client as write-back (`_authed_client(profile)`), which is not guaranteed to carry the `bloom_workflows` grant `fail_cyl_pipeline_run_scans_without_result` actually requires — addendum 1's fix only stopped the message from *misattributing* the wrong RPC/role (borrowed from `map_rpc_error`'s `insert_cyl_result_envelope`-specific hints), it never added a *correct* hint for this RPC's own grant.

   Fixed by appending a short role hint to the raw Postgres message specifically when it indicates `"permission denied"` (case-insensitive substring check — deliberately narrow, so a generic/transient error never gets an inapplicable hint tacked on): naming `bloom_workflows` as the required role, distinct from write-back's own grant, without naming either RPC (to avoid regressing the existing test pinning that this message must never name `insert_cyl_result_envelope` or suggest `bloom_writer`/`bloom_admin`).

5. **The `status_update_matched: false` message unconditionally asserted a single cause** ("it was likely already closed out as 'failed' by an earlier reconciliation attempt") when the same value also arises when *no row matches at all* — including via finding #3's documented no-op-path gap above. The two causes have different implications: "already closed out failed" means the run's `failed_count` already reflects this outcome (not new information), while "no row matched" can mean the scan is still sitting `'queued'` with nothing left to ever resolve it — a materially more concerning case the old message actively obscured by asserting the more benign explanation as fact.

   Fixed by rewording both identical occurrences of this message (`ingest_one_envelope` and the single-envelope `ingest_result` command) to name both possibilities explicitly rather than asserting one, and to note that the former case still needs manual verification rather than being unconditionally reassuring.

### Decision 6 addendum 8: a seventh `/review-pr` round found addendum 7's own fix could strand a run forever — reverted

A seventh round (5 parallel reviewers, run against the PR after addendum 7's fixes) found that addendum 7 item 1's own fix — gating the backstop reconciliation block on `not any_unknown` — was itself a regression, independently traced by two reviewers (Scientific Rigor, Behavioral Correctness) to the same root cause.

**The premise behind addendum 7 item 1 was wrong.** That fix assumed a `'partial'`/`'failed'` rollup with `any_unknown = True` meant "an unresolved sibling workflow whose real outcome might still come in on a later cycle" — mirroring the language of the original human review comment it was responding to ("a transient K8s lookup failure"). But `get_workflow_status`'s actual contract (`services/workflows/k8s_client.py`) says otherwise: it returns `None` **only** on a clean HTTP 404, and its own docstring already characterizes that as "most often ttlStrategy already cleaned it up" — i.e. normally a **permanent** condition, since a genuinely transient network/API failure raises `K8sStatusError` instead, an entirely different code path this loop's outer per-run isolation already handles (isolates that run alone for the cycle, `ok = False`, retried next cycle — nothing to do with `any_unknown`). Decision 6 itself already reasoned through this correctly, before addendum 7 existed: "by the time a workflow 404s, Argo no longer has any record of it — it cannot still be silently running," and explicitly designed reconciliation to apply to a 404'd workflow's own leftover queued rows for exactly that reason.

Given that, addendum 7's fix converted a bounded, narrow risk (the original human reviewer's concern, which — per this corrected understanding — was largely unfounded for the common case) into an unbounded one: any multi-batch run whose batches finish more than `WORKFLOWS_K8S_TTL_SECONDS` apart (routine — addendum 5 already established this isn't rare) will have a permanently-GC'd sibling workflow whose `any_unknown` flag never clears. The gate blocked **both** reconciliation and the status write whenever such a run had a leftover queued row, forever — `done_count`/`failed_count` frozen, the run never reaching a terminal status, and (since the withhold branch never set `ok = False`) completely silent: no log level above `warning`, no contribution to the consecutive-unclean-cycle counter, nothing an operator would notice short of comparing a run's `updated_at` against wall-clock time. This is a **worse** failure mode than the one addendum 7 item 1 fixed: the original bug could mislabel a scan as `'failed'` on an actual data-integrity error of at most one scan; this regression could freeze an entire run's progress indefinitely with no signal at all.

One reviewer (Behavioral Correctness) also noted the gate was scoped too broadly even on its own terms: it keyed off the run-wide `any_unknown` flag rather than whether the *specific* workflow owning the leftover queued row was the one unresolved — an unrelated third workflow 404ing in a 3+-batch run blocked reconciliation of an entirely different, fully-confirmed workflow's queued rows too.

**Decision: revert.** Removed the `not any_unknown` condition from the reconciliation block's guard entirely, restoring Decision 6's original design — the backstop reconciles and the status write proceeds whenever `status != "running"` and there is a leftover queued row, exactly as it did before addendum 7. `test_sweep_still_concludes_failed_or_partial_despite_an_unresolved_workflow` (the existing test this reasoning was already built on) and `test_sweep_withheld_complete_on_404_never_reaches_reconciliation` (the pre-existing, still-correct `'complete'`-withhold, unaffected by this revert) both remain green — confirming the revert doesn't regress anything the pre-addendum-7 design already got right. The addendum 7 item 1 test pair was replaced with a single test proving the restored behavior: `test_sweep_still_reconciles_partial_or_failed_despite_an_unresolved_sibling_workflow`.

Two smaller, independent findings from the same round were also fixed:

- **`bloomcli`'s reconciliation call had no `PGRST202` carve-out**, unlike the poller's own reconciliation call (addendum 7 item 2 added that one, but only on the poller side) — the same "a sibling code path didn't get the same treatment" pattern this PR has repeatedly hit, this time spanning the CLI/poller boundary rather than one file. `_reconcile_unresolved_scans_result` now recognizes `PGRST202` and reports "expected, transient deploy-ordering window" rather than a bare, alarming failure message; `retriable` stays `True` (the default), since Argo's own `retryStrategy` is the correct recovery mechanism for this window regardless.
- **The permission-denied role hint's `"permission denied" in message.lower()` check had no anchor to the specific RPC.** An unrelated error that happens to contain that same phrase for a different reason (e.g. a permission error inside the function body against a different object) would get the same misleading `bloom_workflows` hint. Anchored to the exact `"permission denied for function fail_cyl_pipeline_run_scans_without_result"` wording instead.

Also found, and fixed by documentation rather than code: the reconciliation call's `PGRST202` carve-out (addendum 7 item 2) was never given a spec scenario, and neither was the pre-existing `update_cyl_pipeline_run_status` `PGRST202` carve-out it mirrors (predating this whole change's later rounds, from Task 4.5) — a standing gap this round's additions made more visible rather than one this round introduced. Two new scenarios were added to the `cyl-pipeline-status-polling` spec delta covering the reconciliation call's own carve-out and the addendum-8 revert; `services/workflows/README.md`'s reconciliation paragraph was updated to match. The older `update_cyl_pipeline_run_status` gap was deliberately left alone as out of scope for this round.

Finally, this round's Testing Strategy reviewer caught a small but real documentation-accuracy issue unrelated to any of the above: addendum 7's own task entry (`tasks.md` Task 13.6) excluded `test_main.py`/`test_pipeline.py` from its reported `services/workflows` full-suite count, citing a "pre-existing, unrelated `sleap_roots_contracts`-import collection error" — a claim that does not reproduce in this environment (`sleap_roots_contracts` is a declared, installed dependency; both files import and their tests pass cleanly). ## Risks / Trade-offs

- **Same-batch race between the write-back step's retries and the reconciliation call.** `retryStrategy: {limit: 2, retryPolicy: Always}` on the write-back step means the whole container (all envelopes + the reconciliation call) can re-run from scratch. Mitigated by both RPCs' `WHERE status = 'queued'`/idempotency-key-based short-circuit guards — a second full run is a no-op for anything the first run already resolved.
- **A scan legitimately re-queued into a second run after already failing once** (e.g. a user manually retries a `'partial'` run's failed scans as a fresh `scan_ids`-targeted run) gets its own new `cyl_pipeline_run_scans` row (`UNIQUE(run_id, scan_id)` is per-run, not global) — its outcome is tracked independently under the new run's `argo_workflow_name`, which is correct and requires no special-casing.
- **Removing the `'running'`-skip optimization increases RPC call volume** (one `update_cyl_pipeline_run_status` call per candidate run per poll cycle, always, instead of only on transitions). At the existing `WORKFLOWS_STATUS_POLL_SECONDS=15` default and expected run concurrency, this is a small, bounded increase, not a scaling concern.
- **`argo_workflow_name` is not database-enforced-unique across runs.** Decision 1 relies on "one Argo Workflow name corresponds to exactly one batch dispatch" as an operational fact (Argo's `generateName` randomness), not a schema constraint — no `UNIQUE` constraint exists on `cyl_pipeline_run_scans.argo_workflow_name`. A pathological name collision (vanishingly unlikely in practice) would let the write-back `UPDATE`/the failure-marking RPC silently apply to the wrong run's rows. The same absence of a uniqueness guarantee also means the `AND status != 'failed'` guard on step (7) protects only against a *late delivery of the same scan's own outcome* — it does not, and cannot, distinguish that from a second, genuinely different envelope that happened to resolve to the same `(argo_workflow_name, scan_id)` pair while the row is already `'written'`, which would silently overwrite `source_id` a second time. Both are accepted as real but negligible-probability risks, consistent with this program not otherwise defending against Argo name collisions anywhere else, and consistent with the documented architecture never producing two distinct envelopes for one scan within one batch dispatch.
- **Deploy-ordering affects two independent consumers on two independent timelines, not one.**
  - *`status_poller.py` (Migration B's consumer):* this repo's `deploy.yml` applies application code before database migrations, for both `staging` and `prod` (`docker compose up -d --build` — which rebuilds and restarts the `workflows` container running `status_poller.py` — runs before the "Apply database migrations" step, in the same job). Between the moment the new build starts calling `update_cyl_pipeline_run_status` with `p_done_count`/`p_failed_count` and the moment the migration adding those parameters actually applies (later in the *same* job run), every such call fails (the old 2-arg function doesn't accept them). This is self-healing (each per-run call is already isolated by `sweep_once`'s existing per-run exception handling, and the poller retries every 15s) but is a real failure window this change introduces — and removing the `'running'`-skip optimization means it fires on every candidate run every cycle during that window, rather than only on transitions. Task 4.5 adds a targeted mitigation: catching the specific "function/signature not found" error class (Postgrest's `PGRST202`) and excluding it from the consecutive-unclean-cycle reconnect counter, so this expected, self-healing window doesn't also trigger an unnecessary client reconnect.
  - *`bloomctl` (Migration A's consumer):* unlike `status_poller.py`, `bloomctl` is **not** deployed by `deploy.yml` at all — it has no service entry in `docker-compose.prod.yml`. It is built and published to GHCR by a wholly separate, independently-triggered workflow (`.github/workflows/docker-build-bloomcli.yml`, triggered on push to `staging` or a GitHub Release), and consumed by Argo write-back pods in the separate `sleap-roots-pipeline` repo on a timeline **not bounded by `deploy.yml`'s migration-apply step at all**. If the new `bloomctl` image publishes and gets pulled by a write-back pod before this PR's migration has been applied to that environment, write-back calls fail with the same signature-not-found error class until the migration lands. This is a wider, less-bounded version of the `status_poller.py` risk and was not identified in the first review round. Accepted as a bounded, self-healing risk (the write-back step's own `retryStrategy: {limit: 2, retryPolicy: Always}` means a transient failure here is retried automatically, and `insert_cyl_result_envelope`'s guards make a delayed-but-eventually-successful retry safe) rather than trying to couple two independently-triggered CI workflows across the ordering gap — but Task 8's real-cluster E2E verification should be run only after confirming the target environment's migration has actually applied, specifically to avoid this window producing a flaky, non-representative E2E result.
  - Reordering either pipeline to apply migrations before code is out of scope for this change (it would affect every future migration+consumer PR in this repo, not just this one).
- **Rollback coupling with both consumer images — and no existing runbook for either.** Because PostgREST/Postgres RPC dispatch is signature-based, rolling back either migration while its consumer's already-deployed image still calls the new signature would break that consumer outright (the image would call a signature that no longer exists). For Migration B this means the `workflows`/`cyl-status-poller` container image (rolled back the normal way, via `deploy.yml`'s own git-revert-and-redeploy mechanism, since it's docker-compose-managed). For Migration A this means the `bloomctl` GHCR image — but since `bloomctl` isn't docker-compose-managed, `deploy.yml`'s existing "rollback on failure" step has no awareness of it at all, and there is currently no documented or automated procedure for retagging/re-pinning an older `bloomctl` image inside the separate `sleap-roots-pipeline` repo's `WorkflowTemplate`. A schema-only rollback of either migration is therefore not a safe incident-response lever on its own once this change has shipped. Preferring a forward fix (re-applying a corrected version of the same migration) over a schema rollback is the safer default for both, since every new/changed RPC's guards make a repeated/corrected forward migration safe to re-apply — a genuine rollback of Migration A's schema should not be attempted without first confirming (or accepting the risk of not being able to confirm) which `bloomctl` image tag is actually live in the cluster.
