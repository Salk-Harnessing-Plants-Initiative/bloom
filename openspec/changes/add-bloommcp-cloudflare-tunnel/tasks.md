## 3. CI-testable integration coverage (does NOT require live Cloudflare/off-VPN — testable directly against Caddy)

**Test infrastructure note:** `tests/integration/conftest.py` runs every existing integration test as a plain pytest process on the CI runner host, hitting Caddy via a host-published port — which already qualifies as "not on `supanet`'s trusted subnet" for free (3.3 needs no new infra). But nothing in this repo's integration tests can currently originate a request *from inside* `supanet` (3.2/3.4's positive/trusted-peer cases) — there is no fixture for attaching a test client to a specific Docker network. `docker compose exec` into an already-running `supanet`-attached service is itself a well-precedented pattern in this repo's CI (`pr-checks.yml` already uses it for psql readiness polling and to read an env var out of `bloommcp`) — what's new is calling it from inside a pytest integration test rather than a workflow YAML step, so it needs a small subprocess-invocation helper (with `-T` for non-interactive exec, matching every existing usage in this repo), not entirely new infrastructure. **Do not use `curl`** for the exec'd request: checked against the actual images, `kong:2.8.1` has curl stripped out in its own upstream build (`apt-get purge -y curl` after fetching its `.deb`), and every custom-built `supanet` service in this repo (`bloommcp`, `langchain-agent`, `bloom-web`, `studio`) explicitly avoids installing curl too, per their own Dockerfile/compose comments (they use `python`'s `urllib.request` or Node `fetch` in their healthchecks instead). Use `docker compose exec -T bloommcp python -c "import urllib.request; ..."` instead — `bloommcp`'s image has Python available by construction and this mirrors its own healthcheck's approach. Task 3.2 introduces this helper; 3.4 reuses it rather than duplicating it.

- [ ] 3.1 `tests/integration/test_caddy_tunnel_scope.py` — send requests directly to a running Caddy instance (as `pr-checks.yml`'s `compose-health-check` already does for other routes) with `Host: <tunnel-hostname>` for `/` and confirm it does not reach `bloom-web`/`studio`/`supabase-minio` (404, per the spec's "does not expose bloom-web" scenario). This is pure Caddy-config behavior, not something that needs the real tunnel.
- [ ] 3.2 `tests/integration/test_caddy_tunnel_waf_allows_in_range.py` — via `docker compose exec -T bloommcp python -c "import urllib.request; ..."` (see the test-infrastructure note above), send a request to Caddy with `Host: <tunnel-hostname>` and a genuine in-range `Cf-Connecting-IP`. **Expected passing signal is bloommcp's normal 401 + `WWW-Authenticate` header — NOT a 200.** bloommcp still requires real credentials this test doesn't have; success here means the IP filter let the request through to bloommcp at all, not that it fully authenticated. This is the positive-case counterpart the original tasks.md never had — without it, only the rejection paths below are covered, leaving the capability's actual purpose (letting legitimate traffic through) unverified.
- [ ] 3.3 `tests/integration/test_caddy_tunnel_waf_rejects_spoofed_header.py` — from the ordinary CI-runner vantage point (already outside `supanet`, no new infra needed), send a request with a forged `Cf-Connecting-IP` claiming an Anthropic-range IP; confirm it's rejected at the Caddy layer (not a 401 from bloommcp). This exercises `trusted_proxies` gating by *peer address* — a distinct code path from 3.4.
- [ ] 3.4 `tests/integration/test_caddy_tunnel_waf_rejects_missing_header.py` — reusing 3.2's `docker compose exec -T bloommcp python ...` helper, send a request with **no** `Cf-Connecting-IP` header at all (not spoofed, simply absent); confirm it's still rejected at the Caddy layer, because the client-IP fallback resolves to the exec'd container's own (non-Anthropic) address. This exercises the `client_ip_headers` fallback behavior specifically — kept as a separate test from 3.3 so a bug in one path can't be masked by the other happening to also reject for an unrelated reason.
