## 3. CI-testable integration coverage (does NOT require live Cloudflare/off-VPN — testable directly against Caddy)

**Test infrastructure note:** `tests/integration/conftest.py` runs every existing integration test as a plain pytest process on the CI runner host, hitting Caddy via a host-published port — which already qualifies as "not on `supanet`'s trusted subnet" for free (3.3 needs no new infra). But nothing in this repo's integration tests can currently originate a request *from inside* `supanet` (3.2/3.4's positive/trusted-peer cases) — there is no fixture for attaching a test client to a specific Docker network. `docker compose exec` into an already-running `supanet`-attached service is itself a well-precedented pattern in this repo's CI (`pr-checks.yml` already uses it for psql readiness polling and to read an env var out of `bloommcp`) — what's new is calling it from inside a pytest integration test rather than a workflow YAML step, so it needs a small subprocess-invocation helper (with `-T` for non-interactive exec, matching every existing usage in this repo), not entirely new infrastructure. **Do not use `curl`** for the exec'd request: checked against the actual images, `kong:2.8.1` has curl stripped out in its own upstream build (`apt-get purge -y curl` after fetching its `.deb`), and every custom-built `supanet` service in this repo (`bloommcp`, `langchain-agent`, `bloom-web`, `studio`) explicitly avoids installing curl too, per their own Dockerfile/compose comments (they use `python`'s `urllib.request` or Node `fetch` in their healthchecks instead).

Use `docker compose exec -T bloommcp python -` (feeding a script via stdin, not a `-c` one-liner) instead — `bloommcp`'s image has Python available by construction and this mirrors its own healthcheck's approach. **The request itself needs more than a bare `urlopen` call**, and the script must account for all of it: the tunnel hostname's site block is TLS-only (443, no plaintext fallback), so the request needs `https://`, a custom `Host` header, a custom `Cf-Connecting-IP` header, and an SSL context with **`check_hostname = False` specifically** (chain/CA verification stays on — the wildcard cert has no SAN for the internal `caddy` service name, only for the public hostnames, so only the hostname comparison needs skipping). **Do not use `ssl.CERT_NONE`** — that disables chain verification entirely and would make the test pass even against an unrelated or self-signed certificate, defeating the point of a WAF test. The script also needs `try/except urllib.error.HTTPError` to read `.code`/`.headers` for a non-2xx response, since plain `urlopen` raises rather than returns on 4xx/5xx (mirroring the pattern `tests/integration/conftest.py`'s own `api_request` helper already uses).

**Round-trip protocol** (the script runs inside the container; the pytest test on the CI runner host needs its result back): the script's only stdout output is one JSON line, e.g. `print(json.dumps({"status": code, "headers": dict(headers)}))` — capture it via `subprocess.run([...], input=script.encode(), capture_output=True)` from the pytest test, then `json.loads(result.stdout.decode().strip().splitlines()[-1])` (last line specifically, in case `docker compose exec` itself emits anything else to stdout first). Without an explicit protocol here, this round-trip (host pytest → docker exec → python script → back to host pytest) has no other way to hand a structured result back across the subprocess boundary.

Write this as a small script the test passes over stdin, not a semicolon-joined one-liner crammed into a shell argument. Task 3.2 introduces this helper; 3.4 reuses it rather than duplicating it.
