## ADDED Requirements

### Requirement: Every public id sequence MUST be ahead of its column's data

Each sequence-backed column in schema `public` SHALL have a sequence whose next value exceeds `max(col)`. Sequence-backed columns are those for which `pg_get_serial_sequence` returns a sequence, whether the column is `serial` or `GENERATED … AS IDENTITY`. A table is counted once at its partitioned parent, never at its child partitions.

The next value is `last_value + increment` when the sequence's `is_called` is true, and `last_value` when it is false. A sequence is **behind** when its column has at least one row and `max(col)` is greater than or equal to its next value.

Supabase-managed schemas (`auth`, `storage`, `realtime`, `net`, `pgmq`, `supabase_functions`) are out of scope.

#### Scenario: A freshly migrated database has no behind sequences

- **WHEN** every migration has been applied to an empty database, as in CI
- **THEN** no `public` sequence is behind its column

### Requirement: The advance-lagging-sequences migration MUST advance exactly the behind sequences

The migration `advance_lagging_id_sequences` SHALL advance every behind `public` sequence with `setval(seq, max(col), true)`, so the next default insert receives `max(col) + increment`. For each one it advances, it SHALL emit one `RAISE NOTICE` in this form:

```
advanced public.<seq> for <table>.<col>: next value <old> -> <new> (max(<col>) = <max>)
```

It SHALL NOT call `setval` on any sequence that is not behind, so a sequence never moves backwards, and a sequence that is ahead, equal-and-called or on an empty table keeps both `last_value` and `is_called`. It SHALL end with a `RAISE NOTICE` of the form `advance_lagging_id_sequences: <n> of <m> sequences advanced`. It SHALL lock each behind table against writes and re-check it under the lock before advancing it. It SHALL NOT visit child partitions or any schema other than `public`.

#### Scenario: A fully behind identity sequence is advanced

- **GIVEN** a `public` table with a `GENERATED BY DEFAULT AS IDENTITY` id holds rows with explicit ids 1–5
- **AND** its sequence is at `last_value` 1, `is_called` false
- **WHEN** the migration is applied
- **THEN** a default-id insert into that table receives id 6
- **AND** a NOTICE names the sequence, table and column, with old next value 1, new next value 6 and max 5

#### Scenario: A partly behind serial sequence is advanced

- **GIVEN** a `public` table with a `serial` id holds rows 1–10
- **AND** its sequence is at `last_value` 4, `is_called` true
- **WHEN** the migration is applied
- **THEN** the next default-id insert receives id 11

#### Scenario: A never-called sequence equal to max is advanced

- **GIVEN** a table with `max(id)` 3 and a sequence at `last_value` 3, `is_called` false
- **WHEN** the migration is applied
- **THEN** the next default-id insert receives id 4

#### Scenario: A called sequence equal to max is left untouched

- **GIVEN** a table with `max(id)` 3 and a sequence at `last_value` 3, `is_called` true
- **WHEN** the migration is applied
- **THEN** the sequence's `last_value` and `is_called` are unchanged, and no NOTICE names that table

#### Scenario: An ahead sequence is left untouched

- **GIVEN** a table with rows 1–3 and a sequence at `last_value` 50
- **AND** one such table has `is_called` true, and another has `is_called` false
- **WHEN** the migration is applied
- **THEN** each sequence's `last_value` and `is_called` are unchanged

#### Scenario: An empty table is skipped

- **GIVEN** an empty table whose sequence is at `last_value` 1, `is_called` false
- **WHEN** the migration is applied
- **THEN** the sequence is unchanged, and the first default-id insert receives id 1

#### Scenario: Increment is honoured

- **GIVEN** a table with rows 1–25 and a sequence with `INCREMENT BY 10`, at `last_value` 20, `is_called` true
- **WHEN** the migration is applied
- **THEN** the sequence is unchanged, because its next value is 30, not 21, and 30 exceeds the max

#### Scenario: Large ids and quoted names are handled

- **GIVEN** a behind `bigint` identity column holding 3000000000, in a mixed-case table name whose sequence column is not named `id`
- **WHEN** the migration is applied
- **THEN** the next default-id insert receives 3000000001

#### Scenario: Partitioned tables are visited once at the parent

- **GIVEN** a behind partitioned `public` table with two partitions holding its rows
- **WHEN** the migration is applied
- **THEN** exactly one NOTICE names the parent, and none names a partition

#### Scenario: Other schemas are not touched

- **GIVEN** a behind table in a schema other than `public`
- **WHEN** the migration is applied
- **THEN** that table's sequence is unchanged and is not counted in the summary

#### Scenario: Only behind tables are locked

- **WHEN** the migration body has run inside a transaction
- **THEN** that transaction holds `ShareRowExclusiveLock` on every behind table it advanced, and on no other table it visited

#### Scenario: Re-applying changes nothing

- **GIVEN** the migration has been applied
- **WHEN** its body is applied again
- **THEN** no sequence's `last_value` or `is_called` changes, no NOTICE reports an advanced sequence, and the summary reports 0 advanced

### Requirement: The advance-lagging-sequences migration MUST fail before changing anything when it cannot advance a behind sequence correctly

When any behind sequence cannot be advanced correctly, the migration SHALL `RAISE EXCEPTION` **before calling `setval` on any sequence**. That covers four cases:

- `current_user` lacks `UPDATE` on the sequence. The message names the sequence and its owner.
- `current_user` cannot lock the table.
- The sequence's increment is not positive.
- `max(col)` exceeds the sequence's maximum.

It SHALL NOT skip such a sequence with a warning. It SHALL wait at most `lock_timeout` (5s) for its table locks; a timeout also leaves every sequence unchanged. A sequence that is not behind SHALL never cause a failure.

#### Scenario: A behind sequence the role cannot advance fails the run and changes nothing

- **GIVEN** an advanceable behind table that sorts first
- **AND** a behind table whose sequence is owned by `supabase_admin`, with `UPDATE` revoked from `postgres`
- **WHEN** the migration body runs as `postgres`
- **THEN** it raises an exception naming that sequence and `supabase_admin`
- **AND** the advanceable behind table's sequence is unchanged

#### Scenario: A behind sequence with a non-positive increment fails

- **GIVEN** a behind table whose sequence has `INCREMENT BY -1`
- **WHEN** the migration body runs
- **THEN** it raises an exception naming the sequence and its increment

#### Scenario: A behind sequence whose max exceeds the sequence maximum fails

- **GIVEN** a table with rows 1–10 and a sequence with `MAXVALUE 5`
- **WHEN** the migration body runs
- **THEN** it raises an exception naming the sequence

#### Scenario: A non-behind sequence the role cannot advance is ignored

- **GIVEN** a sequence that is not behind, with `UPDATE` revoked from `postgres`
- **WHEN** the migration body runs as `postgres`
- **THEN** it completes without error, and the sequence is unchanged

### Requirement: The advance-lagging-sequences rollback MUST be a documented no-op

The rollback file for `advance_lagging_id_sequences` SHALL contain no `setval`, `nextval` or `ALTER SEQUENCE` outside SQL comments. Its header SHALL explain that restoring the previous values would put sequences back behind their data. It SHALL keep the repository's STAGING HOT-APPLY ONLY / `supabase migration repair` header convention.

#### Scenario: The rollback changes no sequence

- **WHEN** the rollback file is inspected
- **THEN** it contains no `setval`, `nextval` or `ALTER SEQUENCE` outside SQL comments, and its header states why it is a no-op

### Requirement: Deploy MUST fail without reverting code when any public id sequence is behind

The prod and staging deploy jobs SHALL each run `scripts/sql/sequences_behind.sql` against the live database in a step placed after "Rollback on failure". The step SHALL:

- run read-only, with `default_transaction_read_only=on` and a statement timeout;
- for each returned row, fail with an `::error` annotation naming the behind table, its column, `max` and next value;
- fail with a distinct annotation when the check itself cannot run.

Because the step comes after "Rollback on failure", its failure SHALL leave the deployed code in place. Rollback's existing conditions SHALL be unchanged. See `deploy-migrations` for the migration steps before it, and `deploy-health-check` for the other deploy gates.

#### Scenario: No behind sequences

- **WHEN** the deploy reaches the sequence check and the query returns no rows
- **THEN** the step passes

#### Scenario: A behind sequence fails the deploy and keeps the code

- **WHEN** the query returns a row
- **THEN** the step fails with an annotation naming that table, the job is marked failed, and the deployed code is not rolled back

#### Scenario: The check cannot run

- **WHEN** the step fails to connect or the query errors
- **THEN** the job is marked failed with an annotation saying the check could not run, distinct from the behind-sequence annotation

#### Scenario: Earlier failures still roll back

- **WHEN** a step before "Rollback on failure" fails
- **THEN** "Rollback on failure" runs as before, and the sequence check does not run

#### Scenario: The check never writes

- **WHEN** the check's SQL file is inspected
- **THEN** it is a single `SELECT` containing no `CREATE`, `DO`, `FUNCTION`, `INSERT`, `UPDATE`, `DELETE` or `setval`

### Requirement: make check MUST report behind public id sequences

`scripts/check_health.py` SHALL run `scripts/sql/sequences_behind.sql` and report one problem per behind sequence, naming its table, column, `max` and next value, so that `make check` exits non-zero. Given the same fixtures, the guard query SHALL return exactly the sequences the migration advances.

#### Scenario: A behind sequence is reported

- **GIVEN** query rows describing one behind sequence
- **WHEN** the sequence check formats them
- **THEN** there is one problem naming that table, and `make check` exits non-zero

#### Scenario: The guard and the migration agree

- **GIVEN** the shared scratch fixtures
- **WHEN** the guard query runs, and then the migration body runs
- **THEN** the guard's rows equal the set of sequences the body's NOTICEs report as advanced
- **AND** the guard returns no scratch rows afterwards

### Requirement: Dev data loaders MUST leave no public id sequence behind

Every repository loader that inserts explicit ids into sequence-backed `public` columns SHALL run `scripts/sql/advance_behind_sequences.sql` after its inserts. That covers `make load-test-data`, `supabase/_seed.sql` and `scripts/seed_gravi_mock_data.sql`. That script SHALL be byte-identical to the migration's advance body.

#### Scenario: Loaders reset what they bypass

- **WHEN** each loader is inspected
- **THEN** it runs or includes `scripts/sql/advance_behind_sequences.sql` after its last explicit-id insert

#### Scenario: The advance script matches the migration

- **WHEN** `scripts/sql/advance_behind_sequences.sql` and the migration's `DO` block are compared
- **THEN** they are identical

#### Scenario: A loaded dev stack passes make check

- **WHEN** a dev stack is migrated, `make load-test-data` is run, and then `make check` is run
- **THEN** `make check` reports no behind sequences
