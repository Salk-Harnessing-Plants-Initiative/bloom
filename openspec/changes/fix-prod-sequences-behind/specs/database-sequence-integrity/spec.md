## ADDED Requirements

### Requirement: A migration MUST advance every public id sequence that is behind its column's data

The migration `<ts>_advance_lagging_id_sequences.sql` SHALL visit every column in schema `public` that `pg_get_serial_sequence` resolves to a sequence. It covers both `serial` and `GENERATED … AS IDENTITY`, is not a hard-coded table list, and excludes partitions.

A sequence is **behind** when its column has at least one row and `max(col)` is greater than or equal to the value the sequence would hand out next. That value is `last_value + 1` when `is_called` is true, and `last_value` when it is false.

For each behind sequence, the migration SHALL:

- lock its table against writes;
- re-check under the lock that it is still behind;
- run `setval(seq, max(col), true)`, so the next default insert receives `max(col) + 1`;
- emit one `RAISE NOTICE` naming the sequence, table, column, old next value and new next value.

It SHALL NOT call `setval` on any sequence that is not behind, including empty tables, so a sequence never moves backwards and an ahead sequence keeps both `last_value` and `is_called`. It SHALL end with a `RAISE NOTICE` summarising how many sequences it advanced out of how many it checked. It SHALL NOT touch Supabase-managed schemas (`auth`, `storage`, `realtime`, `net`, `pgmq`, `supabase_functions`).

#### Scenario: A fully behind identity sequence is advanced

- **GIVEN** a `public` table with a `GENERATED BY DEFAULT AS IDENTITY` id holds rows with explicit ids 1–5
- **AND** its sequence is at `last_value` 1, `is_called` false
- **WHEN** the migration is applied
- **THEN** a default-id insert into that table succeeds and receives id 6
- **AND** a NOTICE reports that the table's sequence was advanced

#### Scenario: A partly behind serial sequence is advanced

- **GIVEN** a `public` table with a `serial` id holds rows with ids 1–10
- **AND** its sequence is at `last_value` 4, `is_called` true
- **WHEN** the migration is applied
- **THEN** the next default-id insert receives id 11

#### Scenario: A never-called sequence equal to max is advanced

- **GIVEN** a table whose `max(id)` is 3 and whose sequence is at `last_value` 3, `is_called` false
- **WHEN** the migration is applied
- **THEN** the next default-id insert receives id 4 instead of colliding on 3

#### Scenario: A called sequence equal to max is left untouched

- **GIVEN** a table whose `max(id)` is 3 and whose sequence is at `last_value` 3, `is_called` true
- **WHEN** the migration is applied
- **THEN** the sequence's `last_value` and `is_called` are unchanged
- **AND** no NOTICE names that table

#### Scenario: An ahead sequence is left untouched

- **GIVEN** a table with rows 1–3 whose sequence is at `last_value` 50
- **AND** one such table has `is_called` true and another has `is_called` false
- **WHEN** the migration is applied
- **THEN** each sequence's `last_value` and `is_called` are unchanged

#### Scenario: An empty table is skipped

- **GIVEN** an empty table whose sequence is at `last_value` 1, `is_called` false
- **WHEN** the migration is applied
- **THEN** the sequence is unchanged and the first default-id insert still receives id 1

#### Scenario: Re-applying changes nothing

- **GIVEN** the migration has been applied
- **WHEN** its body is applied again
- **THEN** no sequence's `last_value` or `is_called` changes
- **AND** no NOTICE reports an advanced sequence
- **AND** the summary reports 0 advanced

#### Scenario: A freshly migrated database has no behind sequences

- **WHEN** every migration has been applied to an empty database, as in CI
- **THEN** no `public` sequence is behind its column

### Requirement: The migration MUST fail rather than leave a behind sequence it cannot advance correctly

When a behind sequence cannot be advanced correctly, the migration SHALL `RAISE EXCEPTION`, so its transaction rolls back and the deploy fails. That covers three cases:

- `current_user` lacks `UPDATE` on the sequence. The message names the sequence and its owner.
- Its increment is not positive.
- `max(col)` exceeds the sequence's maximum.

It SHALL NOT skip the sequence with a warning. It SHALL wait at most a bounded `lock_timeout` for a table lock, and fail rather than hang. These checks apply only to behind sequences; a sequence that isn't behind never causes a failure.

#### Scenario: A behind sequence owned by another role fails the migration

- **GIVEN** a behind sequence owned by `supabase_admin`, on which `postgres` has no `UPDATE`
- **WHEN** the migration body runs as `postgres`
- **THEN** it raises an exception naming the sequence and `supabase_admin`
- **AND** no sequence it visited in that run has been changed after the rollback

#### Scenario: A non-behind sequence the role cannot advance is ignored

- **GIVEN** a sequence that is not behind, owned by a role `postgres` has no `UPDATE` on
- **WHEN** the migration body runs as `postgres`
- **THEN** it completes without error and the sequence is unchanged

### Requirement: The migration's rollback MUST be a documented no-op

`supabase/rollbacks/<ts>_advance_lagging_id_sequences_rollback.sql` SHALL contain no `setval` and no other statement that changes a sequence. Its header SHALL explain that restoring the previous values would only put sequences back behind their data. It SHALL keep the repository's rollback header convention.

#### Scenario: The rollback changes no sequence

- **WHEN** the rollback file is inspected
- **THEN** it contains no `setval`, `ALTER SEQUENCE` or `nextval`
- **AND** its header states why it is a no-op

### Requirement: Deploy MUST fail, without reverting code, when any public id sequence is behind

The prod and staging deploy jobs in `.github/workflows/deploy.yml` SHALL each have a step, after "Apply schema-USAGE grants", that runs `scripts/sql/sequences_behind.sql` against the live database. The step SHALL:

- run it inside a read-only transaction;
- when the query returns any row, fail with an `::error` annotation listing each behind table, its column, `max` and the sequence's next value.

A failure of this step SHALL NOT trigger "Rollback on failure", because reverting code cannot fix a sequence. Every other step's failure SHALL still trigger it as before. See `deploy-health-check` for the surrounding deploy gates.

#### Scenario: No behind sequences

- **WHEN** the deploy reaches the sequence check and the query returns no rows
- **THEN** the step passes and the deploy continues

#### Scenario: A behind sequence fails the deploy and keeps the code

- **WHEN** the query returns a row for a behind sequence
- **THEN** the step fails with an annotation naming that table
- **AND** the job is marked failed
- **AND** "Rollback on failure" does not run

#### Scenario: Earlier failures still roll back

- **WHEN** a step before the sequence check fails, such as the smoke test or migrations
- **THEN** the sequence check does not run
- **AND** "Rollback on failure" runs as before

#### Scenario: The check never writes

- **WHEN** the check runs
- **THEN** it executes inside `BEGIN TRANSACTION READ ONLY` and creates no object

### Requirement: make check MUST report behind public id sequences

`scripts/check_health.py` SHALL include a check that runs `scripts/sql/sequences_behind.sql` and reports one problem per behind sequence, naming the table. `make check`, and therefore CI's `dev-stack-smoke`, SHALL then fail. Seed scripts that insert explicit ids into sequence-backed columns SHALL reset those sequences afterwards, so a freshly seeded dev stack passes.

The guard query and the migration SHALL agree on what "behind" means. Given the same scratch fixtures, the query SHALL flag exactly the sequences the migration advances.

#### Scenario: A seeded dev stack passes

- **WHEN** a dev stack is migrated and seeded with `supabase/_seed.sql` and `scripts/seed_gravi_mock_data.sql`
- **THEN** `make check` reports no behind sequences

#### Scenario: A behind sequence is reported

- **GIVEN** a `public` table whose sequence is behind
- **WHEN** the sequence check runs
- **THEN** it reports a problem naming that table, and `make check` exits non-zero

#### Scenario: The guard and the migration agree

- **GIVEN** the scratch fixtures used by the migration tests (behind, partly behind, equal called and not called, ahead, empty)
- **WHEN** the guard query runs over them
- **THEN** it returns exactly the fixtures the migration advances
