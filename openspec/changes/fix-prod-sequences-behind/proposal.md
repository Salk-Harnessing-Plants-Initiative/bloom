## Why

In prod, 21 `public` tables have an id sequence behind their data (bloom#1022). Any insert that lets the database choose the id can draw one that is already taken, and fail with a duplicate-key error.

This surfaced in prod's first successful cylinder pipeline run (run 2, Workflow `sleap-roots-pipeline-x68sv`, 2026-10-02). `cyl_trait_sources` held legacy ids 1–5 with its sequence still at 1, so 5 of the 24 write-backs hit `cyl_trait_sources_pkey`. That table is now past its data (`last_value` 48). The other 20 are not:

- 17 sequences are still at 1, so their next default-id insert collides. These include `species`, `people`, `cyl_scanners`, `cyl_qc_sets` and `cyl_datasets`.
- 3 are partly behind (`cyl_experiments`, `phenotypers`, `cyl_scientists`), so inserts fail once the sequence reaches a taken id.

Staging has 0 of 68 behind. The repo has no `setval` for prod, so the most likely cause is a prod data import or restore that kept explicit ids and never reset the sequences. That import isn't recorded here. Every id column is `GENERATED BY DEFAULT AS IDENTITY` or `serial`, and both accept explicit ids without moving the sequence.

The same mistake exists in the repo for dev:

- `supabase/_seed.sql` inserts `cyl_scanners` ids 1 and 2 explicitly. Dev's `cyl_scanners` sequence is behind today (`max(id)` 1, sequence at 1, never called).
- `scripts/seed_gravi_mock_data.sql` does the same for `cyl_scientists`, `gravi_scan_metadata_section_plants` and `gravi_images`.

Nothing today checks that sequences are ahead of their data, so a future import or seed can bring this back silently.

## What Changes

The change lands in two PRs.

**PR 1: migration (carries this proposal)**

- A new forward-only migration, `<ts>_advance_lagging_id_sequences.sql`, finds every sequence-backed column in `public` with `pg_get_serial_sequence`. It does not use a hard-coded list.
  - It advances a sequence only when the sequence is actually behind: when the value it would hand out next is less than or equal to the column's `max`.
  - It sets that sequence to `setval(seq, max(col), true)`, so the next default insert gets `max + 1`.
  - It leaves ahead, equal and empty cases untouched, including `is_called`. The sequence never moves backwards.
  - It reports each change with `RAISE NOTICE`, plus a one-line summary.
  - It runs as `postgres` inside `supabase db push`'s per-file transaction. It locks each behind table against inserts while advancing it, under a `lock_timeout`.
- The migration fails loudly when it meets a behind sequence that the migrating role can't advance. It `RAISE EXCEPTION`s naming the sequence and its owner, so the file rolls back and the deploy goes red.
  - It also fails on a sequence with a non-positive increment.
  - Neither case exists in prod today. A read-only check on 2026-10-02 found all 65 prod sequences owned by `postgres`, all advanceable by it, and all with increment 1.
- It is a no-op where nothing is behind (staging) and safe to re-apply. On dev it advances `cyl_scanners`.
- Supabase-managed schemas (`auth`, `storage`, `realtime`, `net`, `pgmq`, `supabase_functions`) are out of scope. Bloom creates no schema of its own; every Bloom table is in `public`.
- A companion `supabase/rollbacks/<ts>_advance_lagging_id_sequences_rollback.sql` documents why it is a no-op: moving a sequence back behind its data would only reintroduce the collisions.
- Integration tests, written first, run against scratch tables created inside the test transaction. They cover: identity and serial, behind, partly behind, equal, ahead (called and not called), empty, re-apply, and a behind sequence the migrating role can't advance.
- The schema doesn't change. `make gen-types` and `make erd` should produce no diff, and the PR body uses `No schema changes.`

**PR 2: guard (code-only, against this same change)**

- One read-only "sequences behind" query, used in two places:
  - **Deploy:** a new step in `deploy.yml`, after "Apply schema-USAGE grants" on both prod and staging. It runs the query against the live DB and **fails the deploy** if any `public` sequence is behind, naming each table, its `max` and the sequence's next value.
  - **Dev and CI:** a `check_sequences` check in `scripts/check_health.py` (`make check`, which CI runs in `dev-stack-smoke`).
- The two dev seed scripts reset the sequences they bypass, so `make check` stays green after seeding.

## Impact

- **Affected specs:** a new capability, `database-sequence-integrity`, with all requirements `ADDED`.
  - `deploy-health-check` and `deploy-migrations` are not modified. They cover container health and how migrations are applied, not what is in the database.
  - The deploy step in PR 2 is specified in the new capability and cross-references `deploy-health-check`. No open change MODIFIES either spec.
- **Affected code:**
  - PR 1: `supabase/migrations/<ts>_advance_lagging_id_sequences.sql`, `supabase/rollbacks/<ts>_advance_lagging_id_sequences_rollback.sql`, `tests/integration/test_advance_lagging_id_sequences.py`.
  - PR 2: `scripts/sql/sequences_behind.sql` (new), `scripts/check_health.py`, `.github/workflows/deploy.yml`, `supabase/_seed.sql`, `scripts/seed_gravi_mock_data.sql`, `tests/unit/test_check_health*.py`, `tests/integration/test_sequences_behind_check.py`.
- **Data:** in prod the migration advances the 20 behind sequences. No row is changed.
- **Verification:** CI's database is empty, so CI cannot prove the prod fix (the bloom#780 pattern).
  - Commits and PRs say "Part of #1022", never a closing keyword.
  - After deploy, the read-only check is re-run on staging, then on prod after the staging→main promotion (each prod read with the user's OK). Before and after are recorded in tasks.md.
  - #1022 is closed by hand only after prod shows 0 behind, and with the user's approval.
- **Out of scope:**
  - Correcting run 2's 5 stale `failed` rows in `cyl_pipeline_run_scans`, which is a one-off prod data write needing its own go-ahead.
  - The broader gap that a write-back retry can't update a row an earlier attempt closed as `failed`. That is proposed as a separate issue.
