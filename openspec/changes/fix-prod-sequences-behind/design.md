## Context

**The incident.** Prod's first successful cylinder pipeline run (run 2, Workflow `sleap-roots-pipeline-x68sv`, 2026-10-02) failed 5 of its 24 write-backs on `cyl_trait_sources_pkey`. The table held legacy ids 1–5, and its sequence was still at 1. Argo's retry wrote the five as sources 25–29, and the sequence is now past the data.

**Prod today.** A read-only check of every sequence-backed column in `public` (issue #1022, 2026-10-02) found 21 other tables behind:

- 18 sequences are at 1, among them `species`, `people`, `cyl_scanners`, `cyl_datasets`, `cyl_qc_*`, `scrna_*` and `ortho_gene_id_map`. Their next default-id insert collides. That includes `scripts/ingest_scrnaseq.py`, which inserts `scrna_datasets` and `scrna_cells` with default ids.
- 3 are partly behind: `cyl_experiments`, `phenotypers` and `cyl_scientists`. They collide once the sequence reaches a taken id.

Staging has 0 of 68 behind.

**A second read-only prod check (2026-10-02, `BEGIN TRANSACTION READ ONLY … ROLLBACK`, as `postgres`)** found:

- 65 sequence-backed columns in `public`;
- every sequence and every table owned by `postgres`;
- `has_sequence_privilege('postgres', seq, 'UPDATE')` true for all of them;
- every increment equal to 1, and no sequence that cycles;
- `postgres` with `rolsuper = f`.

**Cause.** Every Bloom id column is `GENERATED BY DEFAULT AS IDENTITY` (58) or `serial`/`bigserial` (10). Both accept explicit ids without moving the sequence. Prod's load is unrecorded, and the user doesn't know how it was done. The repo has the same pattern in its dev loaders, none of which reset sequences:

- `make load-test-data` upserts `test_data/*.csv` with explicit `id` columns through PostgREST, into about 15 tables that overlap prod's list heavily;
- `supabase/_seed.sql` inserts `cyl_scanners` ids 1 and 2;
- `scripts/seed_gravi_mock_data.sql` inserts explicit ids into `cyl_scientists` and 7 `gravi_*` tables.

Dev's `cyl_scanners` is behind today (`max` 1, `last_value` 1, not called).

A plain-format `pg_dump`, which is what the weekly backup takes, restores sequence state exactly. A restore therefore reproduces whatever state was dumped. Any prod dump taken before this fix carries the 21 behind sequences.

**How migrations run.** `supabase db push` applies migrations as `postgres`, one transaction per file. `postgres` is not a superuser and not a member of `supabase_admin`. Supabase's default privileges grant `postgres` all rights on sequences and tables that `supabase_admin` creates in `public`; this was verified on dev.

## Goals / Non-Goals

**Goals**

- Advance every behind `public` sequence through the normal migration path, with no hand-run SQL against prod.
- Never move a sequence backwards, and never touch one that isn't behind. Re-applying changes nothing.
- Change nothing at all when the migration can't finish correctly.
- Make a recurrence visible:
  - a deploy check that fails the deploy;
  - a `make check` check;
  - dev loaders that reset what they bypass.

**Non-Goals**

- Supabase-managed schemas (`auth`, `storage`, `realtime`, `net`, `pgmq`, `supabase_functions`). Bloom creates no schema of its own, and `supabase/migrations/` contains no `CREATE SCHEMA`.
- Correcting run 2's 5 stale `failed` rows in `cyl_pipeline_run_scans`. That is a one-off prod data write needing its own go-ahead.
- The gap that a write-back retry can't update a row an earlier attempt closed as `failed`. That is proposed as a separate issue (tasks 5.6).
- Reconstructing how prod's data was originally loaded.

## Decisions

### D1. "Behind" means the next value handed out is already taken

The decision is in the spec. Its inputs come from the sequence relation itself: `last_value` and `is_called`, plus `seqincrement` from `pg_sequence`. `pg_sequences.last_value` is not used, because it is NULL until the sequence is first called and when the role lacks privilege.

```
next_value := CASE WHEN is_called THEN last_value + increment ELSE last_value END
behind     := max(col) IS NOT NULL AND max(col) >= next_value
```

A behind sequence is set with `setval(seq, max(col), true)`, so the next default insert gets `max + increment`. Since `max >= next_value`, the sequence only moves forward. In PL/pgSQL the `CASE` must sit in parentheses inside an `IF`, because PL/pgSQL ends the `IF` condition at the first `THEN`.

**Rejected: the issue's sketch, `setval(seq, GREATEST(max, last_value), true)` on every non-empty table.** It rewrites ahead sequences too. Take one with `last_value` 50, never called, over rows 1–3: the sketch marks it called, so its next value jumps from 50 to 51. Touching only behind sequences makes the no-op case literally zero `setval` calls.

### D2. Generic over `pg_get_serial_sequence` on `public`

The migration visits every column that has all of the following:

- it is in schema `public`;
- its table has `relkind IN ('r','p')` and `NOT relispartition`, so partitioned parents are in and child partitions are out;
- it is live (`attnum > 0`, not dropped);
- `pg_get_serial_sequence(...)` is not null.

Columns are visited in `ORDER BY` table and column, so the run is deterministic. This covers both `serial` and identity columns, and any number of sequence columns per table.

All names go through `format('%I')` or `regclass`. Values are handled as `bigint`, and 63 of the 68 columns are bigint.

LangChain's runtime `checkpoint*` tables in `public` are included if they have sequences. That is harmless, since advancing a behind sequence is always correct.

### D3. Fail loudly, before changing anything

The migration raises when a **behind** sequence:

- isn't advanceable by `current_user` (`NOT has_sequence_privilege(seq, 'UPDATE')`). The message names the sequence and its owner;
- sits on a table `current_user` can't lock, meaning it has none of UPDATE, DELETE or TRUNCATE. The message names the table and its owner;
- has `seqincrement <= 0`;
- has `max(col) > seqmax`.

These checks apply only to behind sequences. An unusual sequence that isn't behind never blocks a deploy. The user chose fail over skip-and-warn on 2026-10-02. None of these cases exists in prod today.

`setval` is not transactional: neither `ROLLBACK` nor `ROLLBACK TO SAVEPOINT` undoes it. A one-pass loop that advanced some sequences and then raised would leave those advanced. So the body runs in passes:

1. **Find and check.** Compute the behind set and check every behind sequence against D3's conditions. Raise on the first failure.
2. **Lock.** One `LOCK TABLE t1, t2, … IN SHARE ROW EXCLUSIVE MODE` over every behind table (D4).
3. **Re-check under the lock.** Recompute `max` and the sequence state, rebuild the behind set, and re-run D3's checks. Raise on the first failure.
4. **Advance.** `setval` each sequence that is still behind, and NOTICE it.

Every raise, including a `lock_timeout` in pass 2, happens before the first `setval`. A failed run therefore changes no sequence, and the deploy can simply be retried.

### D4. Locking

Prod takes writes during a deploy. A concurrent insert that supplies its own id above the old `max`, landing between reading `max` and `setval`, would leave the sequence behind again. Pass 2's lock prevents that.

`SHARE ROW EXCLUSIVE` blocks INSERT, UPDATE, DELETE and VACUUM. It doesn't block SELECT, `SELECT … FOR UPDATE/SHARE`, or the `FOR KEY SHARE` checks that child foreign keys take. While the request is queued, writers that arrive later wait behind it, but readers never do.

The file follows house style: top-level `BEGIN; SET LOCAL lock_timeout = '5s'; … COMMIT;`. A wait longer than that fails the migration, which is loud and retryable. Two cases can cause one:

- a long app transaction;
- an anti-wraparound autovacuum on a large table such as `scrna_counts` or `scrna_genes`.

Taking all the locks in one statement, after pass 1, keeps the deadlock window small. A deadlock with an app transaction that writes two behind tables in the opposite order is still possible. Postgres detects it within about 1s and aborts one side. If it aborts the migration, nothing has changed (D3) and the deploy is retried.

Only behind tables are locked: none on staging or CI, 21 on prod, 1 (`cyl_scanners`) on dev's first run. Each `max` is an index scan of the primary key.

Bare `nextval()` calls aren't blocked by the lock. No Bloom code makes one; Bloom code only uses defaults.

### D5. Reporting

Each advanced sequence gets one NOTICE:

```
advanced public.<seq> for <table>.<col>: next value <old_next> -> <max+increment> (max(<col>) = <max>)
```

The run ends with a summary:

```
advance_lagging_id_sequences: <n> of <m> sequences advanced
```

Tests assert the format and the counts relative to their fixtures, never hard-coded totals.

Whether `supabase db push` prints NOTICEs into the deploy log is checked in task 2.2. If it doesn't, the read-only checks in tasks §4–§5 are the only evidence.

### D6. Rollback is a documented no-op

The rollback file contains no statement that changes a sequence. Its header explains that the previous values were exactly the bug: moving a sequence back behind its data would bring the collisions back. It keeps the house convention: STAGING HOT-APPLY ONLY, plus `supabase migration repair --status reverted <ts>`.

### D7. Tests: scratch tables, with real sequences snapshotted

`setval` survives rollback, so the integration tests create `public._seq1022_<uuid>_*` tables inside the open transaction. Their sequences are new objects in that transaction, and `pg_conn.rollback()` drops them.

The scratch fixtures live in `tests/integration/sequence_fixtures.py`, so PR 2's guard tests reuse them.

The body comes from `sql_body()` with `BEGIN`/`COMMIT` stripped, and runs under `SET LOCAL ROLE postgres`.

The body also visits real `public` tables:

- On CI, nothing is behind after `db push`.
- On dev, `cyl_scanners` is behind until it is first advanced, and advancing it is the intended fix. That is why tasks 2.2 (`make migrate-local`) comes **before** 2.3 (the test run): otherwise the first test run would advance it and the dev evidence would be lost.
- Every test snapshots `(last_value, is_called)` for every real sequence before and after the body. Every real sequence that wasn't behind must come out unchanged.

**T8, the privilege test.** The test connection is `supabase_admin`. Under Supabase's default privileges, a table that `supabase_admin` creates still gives `postgres` UPDATE on its sequence. So T8 creates the table as `supabase_admin` and runs `REVOKE UPDATE ON SEQUENCE … FROM postgres`, revoking UPDATE only so `postgres` can still read the sequence state and the table. It asserts the precondition `NOT has_sequence_privilege('postgres', seq, 'UPDATE')`. Then it opens a `SAVEPOINT`, runs `SET LOCAL ROLE postgres`, runs the body and expects the exception, and finally runs `ROLLBACK TO SAVEPOINT`. That rollback also reverts the `SET LOCAL ROLE`.

T8 also includes an advanceable behind table, which sorts before the failing one. It asserts that table is unchanged after the failure, which proves D3's passes.

File-text checks run in `tests/unit/` with no database. They cover the rollback content, `lock_timeout`, and that the lock comes before the first `setval`.

### D8. Guard (PR 2)

**The query.** `scripts/sql/sequences_behind.sql` is one plain `SELECT`, with no `DO` block, function or `CREATE`. It reads `max` and `last_value, is_called` from each table and sequence through `query_to_xml(format(…))`, and `seqincrement` from `pg_sequence`. It returns one row per behind sequence: table, column, `max` and next value.

It is plain so it can run in a read-only transaction. Even a `pg_temp` function can't be created there; this was checked on dev on 2026-10-02.

**The deploy step.** "Check id sequences are not behind (production|staging)" runs **after "Rollback on failure"**, just before cleanup. It runs on both prod and staging, using each environment's existing grants-step `compose exec … psql -U supabase_admin` command:

- the SQL comes from the file on stdin;
- `PGOPTIONS='-c default_transaction_read_only=on -c statement_timeout=60s'`;
- each returned row prints a one-line `::error title=Id sequence behind its data (<env>)::<row>`, and the step exits 1;
- a failure to run prints a separate `::error title=Sequence check could not run (<env>)::`.

Because Rollback has already been evaluated by then, a red sequence check keeps the new code: reverting code can't fix a sequence. Rollback's condition is unchanged on both environments. Staging keeps `failure() && steps.preflight_staging.outcome == 'success'`, which `tests/unit/test_deploy_staging_supersede_and_pin.py` pins. A failure in any earlier step skips the check, because it has no `if:`, and rolls back exactly as today.

**`make check`.**

- A pure `sequence_problems(rows)` formats one problem per row.
- `check_sequences(conn)` runs the file and returns `sequence_problems(...)`.
- `main` includes it.

CI's `dev-stack-smoke` runs `make check` after `make migrate-local`, before its only seed (`scripts/ci/seed_smoke_experiments.sql`, default ids). So in CI it confirms the migrated state. It catches loader problems only on a developer's stack.

**Dev loaders.** `scripts/sql/advance_behind_sequences.sql` is the migration's `DO` block, copied byte for byte. A unit test pins the copy to the migration body. The isolation lint stops PR 1 from shipping files under `scripts/`.

These run it after inserting:

- `make load-test-data`, through `compose exec … psql`, since PostgREST can't call `setval`;
- `supabase/_seed.sql`;
- `scripts/seed_gravi_mock_data.sql`.

That replaces copying `seed_cyl_mock_data.sql`'s idiom, which hard-codes sequence names and can move a sequence backwards.

Nothing in CI runs these loaders, so their tests are:

- text tests: each loader runs or includes the advance script after its inserts;
- one manual `make load-test-data && make check` on a dev stack, recorded in tasks.md.

**Guard and migration agree.** The integration test runs the guard over the shared scratch fixtures, then the migration body. It asserts that the guard's rows equal the set the body's NOTICEs advanced, and that the guard returns no scratch rows afterwards.

## Risks / Trade-offs

- **Lock waits or a deadlock during the prod deploy.** Mitigated by locking only behind tables, in one statement, under a 5s `lock_timeout`. Any failure changes nothing and is retryable (D3, D4).
- **The prod fix is unprovable in CI,** because CI's database is empty (the bloom#780 pattern). That is why the change uses "Part of #1022" and read-only before/after checks.
- **A red deploy from data drift, with no automatic fix.** This is intended, per the user's decision on 2026-10-02. Clearing it takes a new migration that re-runs the advance body, never a hand `setval` on prod. The `_WIKI` runbook entry from PR 2 says so.
- **A red sequence check doesn't reopen deploy-gated issues** (the bloom#780 pattern). That is acceptable, because the check is not migration-gated. The runbook says to check them by hand.
