## Context

[bloom#625](https://github.com/Salk-Harnessing-Plants-Initiative/bloom/issues/625) — `list_experiments()`
(`bloommcp/src/bloom_mcp/data_access/supabase_reader.py:246-300`) enumerates `cyl_experiments` cheaply,
then calls `get_experiment_traits` once **per experiment** with no source/run pin, computing
`len({r["plant_id"] for r in rows})`/`len({r["trait_name"] for r in rows})` client-side and discarding
the rows. 224 experiments on staging today; only 9 have any `cyl_scan_traits` data reachable (via
`cyl_scan_traits.scan_id -> cyl_scans.plant_id -> cyl_plants.wave_id -> cyl_waves.experiment_id`), but
`experiment_id=1` alone contributes 13.8M of `cyl_scan_traits`'s 28.8M rows — fetching and discarding that
one experiment's full trait set is plausibly the dominant cost of the observed 4+-minute hang, not the
224x fan-out alone.

This is a direct, previously-flagged follow-up to `refactor-supabase-reader-db-tier2`'s own Decision D4
(that change's design.md, lines 261-324), which introduced today's per-experiment bulk-fetch shape and
explicitly named the risk: *"If this proves too slow at real experiment-count scale, a dedicated summary
RPC is the natural follow-up... no performance data yet shows the direct approach doesn't scale."* It
also flagged a **pre-existing correctness gap** this change fixes as a side effect, not just a
performance win: D4's unpinned bulk fetch could disagree with `load_experiment`'s latest-selection
semantics for the same experiment. The new function's `GROUP BY`-equivalent aggregation is required to
match `load_experiment`'s latest-selection surface exactly, closing that gap rather than reproducing it.

## Goals / Non-Goals

- **Goals:** `list_experiments()` returns in well under a second at staging's 224-experiment scale via
  one round trip instead of 224; the per-experiment counts it returns match what `load_experiment(str
(experiment_id))` would derive for that same experiment (same latest-selection semantics — fixing, not
  preserving, D4's known inconsistency); a deliberately chosen, overridable RPC timeout so a future slow
  query fails loudly; forward-only migration + rollback, tested up/down against local Supabase; the new
  function's signature is reusable by the separate, future source-discovery effort bloom#625 names as
  out of scope here.
- **Non-Goals:** the source-discovery/source-pinning MCP-facing capability itself (no new tool, no
  `source_id`/`run_id` parameter threaded through any analysis tool) — tracked separately per bloom#625.
  No RLS or write-grant change. No change to `get_experiment_traits`, `get_scan_traits`,
  `list_experiment_trait_sources`, or any existing view. No per-user auth change (shared `bloom_agent`
  role stays).

## Decisions

### D1 — Function signature: `bigint`, not the issue's literal `int`

**Status: needs Benfica's confirmation**, same review gate bloom#625 itself names for this decision.

```sql
CREATE OR REPLACE FUNCTION public.get_experiment_summary_counts(
    experiment_id_ bigint DEFAULT NULL,
    source_id_     bigint DEFAULT NULL,
    run_id_        text   DEFAULT NULL
) RETURNS TABLE (
    experiment_id bigint,
    n_plants      int,
    n_traits      int
)
LANGUAGE plpgsql STABLE SECURITY INVOKER
```

bloom#625's own SQL sketch uses `int` for `experiment_id_`/`source_id_`/the `experiment_id` return
column. Every existing sibling object on these same tables is `bigint`: `cyl_experiments.id` (`BIGINT
PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY`), `get_experiment_traits(experiment_id_ bigint, source_id_
bigint, run_id_ text)`, `get_scan_traits`, `list_experiment_trait_sources(experiment_id_ bigint)`.
Introducing `int` here would be a new, inconsistent type split across sibling RPCs reading the same
columns — recommending `bigint` throughout instead, treating the issue's `int` as shorthand rather than a
deliberate type choice. `n_plants`/`n_traits` stay plain `int` (a `COUNT(DISTINCT ...)` result, not a
foreign-key column — no experiment plausibly has more than 2^31 plants or traits).

**Not a byte-for-byte mirror of `get_experiment_traits`, despite reusing its shape.**
`get_experiment_traits`'s `experiment_id_` has **no default** (required, positional-first) — only
`source_id_`/`run_id_` default to `NULL`. This function deliberately defaults **all three**, including
`experiment_id_`, so `list_experiments()` can call it with `{}` to get every experiment's counts in one
round trip. That's a necessary, deliberate divergence, not an oversight to reconcile.

### D2 — Aggregation: reuse `get_experiment_traits`'s join chain and disjunction, not a `cyl_scan_traits_latest` join

bloom#625's own text says the unpinned case must "`GROUP BY` over the same latest-selection surface
(`cyl_scan_traits_latest`, not the raw table)." Read literally that's not buildable as a single join:
`cyl_scan_traits_latest`'s columns are `scan_id, trait_id, trait_name, source_id, value` — **no
`plant_id`, no `experiment_id`** (confirmed by reading the view's definition in
`20260701000000_cyl_trait_read_source_aware.sql`). Reaching `plant_id`/`experiment_id` requires the same
join chain `get_experiment_traits`/`get_scan_traits` already use:
`cyl_experiments -> cyl_waves -> cyl_plants -> cyl_scans -> cyl_scan_traits_source`. So this function
reuses `get_experiment_traits`'s **exact** `FROM`/`JOIN` chain and three-way disjunction against
`cyl_scan_traits_source` (default-latest via `src.is_latest` / pin `source_id_` / pin `run_id_`,
mutually exclusive) rather than joining the `_latest` view — this is the concrete mechanism that
satisfies bloom#625's "must match `load_experiment`'s latest-selection semantics" requirement, since it's
the same predicate `get_experiment_traits` itself evaluates, not a re-derivation:

```sql
RETURN QUERY
SELECT
    cyl_experiments.id AS experiment_id,
    COUNT(DISTINCT cyl_plants.id)::int AS n_plants,
    COUNT(DISTINCT src.trait_name)::int AS n_traits
FROM public.cyl_experiments
JOIN public.cyl_waves ON cyl_waves.experiment_id = cyl_experiments.id
JOIN public.cyl_plants ON cyl_plants.wave_id = cyl_waves.id
JOIN public.cyl_scans ON cyl_scans.plant_id = cyl_plants.id
JOIN public.cyl_scan_traits_source src ON src.scan_id = cyl_scans.id
WHERE (experiment_id_ IS NULL OR cyl_experiments.id = experiment_id_)
  AND (
        (source_id_ IS NULL AND run_id_ IS NULL AND src.is_latest)
     OR (source_id_ IS NOT NULL AND src.source_id = source_id_)
     OR (run_id_ IS NOT NULL AND src.source_id = (
            SELECT max(s2.source_id) FROM public.cyl_scan_traits_source s2
            WHERE s2.scan_id = src.scan_id AND s2.trait_id = src.trait_id
              AND s2.pipeline_run_id = run_id_))
  )
GROUP BY cyl_experiments.id;
```

Leading `IF source_id_ IS NOT NULL AND run_id_ IS NOT NULL THEN RAISE EXCEPTION ...` guard, same as
`get_experiment_traits`/`get_scan_traits` (requires `plpgsql`, matching D1's `LANGUAGE` choice).

**`COUNT(DISTINCT trait_name)`, not `trait_id`** — matches the Python code being replaced exactly
(`{r["trait_name"] for r in rows}`), and matches what a caller would see as "distinct trait columns" in
the pivoted wide frame.

**Only experiments with at least one matching row get a result row.** Since 215/224 experiments have no
`cyl_scan_traits` data reachable at all, an unpinned call returns rows for only ~9 experiments. This is
correct SQL (an inner-join aggregate has nothing to group for a zero-match experiment) but means
`list_experiments()` — not the SQL — is responsible for defaulting missing experiments to
`n_plants=0, n_traits=0` (see D3). Adding a `LEFT JOIN` from `cyl_experiments` to always emit a zero-row
per experiment was considered and rejected: it would need the join reordered specifically for the
`experiment_id_ IS NULL` case, complicating one function with two different join shapes for what is
already a cheap fixup in Python (`list_experiments()` already holds the full experiment-id list from its
own `cyl_experiments` `SELECT`).

### D3 — `list_experiments()` merges by `experiment_id`, defaulting missing entries to zero

```python
counts_by_id = {
    row["experiment_id"]: row
    for row in _sc.call_rpc(_RPC_GET_EXPERIMENT_SUMMARY_COUNTS, {
        "experiment_id_": None, "source_id_": None, "run_id_": None,
    })
}
for row in response.data:  # the existing cheap cyl_experiments SELECT, unchanged
    experiment_id = row["id"]
    counts = counts_by_id.get(experiment_id, {"n_plants": 0, "n_traits": 0})
    summary = ExperimentSummary(
        filename=str(experiment_id),
        stem=str(experiment_id),
        rows=counts["n_plants"],
        total_columns=counts["n_traits"] + _FIXED_COLUMN_COUNT,
        trait_columns=counts["n_traits"],
        experiment_name=str(row.get("name") or experiment_id),
        genotype_col=_GENOTYPE_COL,
        sample_id_col=_SAMPLE_ID_COL,
    )
    summaries.append(summary)
```

One RPC call total (not one per row), replacing lines 261-298's per-row `try/_sc.call_rpc/except` loop.
The `cyl_experiments` listing SELECT itself, and its per-row malformed-row handling (missing `"id"` key —
see `test_list_experiments_excludes_a_malformed_row`), stay exactly as they are; only the trait-count
lookup changes.

### D4 — Bulk-call failure now fails `list_experiments()` outright, not silently drops one experiment

Today, a `get_experiment_traits` failure for one experiment is caught per-row and that experiment is
excluded from the list (`logger.warning(...); continue`) — the other 223 still succeed independently.
With one bulk call, there is no "this experiment's fetch failed" granularity left: a
`get_experiment_summary_counts` failure means *no* experiment's counts. Wrap the call through the file's
existing `_safe_rpc` helper (used by `load_experiment`, not by today's `list_experiments()`) so a failure
raises `ExperimentReadError` rather than being swallowed — matching bloom#625's own acceptance criterion
that a blocked/slow query "fails with a clear, structured error instead of hanging" or, transitively,
instead of silently returning an empty or wrong list. This is a deliberate behavior change, not an
oversight: `list_experiments()` can no longer partially succeed the way it could when failure was
scoped per experiment.

### D5 — Bounded, overridable PostgREST/RPC timeout

**Status: default value needs benchmark data before merge** (bloom#625's own decision #3 — "needs to be
generous enough for legitimate slow queries... proposing to benchmark against a realistic
`load_experiment` call on the largest current experiment").

Traced the actual current behavior (reading the installed `supabase-py` 2.31.0 source, not assumed):
`supabase.create_client(url, key)` with no `options=` already gets `ClientOptions.postgrest_client_timeout
= DEFAULT_POSTGREST_CLIENT_TIMEOUT = 120` seconds (`postgrest/constants.py`), which flows through
`Client.postgrest` -> `_init_postgrest_client(timeout=...)` -> `SyncPostgrestClient.__init__` ->
`httpx.Client(timeout=...)` -> every `.rpc(...).execute()` call. So bloom#625's framing ("no client-side
timeout anywhere") is slightly imprecise — there already is one, just an un-chosen 120s default nobody
set deliberately. That reconciles with the observed 4+-minute hang: no *single* RPC call needed to exceed
120s for 224 sequential calls to sum past four minutes.

The fix is choosing a deliberate, bounded value and making it overridable, mirroring the existing
`get_storage_client(*, timeout_seconds: float | None = None)` precedent (`supabase_client.py:179-198`,
same file):

```python
_DEFAULT_POSTGREST_TIMEOUT_SECONDS = 30  # placeholder — see Testing/benchmark task before merge

def get_postgrest_client(*, timeout_seconds: float | None = None) -> supabase.Client:
    options = supabase.ClientOptions(
        postgrest_client_timeout=timeout_seconds
        if timeout_seconds is not None
        else _DEFAULT_POSTGREST_TIMEOUT_SECONDS
    )
    return supabase.create_client(url, key, options=options)
```

**This changes `get_postgrest_client()`'s signature**, which `test_supabase_client.py:128-134`
(`test_client_accessors_accept_no_caller_credential_parameter`) currently pins to zero parameters:

```python
assert set(inspect.signature(sc.get_postgrest_client).parameters) == set()
```

That assertion's own docstring frames it as guarding against a *caller-credential* parameter specifically
(no per-call API key/session injection) — `timeout_seconds` is orthogonal to that concern, so the test is
updated to `== {"timeout_seconds"}`, matching `get_storage_client`'s already-asserted set on the same
line. **Rejected alternative:** hardcode the timeout in the function body with no new parameter, leaving
the test untouched. Rejected because it forecloses tests (and any future caller) from exercising a tight
timeout deliberately — `get_storage_client`'s own precedent already established the overridable-kwarg
shape for exactly this reason, and diverging from it for the sibling accessor would be the inconsistency,
not the fix.

`call_rpc()` itself is unchanged — it calls `get_postgrest_client()` with no arguments, so it picks up
the new bounded default automatically; no caller of `call_rpc` needs to change to benefit.

**30s is a placeholder, not a final value.** Task 3.x (tasks.md) benchmarks a realistic `load_experiment`
call (the largest current experiment's raw fetch) against local/staging Postgres and adjusts this
constant before merge, per bloom#625's own proposed methodology. It must be generous enough that a
legitimate large-experiment `get_experiment_traits` call (Tier 2's `load_experiment` raw-tier fetch) does
not spuriously fail, but tight enough that a genuinely blocked query surfaces in seconds, not minutes.

## Migration / Rollback

Single forward-only migration `supabase/migrations/20260807000000_get_experiment_summary_counts.sql`
(later than every migration on both `main` and `staging` as of this proposal — both tips are at
`20260803000000_add_cyl_experiment_search.sql`; re-check immediately before opening the PR per this
repo's known same-day-collision precedent). `CREATE OR REPLACE FUNCTION` (safely re-runnable);
`REVOKE EXECUTE ON FUNCTION public.get_experiment_summary_counts(bigint, bigint, text) FROM PUBLIC;`
followed by `GRANT EXECUTE ... TO bloom_agent, bloom_user, bloom_admin, authenticated;` — matching Tier
1's round-1-review-tightened explicit-grant posture (`get_experiment_traits`), not `get_scan_traits`'s
older implicit-PUBLIC default. Companion
`supabase/rollbacks/20260807000000_get_experiment_summary_counts_rollback.sql`:
`DROP FUNCTION IF EXISTS public.get_experiment_summary_counts(bigint, bigint, text);` (full signature, to
avoid ambiguity under any future overload). Hand-edit the five tracked `database.types.ts` copies
(`web/lib`, `web/types`, `packages/bloom-js/src/types`, `packages/bloom-fs/src/types`,
`packages/bloom-nextjs-auth/src/lib`), matching each file's own existing style (some alphabetical
single-line `Args`, `web/types/database.types.ts` SQL-declaration-order multi-line) — same caveat as
Tier 1: no TypeScript caller exists, so `tsc --noEmit` gives no signal on the hand-edit; check it by hand
against the `RETURNS TABLE` clause. `n_plants`/`n_traits` are typed non-null `number` (a `COUNT(...)`
result is never `NULL`, unlike Tier 1's `trait_value`/`source_id`).

## Risks / Trade-offs

- **"Well under a second" is an acceptance target, not a guarantee this design proves on paper.** An
  unpinned call still does one full aggregate scan over `cyl_scan_traits_source`'s `is_latest` rows
  (which, per the existing view's own definition, is itself a computed predicate over the full 28.8M-row
  table, not a materialized/indexed flag) — dramatically cheaper than fetching and discarding 13.8M rows
  over the wire 9 times, but not provably sub-second without benchmarking against staging's actual data
  and indexes. If benchmarking (tasks.md) shows it isn't fast enough, an index on
  `cyl_scan_traits(is_latest, scan_id)` or equivalent is the natural next step — not added speculatively
  here, since no measurement yet shows it's needed.
- **D4's stricter failure mode is a real trade-off, not a pure improvement.** Today, one bad experiment
  (e.g. a data-integrity issue triggering an RPC error) silently disappears from the list while the rest
  load fine. After this change, the same bad state means the *whole* list call fails. This is the correct
  choice for a *timeout/backend-health* failure (the bug this issue exists to fix) but is a strictly worse
  outcome for a *data-integrity* failure isolated to one experiment. No such case is known to exist today
  (`test_list_experiments_excludes_a_failing_experiment`'s scenario was synthetic, not observed on
  staging) — flagged here so a future report of "the whole list is broken because of one experiment" is
  recognized as this trade-off, not a new regression to chase blindly.
- **The 120s pre-existing default was already a bound, just not a chosen one.** Framing this change as
  "adding a timeout where none existed" (bloom#625's literal words) slightly overstates the gap — the
  real fix is *choosing* a smaller, deliberate value backed by benchmark data, not introducing bounded
  behavior from scratch.
- **`get_experiment_summary_counts`'s reuse by the future source-discovery effort is speculative.** Its
  three-parameter shape is designed to be reusable, but that effort's actual proposal may still want a
  different shape once written — this change does not commit that future work to using this function
  unchanged, only avoids foreclosing it.

## Testing (TDD)

- **Integration tests** (`tests/integration/test_cyl_experiment_summary_counts.py`), following
  `test_cyl_read_path.py`'s/`test_cyl_experiment_traits.py`'s fixtures (`pg_conn`, `_seed_experiment_scan`,
  `_trait`, `_deliver`):
  - Unpinned call (`{}`) returns `(n_plants, n_traits)` for a multi-scan, multi-trait experiment matching
    a hand-computed count from seeded data.
  - Unpinned call's counts match `get_experiment_traits(experiment_id_)`'s own
    `len(distinct plant_id)`/`len(distinct trait_name)` byte-for-byte (the direct oracle bloom#625's
    acceptance criteria names — "counts in the listing match exactly what `load_experiment` would
    derive").
  - `source_id_`/`run_id_` pin each match `get_experiment_traits` with the same pin, same as the unpinned
    case above.
  - Both `source_id_` and `run_id_` set raises, same as `get_experiment_traits`/`get_scan_traits`.
  - An experiment with zero matching `cyl_scan_traits` rows returns **zero rows** from the function
    (not a zero-valued row) — pins D2's "no LEFT JOIN" decision so a regression doesn't silently start
    emitting synthetic zero-rows from SQL.
  - Cross-experiment isolation (mirrors the Tier 1 precedent's 2.8/2.13).
  - Role reads: `bloom_agent`/`bloom_user`/`bloom_admin` via `SET LOCAL ROLE`; `authenticated` via
    `has_function_privilege(...)`.
  - No-write-capability static scan of the migration SQL text (same regex-based check as Tier 1's 7.8).
  - Migration idempotency + rollback round-trip (mirrors Tier 1's 2.15/2.16).
  - PostgREST/HTTP-layer reachability smoke test (mirrors Tier 1's 7.7), skipped locally, run in CI's
    `compose-health-check`.
- **`bloommcp`-side unit tests** (`bloommcp/tests/data_access/test_supabase_reader.py`, fakes only, no
  live DB):
  - `test_list_experiments_enumerates_database_experiments` updated: seed via
    `fake_supabase_db.seed_traits(...)`, assert one `get_experiment_summary_counts` RPC call total (not
    per-experiment), correct `rows`/`trait_columns` mapping.
  - New: an experiment with no seeded traits gets `rows=0, trait_columns=0` (not excluded from the list),
    exercising D3's default-to-zero merge.
  - `test_list_experiments_excludes_a_failing_experiment` **deleted, not updated** — its premise (a
    per-experiment RPC failure excludes only that experiment) no longer holds; replaced by a new test
    asserting a `get_experiment_summary_counts` failure raises `ExperimentReadError` from
    `list_experiments()` (D4).
  - `test_list_experiments_excludes_a_malformed_row` stays as-is — unaffected by this change, since the
    malformed-row handling is in the unchanged `cyl_experiments` listing loop, not the trait-count fetch.
  - `bloommcp/tests/conftest.py`'s `FakeSupabaseDB.call_rpc` dispatcher gets a new
    `"get_experiment_summary_counts"` branch, deriving `{experiment_id, n_plants, n_traits}` rows from the
    same `self._traits` seed dict the existing `"get_experiment_traits"` branch already reads, applying
    the same `source_id_`/`run_id_` filtering logic — so a fake-backed test can't pass while the real SQL
    function's semantics disagree.
  - `bloommcp/tests/test_supabase_client.py`: `test_client_accessors_accept_no_caller_credential_parameter`
    updated to `{"timeout_seconds"}` for `get_postgrest_client` (D5); new test asserting a very small
    `timeout_seconds` override actually raises a timeout-shaped error against a slow fake/mock, proving
    the parameter is threaded through, not merely accepted and ignored.

Written RED first, confirmed failing (`UndefinedFunction` for the SQL tests; the updated
`bloommcp`-side tests fail against the current per-experiment implementation) before implementation.
