## ADDED Requirements

### Requirement: `cyl_pipeline_runs` table

The database SHALL provide a `cyl_pipeline_runs` table with `id BIGINT GENERATED BY DEFAULT AS
IDENTITY PRIMARY KEY`, one row per pipeline-trigger request. It SHALL provide columns
`target_level` (`text`, one of `'scan'|'wave'|'experiment'|'scan_ids'`), `target_id` (`bigint`,
nullable — `NULL` when `target_level = 'scan_ids'`), `params` (`jsonb`, stored exactly as supplied
in the trigger request body — this phase's route does not call `resolve_params()` or otherwise
derive `params` from a scan's Bloom metadata; resolving `{species, mode, age}` from metadata plus
user overrides, if needed, is the caller's responsibility), `requested_by` (`uuid`, attribution
only — not a visibility filter), `status` (`text`, one of
`'queued'|'submitted'|'running'|'complete'|'partial'|'failed'`, defaulting to `'queued'`),
`scan_count`/`done_count`/`reused_count`/`failed_count` (`integer`, defaulting to `0`), and
`created_at`/`submitted_at`/`completed_at` (`timestamptz`) plus `error_message` (`text`, nullable).

#### Scenario: A run row is created with defaults

- **WHEN** a row is inserted supplying only `target_level`, `target_id`, `params`, `requested_by`
- **THEN** `status` defaults to `'queued'`
- **AND** `scan_count`/`done_count`/`reused_count`/`failed_count` default to `0`
- **AND** `submitted_at`/`completed_at`/`error_message` are `NULL`

#### Scenario: target_id is nullable for scan_ids requests

- **WHEN** a row is inserted with `target_level = 'scan_ids'` and `target_id = NULL`
- **THEN** the insert succeeds

### Requirement: `cyl_pipeline_run_scans` table

The database SHALL provide a `cyl_pipeline_run_scans` table with `id BIGINT GENERATED BY DEFAULT AS
IDENTITY PRIMARY KEY`, one row per scan within a run. It SHALL provide `run_id` (`bigint NOT NULL
REFERENCES cyl_pipeline_runs(id)`), `scan_id` (`bigint NOT NULL REFERENCES cyl_scans(id)`), a
`UNIQUE(run_id, scan_id)` constraint, `batch_index` (`integer`, nullable until batching assigns it),
`argo_workflow_name` (`text`, nullable — filled in only once a later phase submits the batch),
`status` (`text`, one of `'queued'|'predicted'|'written'|'reused'|'failed'`, defaulting to
`'queued'` — note: this phase's route never writes `'reused'` itself; that value is set only by a
later phase once the cluster-side skip-if-done check actually determines a scan needed no new work,
see the `cyl-pipeline-trigger` capability's dedup requirement), `attempts` (`integer`, defaulting to
`0`), `source_id` (`bigint`, nullable, `REFERENCES cyl_trait_sources(id)`), `error_message` (`text`,
nullable), and standard `created_at`/`updated_at` timestamps.

#### Scenario: One row per scan per run, duplicates rejected

- **WHEN** a second row is inserted with the same `(run_id, scan_id)` pair as an existing row
- **THEN** the database rejects the insert with a unique-constraint violation

#### Scenario: A scan row can be created without a batch or workflow assignment yet

- **WHEN** a row is inserted supplying only `run_id`, `scan_id`, `status = 'queued'`
- **THEN** the insert succeeds with `batch_index`, `argo_workflow_name`, `source_id` all `NULL`

### Requirement: Role-based read/write access matches the standard cyl_* convention

Both tables SHALL have Row Level Security enabled. `bloom_admin` SHALL hold `FOR ALL` access.
`bloom_agent` and `bloom_user` SHALL hold read-only (`SELECT`) access, matching the repo-wide
convention that `bloom_user` no longer receives write policies. `bloom_workflows` SHALL hold
`SELECT` and a **column-scoped** `INSERT` on both tables — scoped to exactly the columns
`services/workflows/pipeline.py` populates (`target_level, target_id, params, requested_by, status,
scan_count, reused_count` on `cyl_pipeline_runs`; `run_id, scan_id, batch_index, status` on
`cyl_pipeline_run_scans`), matching this repo's own column-scoped-grant precedent for the same role
(`20260716000000_create_workflows_role.sql`'s `GRANT INSERT (scan_id, path, frames) ON
cyl_scan_videos`) rather than a blanket whole-table `INSERT`. It SHALL **NOT** hold `UPDATE` in this
phase: no code path in this phase updates either table after insert, and this repo's own convention
(`20260716000000_create_workflows_role.sql`) is to expand grants only when a new endpoint actually
needs them — a later phase (the dispatch worker's status writes) adds its own `UPDATE` grant via its
own migration when that code lands. No role other than `bloom_admin` and `bloom_workflows` SHALL hold
write access to either table.

#### Scenario: bloom_user can read but not write

- **WHEN** a session with role `bloom_user` attempts `SELECT` on `cyl_pipeline_runs`
- **THEN** the query succeeds
- **WHEN** the same session attempts `INSERT` or `UPDATE` on `cyl_pipeline_runs`
- **THEN** the database rejects it with an insufficient-privilege error

#### Scenario: bloom_workflows can insert but not yet update

- **WHEN** a session with role `bloom_workflows` inserts a row into `cyl_pipeline_runs`
- **THEN** the insert succeeds
- **WHEN** the same session attempts to `UPDATE` that row's `status` column
- **THEN** the database rejects it with an insufficient-privilege error (proving this phase's
  least-privilege boundary — `UPDATE` is intentionally not yet granted)

#### Scenario: bloom_workflows can insert only the columns it actually populates

- **WHEN** a session with role `bloom_workflows` inserts a `cyl_pipeline_run_scans` row supplying only
  `run_id`, `scan_id`, `batch_index`, `status`
- **THEN** the insert succeeds
- **WHEN** the same session attempts to insert a row that also supplies `argo_workflow_name`
- **THEN** the database rejects it with an insufficient-privilege error (proving the `INSERT` grant is
  column-scoped, not whole-table)

#### Scenario: anon has no access

- **WHEN** an unauthenticated (`anon`) request queries either table
- **THEN** Row Level Security denies all rows (no policy grants `anon` access)

### Requirement: Realtime publication

Both `cyl_pipeline_runs` and `cyl_pipeline_run_scans` SHALL be added to the `supabase_realtime`
publication via an idempotent `DO $$ ... EXCEPTION WHEN duplicate_object THEN NULL; END$$` block,
matching this repo's existing convention (e.g. `cyl_scans`, `gravi_scans`), so that Bloom's web UI
can subscribe to run/scan status changes without polling.

#### Scenario: Both new tables are in the Realtime publication

- **WHEN** the migration has been applied
- **THEN** `cyl_pipeline_runs` and `cyl_pipeline_run_scans` both appear in
  `pg_publication_tables` for `supabase_realtime`

#### Scenario: Re-applying the migration does not error

- **WHEN** the `ALTER PUBLICATION ... ADD TABLE` statements run a second time (e.g. a repeated
  `supabase db push`)
- **THEN** the migration completes without raising `duplicate_object`

### Requirement: bloom_workflows can check all of a scan's trait sources for the dedup preview

`bloom_workflows` SHALL hold column-scoped `SELECT (scan_id, source_id)` on `cyl_scan_traits` and
column-scoped `SELECT (id, metadata)` on `cyl_trait_sources` — the join path needed to check **all**
of a scan's trait sources (`cyl_scan_traits.scan_id → source_id → cyl_trait_sources.id`, a scan can
have more than one source from successive computations) for the dedup preview described in the
`cyl-pipeline-trigger` capability. This grant supports an existence check across all of a scan's
sources, not a filter to only its most recent one — see that capability's dedup requirement for why
"most recent" is the wrong criterion here. No other column or table access is granted by this
requirement.

#### Scenario: bloom_workflows can check every source for a scan, not only the most recent

- **WHEN** a session with role `bloom_workflows` selects `scan_id, source_id` from `cyl_scan_traits`
  and joins to `id, metadata` on `cyl_trait_sources`, for a scan that has more than one source
- **THEN** the query succeeds and returns all of that scan's sources, not only the one with the
  highest `source_id`

### Requirement: pgmq dispatch queue with a least-privilege enqueue function

The database SHALL provide a pgmq queue named `cyl_pipeline_dispatch` (via `pgmq.create`, guarded by
an existence check so re-applying is a no-op) and a `SECURITY DEFINER` function
`enqueue_cyl_pipeline_batch(p_run_id bigint, p_batch_index integer, p_scan_ids bigint[]) RETURNS
bigint` (returning the pgmq `msg_id`) that sends one message per batch. `EXECUTE` on this function
SHALL be revoked from `PUBLIC`, `anon`, and `authenticated`, and granted only to `bloom_workflows` —
matching the explicit triple-revoke this repo's pgmq precedent (bloom PR #469, referenced but not
depended upon) found necessary, since Supabase's default privileges grant new public-schema
functions `EXECUTE` to `anon`/`authenticated` directly.

#### Scenario: bloom_workflows can enqueue a batch

- **WHEN** a session with role `bloom_workflows` calls `enqueue_cyl_pipeline_batch` with a valid
  `run_id`, `batch_index`, and non-empty `scan_ids` array
- **THEN** the call succeeds and returns a pgmq `msg_id`
- **AND** a corresponding message is readable from the `cyl_pipeline_dispatch` queue

#### Scenario: EXECUTE is denied to anon, authenticated, and PUBLIC

- **WHEN** `has_function_privilege` is checked for `anon`, `authenticated`, and the implicit `PUBLIC`
  grantee against `enqueue_cyl_pipeline_batch`'s signature
- **THEN** each reports `EXECUTE` as `false`
- **AND** the same check for `bloom_workflows` reports `true`

### Requirement: Forward-only migration with a companion rollback script

The migration adding these tables, policies, publication entries, and queue/function SHALL be
additive-only (no destructive changes to existing tables) and MUST NOT be edited after it is applied
to any shared environment, matching this repo's forward-only migration convention. A companion manual
rollback script SHALL be provided under `supabase/rollbacks/` that drops the new tables, function,
queue, and publication entries, returning the schema to its prior state. The rollback script's
correctness SHALL be verified by actually applying it (in a rolled-back test transaction), not merely
by inspection.

#### Scenario: Rollback script removes everything the migration added

- **WHEN** the companion rollback script is applied to a database where the migration had been
  applied
- **THEN** `cyl_pipeline_runs` and `cyl_pipeline_run_scans` no longer exist
- **AND** `enqueue_cyl_pipeline_batch` no longer exists
- **AND** the `cyl_pipeline_dispatch` pgmq queue no longer exists

#### Scenario: The migration body is idempotent

- **WHEN** the migration's SQL body is applied a second time (e.g. within one open transaction, for
  test purposes)
- **THEN** it completes without error
