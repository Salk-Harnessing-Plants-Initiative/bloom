## MODIFIED Requirements

### Requirement: Migration failures MUST be highly visible on GitHub Actions

Default step failure (red X with CLI error in step logs) is insufficient. Each deploy and CI run MUST produce three layers of visibility: a top-of-run error banner on failure, an actionable `migration list` diagnostic step, and a markdown summary panel on every run. Layer C MUST use the CLI's native markdown output — the `-o json` flag does NOT exist on the `migration list` subcommand in Supabase CLI v2.92.1.

Both the Layer B diagnostic step (`Show migration status on failure`, `if: failure()`) and the Layer C summary step (`Migration summary`, `if: always()`) depend on `.env.ci`, which is generated by an earlier step in the same `compose-health-check` job. Each of these two steps SHALL check `.env.ci` exists as the first action in its `run:` block and, if absent, print a skip message and exit 0 instead of proceeding — so a run canceled early, or a job that failed at an earlier unrelated step, before `.env.ci` was generated reports cleanly instead of stacking a missing-file error on top of the real signal.

#### Scenario: Migration failure emits a workflow error annotation

Given `supabase db push` exits non-zero
When the "Apply database migrations" step handles the failure
Then the step MUST emit a `::error title=Migration failed::` annotation
And the step MUST exit 1 so the workflow is marked as failed

#### Scenario: Diagnostic step runs on any migration failure

Given the "Apply database migrations" step has failed
When the workflow evaluates subsequent steps
Then a step with `if: failure()` MUST run `supabase migration list --db-url <url>` against the target database
And the output MUST show which migrations are recorded in `supabase_migrations.schema_migrations` and which files in `supabase/migrations/` are pending

#### Scenario: Migration state MUST appear in workflow summary via raw markdown

Given the workflow has attempted migrations (success or failure)
When the job finishes
Then a step with `if: always()` MUST write markdown to `$GITHUB_STEP_SUMMARY`
And the markdown MUST contain the raw output of `supabase migration list --db-url <url>` (a markdown table with `Local | Remote | Time (UTC)` columns emitted natively by the CLI)
And the implementation MUST NOT rely on `-o json` — that flag does not exist on the `migration list` subcommand in Supabase CLI v2.92.1

#### Scenario: Migration summary step guards against .env.ci never being generated

- **GIVEN** the `compose-health-check` job's `Migration summary` step (`if: always()`) is about to run
- **AND** `.env.ci` does not exist because a superseding push canceled the run before "Generate .env.ci from secrets" completed
- **WHEN** the step evaluates the guard as the first action in its `run:` block
- **THEN** it SHALL print a skip message and exit 0 instead of attempting to grep `.env.ci` or call `supabase migration list`
- **AND** it SHALL NOT fail with a missing-file error

#### Scenario: Diagnostic step guards against .env.ci never being generated

- **GIVEN** the `compose-health-check` job's `Show migration status on failure` step (`if: failure()`) is about to run
- **AND** an earlier, unrelated step (e.g. "Install Supabase CLI") failed before "Generate .env.ci from secrets" ever ran, so `.env.ci` does not exist
- **WHEN** the step evaluates the guard as the first action in its `run:` block
- **THEN** it SHALL print a skip message and exit 0 instead of attempting to grep `.env.ci`
- **AND** it SHALL NOT stack a missing-file error on top of the genuine earlier failure

## ADDED Requirements

### Requirement: CI job Cleanup steps SHALL guard against their compose env file never being generated

The `compose-health-check` job's `Cleanup` step (`docker compose --env-file .env.ci down -v`) and the `dev-stack-smoke` job's `Cleanup` step (`docker compose -f docker-compose.dev.yml --env-file .env.dev down -v`) both run `if: always()` and both depend on an env file (`.env.ci` / `.env.dev` respectively) generated by an earlier step in the same job. `pr-checks.yml`'s `concurrency: { cancel-in-progress: true }` block is workflow-level, not job-level, so a superseding push to the same ref cancels every job in the run simultaneously — either job's `Cleanup` step can run before its env file was ever generated. Each `Cleanup` step SHALL check its env file exists as the first action in its `run:` block and, if absent, print a skip message and exit 0 instead of attempting `docker compose --env-file <file> down -v`, which errors with `couldn't find env file` — and there is nothing to tear down anyway, since the compose stack was never brought up.

#### Scenario: compose-health-check Cleanup guards against .env.ci never being generated

- **GIVEN** the `compose-health-check` run was canceled before "Generate .env.ci from secrets" completed
- **WHEN** the `Cleanup` step runs under `if: always()`
- **THEN** it SHALL detect `.env.ci` is absent and exit 0 with a skip message
- **AND** it SHALL NOT fail on a `couldn't find env file` error

#### Scenario: dev-stack-smoke Cleanup guards against .env.dev never being generated

- **GIVEN** the `dev-stack-smoke` run was canceled before "make init (generate .env.dev with fresh local secrets)" completed
- **WHEN** the `Cleanup` step runs under `if: always()`
- **THEN** it SHALL detect `.env.dev` is absent and exit 0 with a skip message
- **AND** it SHALL NOT fail on a `couldn't find env file` error

#### Scenario: Normal teardown is unaffected when the env file exists

- **GIVEN** a `compose-health-check` or `dev-stack-smoke` run reached the step that generates its env file
- **WHEN** the corresponding `Cleanup` step runs
- **THEN** the guard SHALL pass and `docker compose --env-file <file> down -v` SHALL run exactly as before this change
