## Why

`FakeResultStore` is happy-path-only, so any workflow test that runs against it proves nothing about the failure semantics `SupabaseResultStore` actually has — including the guards #324 adds (commit-failure cleanup, duplicate-`v<N>` reallocation). `test_store_parity.py` only exercises single-output create→commit→get; both stores share `_artifacts.hash_outputs`, so its hash/key assertions are tautological rather than a real cross-backend check.

Tracked out of the `/review-pr` of #323, deferred pending #324. **#324 is implemented on the stacked branch this change builds on, but has not yet merged to `staging`** (PR #464 is open at the time of writing). This change mirrors PR #464's exact guard structure (`_MAX_ID_ATTEMPTS`, the two-phase collision check, `CommitFailedError` semantics) — if that structure changes during #464's own review, this proposal should be re-checked before implementation starts, and this change should not merge ahead of #464.

## What Changes

- Add a failure-injection surface to `FakeResultStore` (new public methods on the concrete class, not the `ResultStore` Protocol) so tests can force a commit failure after N of the staged outputs are recorded (`N` ranges `0..len(outputs)` inclusive; `N == len(outputs)` models a failure at the pre-append/manifest-write-equivalent step) and a duplicate-`v<N>` collision between `create_run` and `commit` — mirroring the scenarios `test_supabase_result_store.py` covers via `monkeypatch`ing `bloom_mcp.supabase_client`.
- Give `FakeResultStore.commit` an explicit per-output recording loop after `hash_outputs` (mirroring `SupabaseResultStore.commit`'s upload loop), so the failure-injection hook has a real per-iteration checkpoint — today the fake calls `hash_outputs` once with no per-output step to fail at. No change to `_artifacts.hash_outputs` itself or its shared (and already-tautological) role.
- Switch `FakeResultStore`'s version-id allocation from count-based (`f"v{len(existing)+1}"`) to the same scan-based `next_version_id` (`bloom_mcp.storage.versioning`) `SupabaseResultStore` already uses, via a small duck-typed adapter (the fake has no `Manifest`, only a `list[StoredRun]`) — so collision/reallocation is meaningful and provably uses identical semantics to the real adapter, not a reimplementation that could quietly diverge. Give `commit` the same two-phase guard (pre-record check + bounded reallocation, pre-append recheck) as `SupabaseResultStore.commit`.
- Fix two latent ordering bugs in `FakeResultStore.commit`, both currently invisible because nothing in the fake's commit path ever fails: (1) the run is dropped from `self._open` *before* the hash/record step, so an injected mid-commit failure would wrongly make a retry raise `RunStateError` instead of succeeding; (2) the staging dir is deleted unconditionally in `hash_outputs`'s `finally`, so a failed commit would not leave it retryable. Both must only happen on the success branch, matching `SupabaseResultStore.commit`'s success-only teardown.
- Add a seed hook so a v2-shaped historical run (no `seed`/`agent`/`output_sha256`/`output_keys`) can be registered on `FakeResultStore` directly, so v2-manifest back-compat becomes a parity scenario instead of `SupabaseResultStore`-only.
- Parametrize `test_store_parity.py`'s scenario set across `fake`/`supabase` to add: commit-failure retry, duplicate-id reallocation (the realistic, sequential-interleaving case — two `create_run` calls naturally collide on both backends with no injection needed), and v2-manifest back-compat. A small per-kind test helper hides "monkeypatch `supabase_client.upload_file`/`write_manifest`" vs. "call the fake's injection hook" behind one call so each scenario body runs unmodified against both backends. Retry-exhaustion and the late/pre-append collision are deliberately *not* re-parametrized here — each backend already covers them independently (see design.md Decision G) — to avoid a second, structurally mismatched injection helper for marginal added confidence.
- Add `FakeResultStore`-only unit tests for the new injection hooks in `test_fake_result_store.py`, mirroring the applicable subset of `test_supabase_result_store.py`'s failure/collision tests (5 of its 8 — see design.md for which two are intentionally not mirrored, and why).

## Impact

- Affected specs: `bloommcp-result-store` (MODIFIED: `FakeResultStore Adapter` requirement — gains the "Fake simulates a mid-commit failure..." and "...a duplicate-id collision..." scenarios, and extends the existing "Fake and Supabase adapters agree on observable behaviour" scenario's coverage)
- Affected code:
  - `bloommcp/src/bloom_mcp/result_store/fake_store.py` (per-output recording loop, scan-based id allocation + two-phase guard, injection hooks, the two ordering-bug fixes)
  - `bloommcp/tests/result_store/test_store_parity.py` (parametrized failure/collision/v2-backcompat scenarios + shared injection helper)
  - `bloommcp/tests/result_store/test_fake_result_store.py` (new fake-only injection-hook tests)
  - `bloommcp/docs/2026-06-15-bloom-mcp-phase2-persistence-design.md` (§8's #325 note, and the related #324 bullet at line 113 / §7's Tier-2 note at line 107)
- Verified unaffected (checked, not just assumed): the 7 other test files that construct `FakeResultStore` directly (`test_qc_clean_tool.py`, `test_straggler_routing.py`, `test_clustering_tool.py`, `test_pca_analysis_tool.py`, `test_qc_inspect_tool.py`, `test_remove_outliers_tool.py`, `test_workflow_persistence.py`) — none inspect staging-dir state or `_open` after a failure, so the ordering-bug fixes and the new recording loop are behavior-preserving for them.
- Not affected: `ResultStore` port/Protocol signatures, manifest schema, `SupabaseResultStore` (PR #464, a separate change), `ExperimentReader`/`FakeReader`/`SupabaseReader` — see design.md's Non-Goals for why the reader side is out of scope for this pass despite the issue title, and why that scoping call needs explicit reviewer sign-off (issue #325 has no comments confirming it).
