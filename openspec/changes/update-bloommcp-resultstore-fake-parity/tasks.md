## 3. Parametrize `test_store_parity.py`

- [x] 3.1 Add `_inject_commit_failure(kind, store, monkeypatch, *, experiment, tool_class, after_outputs, num_outputs)`: for `"fake"`, calls `store.fail_next_commit(...)`; for `"supabase"`, monkeypatches `bloom_mcp.supabase_client.upload_file` to fail on the `(after_outputs + 1)`-th call when `after_outputs < num_outputs`, or monkeypatches `bloom_mcp.result_store.supabase_store.write_manifest` to raise when `after_outputs == num_outputs` (the manifest-write-equivalent boundary).
- [x] 3.2 Parametrized scenario `test_commit_failure_retry_parity` — both backends leave `list_runs` unadvanced after an injected failure and succeed on retry with the same `run_ref`; asserts on `version_dir` prefix (non-shared logic), not only `hash_outputs`'s shared output.
- [x] 3.3 Parametrized scenario `test_duplicate_id_reallocates_to_distinct_ids_parity` — **no injection helper needed**: two plain `create_run` calls against empty state allocate the *same* provisional id on both backends (verified via `assert run1.version_id == run2.version_id`), and committing both lands on distinct, non-clobbered ids/bytes/hashes on both. Simpler than the originally-planned `_seed_collision` parity helper and exercises the exact same realistic "interleaved sequential commits" path both `SupabaseResultStore`'s own test and the fake's section-2 test cover directly.
- [x] 3.4 Parametrized scenario `test_v2_backcompat_parity` — seed a v2-shaped run (`seed_v2_run` on the fake, the existing `manifest_v2.json` fixture written into `fake_supabase_storage.objects` for `SupabaseResultStore`) and commit a new run; asserts it appends alongside the v2 entry on both backends with `get_run("latest")` resolving to the new one.
- [x] 3.5 **Scoping decision, deviating from the original plan**: retry-exhaustion and the late/pre-append collision are **not** re-parametrized here. Both are already independently, thoroughly covered on each backend — `SupabaseResultStore` by its 3 existing tests (`test_retry_exhaustion_before_upload_raises_with_no_uploads`, `test_prewrite_collision_cleans_up_and_retry_succeeds`, plus the interleaved-ids test), the fake by section 2's new mirrors (2.9–2.11) — and building a `_seed_collision` parity helper that reaches into `SupabaseResultStore`'s internals (raw manifest JSON seeding for one check, monkeypatching an `AnalysisDir` instance's `read_manifest` for the other) to force these exact edge cases into a *shared* scenario body added test-harness complexity disproportionate to the marginal confidence gained over the existing independent coverage. `test_duplicate_id_reallocates_to_distinct_ids_parity` (3.3) already proves the realistic, common case — sequential interleaved commits — cross-backend.
