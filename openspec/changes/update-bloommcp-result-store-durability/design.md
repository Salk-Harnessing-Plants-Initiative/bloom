## Context

`SupabaseResultStore.commit` (`bloommcp/src/bloom_mcp/result_store/supabase_store.py:96`) uploads each staged output, builds the v3 `VersionEntry`, then writes the manifest last. This ordering is already correct for the single-writer case — see the existing spec scenario "Commit failure cleans up and does not corrupt the manifest" — but issue #324 (deferred out of the #323 review, referenced from the persistence design's §8 deferred section) flags two gaps behind that single-writer assumption:

- **A. Orphaned objects** — a failed upload mid-loop leaves the objects uploaded before it unreferenced in the `bloommcp-data` bucket forever (no manifest entry ever points at them, and `next_version_id` never reuses that `v<N>`).
- **B. No CAS** — `create_run` allocates `version_id` from one `read_manifest()` call; `commit` re-reads and appends without re-checking that id is still free. Two interleaved `create_run → commit` cycles can allocate and append the same `v<N>`.

Both are explicitly "currently safe" under bloom-mcp's one-container/single-process topology today (medium priority, `not-deploy-blocker`), but should stop being silently relied upon.

**Two notes on this document's history, both from PR review — corrected, not silently fixed.**

1. An earlier draft proposed re-checking for a version-id collision only immediately before `write_manifest`, after the upload loop, and "rebuilding the `VersionEntry` with a new id" on collision. That is unsound: `version_dir` (and therefore every object key `key_for()` produces, via `adir.key(f"{state.version_dir}/{rel}")`) is derived from `version_id` at `create_run` time, before any upload happens. Two writers that collide on `version_id` therefore also collide on `version_dir` and upload to the *same object keys* — with `upsert: true`, the second writer's upload silently overwrites the first's bytes before any check ever runs. Relabeling the manifest entry's `id` afterward does not fix already-clobbered storage; it ships two manifest entries that both point at inconsistent data. Decision B's two-phase check (finalize `version_id`/`version_dir`/every derived key *before* any byte moves) fixes this ordering bug.
2. A later draft — the two-phase check above, plus an explicit rejection of an in-process lock ("serialization is already effectively true today") — still had a live bug, caught independently by two review passes: `commit` is dispatched by FastMCP's Starlette server via a **thread pool**, so two `commit()` calls for the same `(experiment, tool_class)` can genuinely race *within one process*, not just interleave sequentially. Both can pass the pre-upload check before either writes the manifest (since neither has written yet, both see "free"), compute the identical deterministic `version_dir`, and upload to the same keys; the loser's pre-write check then correctly detects the collision, but its cleanup (Decision A) deletes keys the *winner's already-committed* manifest entry now depends on — actively worse than the bug this change exists to fix. Decision B now adds the lock this document previously rejected, for the reason the rejection assumed didn't hold.

## Goals / Non-Goals

- Goals:
  - Close gap A: a failed commit leaves no orphaned remote objects (best-effort delete of what was uploaded so far), and the delete actually succeeds against real Supabase (not just against the in-memory test fake).
  - Close gap B's observable failure mode for same-process concurrency — including genuinely concurrent `commit()` calls under FastMCP's thread-pool dispatch, not only sequentially-interleaved ones: two `create_run → commit` cycles for the same `(experiment, tool_class)` never produce a duplicate `v<N>` id or clobber each other's stored bytes, and a committed run's `id`/`version_dir`/`output_keys`/`output_sha256` are always mutually consistent with each other and with what was actually uploaded.
  - Keep the fix inside the adapter (`SupabaseResultStore`), with no change to the `ResultStore` port, `FakeResultStore`'s happy-path behavior, or the manifest schema.
- Non-Goals:
  - True storage-level atomic compare-and-swap, or safety for genuinely *simultaneous* multi-instance writers whose upload windows overlap byte-for-byte. See "CAS mechanism" below for why this is deferred rather than attempted now.
  - A prefix reaper / background job that sweeps orphaned objects independent of a specific failed commit.
  - Multi-instance / per-user-identity writes (already tracked as a separate, larger deferred item in the persistence design §8).

## Decisions

### A. Best-effort cleanup on commit failure, backed by a scoped DELETE grant

- Decision: track which output keys were successfully uploaded in `commit`'s loop; on any exception (upload or manifest write), attempt to delete those keys before re-raising `CommitFailedError`. A delete failure is caught, logged server-side (same redaction discipline as the existing error path — no Supabase URL/object path in the agent-facing message), and never replaces or masks the original error. The delete itself uses a shorter network timeout (`_CLEANUP_TIMEOUT_SECONDS = 5.0`, via `get_storage_client(timeout_seconds=...)` overriding storage3's 20s default) than a load-bearing call would — cleanup is best-effort, so a hung delete should give up and let the already-actionable `CommitFailedError` surface promptly rather than hold the caller for as long as a real upload might reasonably wait.
- New primitive: a bulk-delete helper added alongside the existing five storage helpers (`upload_file`, `download_file`, `write_json`, `read_json`, `list_prefix`) in `bloom_mcp.supabase_client`, delegating to `bloom_mcp.storage_backend.active_backend()` exactly like its siblings. `SupabaseStorageBackend` implements it via `storage3`'s existing `Bucket.remove(paths: list[str])` (already bulk-capable — no new dependency; confirmed present in the installed `storage3==2.31.0`). `LocalStorageBackend` implements it via `Path.unlink(missing_ok=True)` inside the existing root-containment guard, mirroring `download_file`'s key-resolution — best-effort across the whole batch (one bad key doesn't abort deleting the rest), matching the Supabase backend's single bulk call. The `StorageBackend` Protocol (`storage_backend.py:52-63`) gains this sixth method, and its docstring ("the five object-storage operations...") is updated to six. `delete_files` has direct `SupabaseStorageBackend`-level unit tests (`tests/test_storage_backend.py`) — on review this turned out to be the *only* `SupabaseStorageBackend` method with one; `upload_file`/`download_file`/`write_json`/`read_json`/`list_prefix` were previously exercised only indirectly (via the `fake_supabase_storage` fixture, which patches at the `supabase_client` free-function level, or via `LocalStorageBackend`'s extensive direct coverage) — out of scope to backfill here, but worth noting as the real, broader version of the gap a review pass flagged narrowly against `delete_files`.
- **Required companion migration — bloom_agent currently cannot delete anything.** `supabase/migrations/20260605000000_create_bloommcp_data_bucket.sql:26-29,61` deliberately grants `bloom_agent` only `INSERT, UPDATE` on `storage.objects` ("DELETE intentionally NOT granted... cleanup is admin-only"). Without a grant, `delete_files` 403s against real Supabase on every call; because the delete is best-effort (caught and logged), gap A would appear closed in unit tests against the fake boundary while never actually closing in a deployed environment. This change therefore adds `supabase/migrations/20260723000000_grant_bloommcp_agent_output_delete.sql`, granting `bloom_agent` DELETE scoped **more narrowly than the existing INSERT/UPDATE policies**: `bucket_id = 'bloommcp-data' AND name ~ '^bloommcp_output/'` — i.e. bloom_agent can delete objects under the output prefix only, never under `bloommcp_input/` (source CSVs), even though INSERT/UPDATE already cover the whole bucket. Shipped SQL:
  ```sql
  DROP POLICY IF EXISTS agent_delete_bloommcp_output ON storage.objects;
  CREATE POLICY agent_delete_bloommcp_output
    ON storage.objects
    FOR DELETE TO bloom_agent
    USING (bucket_id = 'bloommcp-data' AND name ~ '^bloommcp_output/');

  GRANT DELETE ON storage.objects TO bloom_agent;
  ```
  A first draft used `LIKE 'bloommcp_output/%'` instead of the `~` regex anchor — caught on review: an unescaped `_` in a `LIKE` pattern is itself a single-character wildcard, so that pattern would *also* match `bloommcp-output/`, `bloommcp.output/`, etc., silently widening the policy beyond the exact prefix this section and the migration's own comment claim. The regex anchor has no such footgun.
  **This reverses part of a deliberate prior security decision and needs explicit sign-off from whoever owns Supabase RLS review**, not just OpenSpec approval — see "Disclosed risk" below. **Verified live** (not just "the SQL doesn't error"): after applying via `make migrate-local` against the dev stack, `bloom_agent` successfully deleted a probe object under `bloommcp_output/`, and a delete attempt under `bloommcp_input/` returned an empty result with the object confirmed still present on read-back — RLS silently blocked it as designed.
- **Disclosed risk (deliberately chosen, not hidden).** RLS/GRANT is a *capability*, not a *call site*: once `bloom_agent` can delete under `bloommcp_output/`, that capability exists for the whole role, not just for the commit-failure cleanup path — a bug elsewhere in bloommcp (or a compromised process holding `BLOOM_AGENT_KEY`) could delete *any* object under that prefix, including already-committed, manifest-referenced runs, not only its own orphans. The original migration's "cleanup is admin-only" stance was a deliberate hedge against exactly this. This change accepts that widened blast radius as the cost of actually closing gap A in production (the alternative — logging orphans for an admin to clean up manually — was the other option surfaced to and rejected by the proposal owner in favor of a real fix). The prefix scoping (output-only, never input) is the mitigation actually shipped; a tighter scoping (e.g., only objects with no manifest reference, checked via a Postgres function) was considered and deferred as more moving parts than this pass justifies (see Open Questions).
- Alternatives considered: a standalone reaper that periodically lists object prefixes with no manifest entry and prunes them (admin-identity, no `bloom_agent` grant change needed). Rejected for this pass — the issue lists it as an *or*, not an *and*, and it's strictly more moving parts (a scheduled job, a bucket-wide listing) to solve the same failure the try/except already observes synchronously. Left as a future option if the DELETE-grant risk above is judged unacceptable on review.

### B. A per-key lock makes same-process commits mutually exclusive, plus a two-phase manifest guard as defense-in-depth

- **Primary decision: a per-`(output_root, experiment, tool_class)` lock, held for the entire `commit()` critical section.** Both adapters acquire a `KeyedLock` for that tuple (`result_store/_locks.py`) before touching the manifest, releasing only after the write (or the cleanup-and-raise on failure). This makes every `commit()` call for the same manifest fully serialized *within this process*: whichever call acquires the lock first runs its entire pre-upload-check → upload → pre-write-check → manifest-write sequence to completion before the other's `commit()` call even starts its pre-upload check. The second call's pre-upload check therefore always sees the first's fresh entry *before* uploading anything, and reallocates before any byte moves — the shared-key race described in the Context note above cannot occur.
  - **Why a shared `_locks.py` module, not two independent `dict[key, threading.Lock]` registries.** An earlier draft duplicated the registry (a plain dict + a meta-lock + a lazy-create-on-miss function) once per adapter, mirroring how `_MAX_ID_ATTEMPTS` is intentionally duplicated as a one-line constant. A whole mutual-exclusion primitive is a different risk category from a one-line constant — two independently hand-rolled copies of nontrivial concurrency code can silently drift in a way a duplicated `int` cannot (this is the same "no shared helper" risk already flagged for the two-phase collision check). `KeyedLock` lives alongside `_artifacts.py` (the existing precedent for adapter-shared-but-internal code) and is namespaced per adapter (`("supabase", ...)` / `("fake", ...)`) so the two never contend on each other's locks even given identical `(output_root, experiment, tool_class)` values.
  - **Bounded by construction, not just "cheap enough not to matter."** `KeyedLock`'s registry entry for a key exists only while at least one caller is inside its `with` block for that key (holding or waiting on the lock) — via a refcount incremented under a guard on entry and decremented (evicting at zero) on exit — never for the process's lifetime. Registry size is therefore bounded by the number of *currently in-flight, distinct* keys, not the number of experiments/tool_classes ever seen over a long-running process's life. Direct unit tests (`tests/result_store/test_locks.py`) cover: no entry survives past a sequential `with` block; 500 distinct keys used sequentially leave no residue; two real threads racing the same key serialize correctly; an entry is *not* evicted while a second, still-blocked caller has already registered against it (the property the bounding logic must not break); and an exception inside the block still releases and evicts.
- **Two-phase manifest check, kept as defense-in-depth (not the primary guarantee it was originally designed to be).** `commit` still performs two manifest reads:
  1. **Pre-upload check.** At the start of the critical section, re-read the manifest fresh. While the current `version_id` already has an entry in *that* read, re-allocate via `next_version_id` and recompute `version_dir` via `version_dir_name` — together — bounded (`_MAX_ID_ATTEMPTS = 3`), **re-reading the manifest on every attempt, not once before the loop** (an earlier draft cached one snapshot; `next_version_id`'s output can never re-collide with the snapshot it was computed from, so that version of the loop could only ever run 0 or 1 times through real contention — the bound was only reachable via an artificial test stub, not anything that could happen in production). Nothing has been uploaded yet, so exhausting the bound here is a cheap failure: raise before any upload.
  2. **Hash + upload** using the finalized `version_id`/`version_dir` for `key_for`, hashing, and the upload loop — exactly as today, against the (possibly reallocated) values. `RunHandle.version_id` is updated to match, so a caller reading it after `commit()` sees the id that was actually stored, not a stale provisional one.
  3. **Pre-write check.** Immediately before `write_manifest`, re-read the manifest once more. Under the lock, no *other* `commit()` call can be concurrently mid-flight for this same key, so this check's only realistic job now is catching a caller that bypasses the lock (a future direct manifest writer) — but it costs one cheap extra read and keeps the "id/version_dir/keys chosen together, never patched after the fact" invariant explicit and self-checking rather than implicit in the lock alone.
- **CAS mechanism — why a lock, not storage-api conditional writes.** The persistence design (§8) proposed a real conditional-upload primitive "via the Supabase Storage API's conditional-upload support." Inspecting the installed `storage3` SDK (`storage3/_sync/file_api.py`) shows `upload`/`update` only expose `x-upsert` (all-or-nothing overwrite, not a version/ETag precondition) — there is no typed conditional-write parameter, and confirming whether the self-hosted `storage-api` service backing it enforces arbitrary conditional headers (`If-Match` on a stored ETag/version) is out of scope for this repo (it is a separate deployed service, not vendored here) and unverified. An in-process lock needs no such unverified external primitive and fully closes the concurrency model this process actually has (a thread pool, not true multi-instance parallelism).
- **Residual limitation (documented precisely, not silently relied upon).** The lock closes same-process concurrency completely — including genuinely simultaneous `commit()` calls, not just sequentially-interleaved ones. It does **not** protect against a real multi-instance deployment, where a second *process* (on a different machine or a different container) holds no reference to this process's lock registry. That residual still needs either (a) a verified storage-api conditional-upload precondition, or (b) moving the `latest`/version-ledger pointer into a Postgres row updated inside a real transaction (true CAS). Both are larger changes than this medium-priority, non-blocking hardening pass justifies; the trigger for revisiting is unchanged from the design doc: bloom-mcp scaling past a single instance/process.
- Alternatives considered:
  - Checking only once, immediately before `write_manifest`, with no lock (the first draft) — rejected per the Context note above: it lets uploads land under a colliding path before any collision is ever detected.
  - The two-phase manifest check alone, with no lock (the second draft, and this document's own prior position) — rejected on review: it assumed two `commit()` calls for the same key never truly overlap in this process, which does not hold under FastMCP's thread-pool dispatch of sync tool handlers. Two calls can both pass the pre-upload check before either writes, defeating the check's ordering guarantee.
  - A cross-process lock (e.g., a Postgres advisory lock) instead of an in-process `threading.Lock` — not pursued: it would incidentally narrow the still-open multi-instance gap too, but adds a live DB round-trip to every commit and a new failure mode (advisory-lock timeout/deadlock) to reason about, for a residual case this change's scope explicitly defers. Worth reconsidering if/when the multi-instance trigger fires for real.

## Risks / Trade-offs

- The DELETE-grant widening (Decision A) is the largest trade-off in this change — see "Disclosed risk" above. It is a real, if narrowly-scoped, expansion of `bloom_agent`'s capability and should be reviewed as such, independent of the OpenSpec approval.
- Best-effort delete-on-failure adds a second failure surface (the delete call itself can fail, e.g. on the same network blip that failed the upload) — mitigated by catching and logging rather than propagating, so a doomed cleanup never hides the original, more actionable `CommitFailedError`.
- The two-read guard costs one extra `read_manifest()` call on every commit (pre-upload check) plus the pre-write check that already existed conceptually — two manifest reads per commit instead of one, even on the non-colliding path. Cheap (one JSON download each) relative to the upload(s) it brackets.
- The per-key lock serializes commits for the *same* `(experiment, tool_class)` but not across different ones, so unrelated tool calls are unaffected; a burst of retries all colliding on one key would queue behind the lock rather than fail fast, which is the intended trade-off (correctness over throughput for a rare, already-bounded-by-`_MAX_ID_ATTEMPTS` case).
- The residual limitation (documented above) means this change should not be read as "solves multi-writer safety" for real multi-instance concurrency — it fully closes same-process concurrency (both sequential interleaving and genuinely simultaneous thread-pool races; id/version_dir/keys can no longer disagree with each other, and a winner's committed bytes can no longer be deleted by a loser's cleanup), and still needs the design's already-deferred bigger fix before bloom-mcp actually runs multiple *processes*.

## Migration Plan

This change includes one real migration (Decision A's DELETE grant) alongside purely additive adapter code. The migration is additive/idempotent (`DROP POLICY IF EXISTS` + `CREATE POLICY`, matching `20260605000000`'s pattern) and reversible: `DROP POLICY agent_delete_bloommcp_output; REVOKE DELETE ON storage.objects FROM bloom_agent;` fully reverts to today's admin-only-cleanup posture with no data loss, if review determines the widened capability isn't acceptable. No manifest/data-shape migration — existing v2/v3 manifests are read and written unchanged when no collision/failure occurs. Applied and behaviorally verified against the running dev stack (`make migrate-local`, then a live delete against both prefixes — see task 0.2). Roll out behind normal PR review (including explicit RLS sign-off per the Disclosed Risk note) — no feature flag, since the changed paths (failure and collision) are not on the happy path any existing golden/smoke test exercises today.

## Open Questions

- **Needs explicit RLS/migration-owner sign-off** (separate from OpenSpec approval): is the output-prefix-scoped DELETE grant an acceptable trade-off, or should gap A instead ship as detect-and-log-for-admin-cleanup with no grant change? The proposal owner's initial call is to add the scoped grant, and its live behavior is now verified (see Decision A) — this still needs a human sign-off on the trade-off itself, not just proof the SQL works as written.
- Should the bounded retry count (proposed: 3, used identically at the pre-upload and effectively-once at the pre-write check) be a module constant or configurable? Leaning toward a private module constant — no caller has surfaced a need to tune it.
- Should the DELETE grant be scoped even tighter than "any object under `bloommcp_output/`" — e.g. only objects with no manifest reference, enforced via a Postgres function/trigger rather than a static prefix policy? Considered and deferred as more moving parts than this pass justifies; worth a fast-follow if the disclosed blast radius above is judged too wide.
- If a future spike confirms `storage-api` does support a conditional-write precondition, that would let gap B's residual multi-instance window close for real without moving to Postgres — worth a fast-follow spike, not blocking this change.
