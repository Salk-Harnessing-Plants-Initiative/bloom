## Context

`SupabaseResultStore.commit` (`bloommcp/src/bloom_mcp/result_store/supabase_store.py:96`) uploads each staged output, builds the v3 `VersionEntry`, then writes the manifest last. This ordering is already correct for the single-writer case — see the existing spec scenario "Commit failure cleans up and does not corrupt the manifest" — but issue #324 (deferred out of the #323 review, referenced from the persistence design's §8 deferred section) flags two gaps behind that single-writer assumption:

- **A. Orphaned objects** — a failed upload mid-loop leaves the objects uploaded before it unreferenced in the `bloommcp-data` bucket forever (no manifest entry ever points at them, and `next_version_id` never reuses that `v<N>`).
- **B. No CAS** — `create_run` allocates `version_id` from one `read_manifest()` call; `commit` re-reads and appends without re-checking that id is still free. Two interleaved `create_run → commit` cycles can allocate and append the same `v<N>`.

Both are explicitly "currently safe" under bloom-mcp's one-container/single-process topology today (medium priority, `not-deploy-blocker`), but should stop being silently relied upon.

**A note on this document's Decision B.** An earlier draft of this design proposed re-checking for a version-id collision only immediately before `write_manifest`, after the upload loop, and "rebuilding the `VersionEntry` with a new id" on collision. That is unsound: `version_dir` (and therefore every object key `key_for()` produces, via `adir.key(f"{state.version_dir}/{rel}")`) is derived from `version_id` at `create_run` time, before any upload happens. Two writers that collide on `version_id` therefore also collide on `version_dir` and upload to the *same object keys* — with `upsert: true`, the second writer's upload silently overwrites the first's bytes before any check ever runs. Relabeling the manifest entry's `id` afterward does not fix already-clobbered storage; it ships two manifest entries that both point at inconsistent data. Decision B below fixes this by finalizing `version_id`, `version_dir`, and every derived key *before* any byte moves.

## Goals / Non-Goals

- Goals:
  - Close gap A: a failed commit leaves no orphaned remote objects (best-effort delete of what was uploaded so far), and the delete actually succeeds against real Supabase (not just against the in-memory test fake).
  - Close gap B's observable failure mode for the realistic single-process case — two `create_run → commit` cycles whose commits run sequentially (one fully completes, including its manifest write, before the next starts uploading) never produce a duplicate `v<N>` id, and a committed run's `id`/`version_dir`/`output_keys`/`output_sha256` are always mutually consistent with each other and with what was actually uploaded.
  - Keep the fix inside the adapter (`SupabaseResultStore`), with no change to the `ResultStore` port, `FakeResultStore`'s happy-path behavior, or the manifest schema.
- Non-Goals:
  - True storage-level atomic compare-and-swap, or safety for genuinely *simultaneous* multi-instance writers whose upload windows overlap byte-for-byte. See "CAS mechanism" below for why this is deferred rather than attempted now.
  - A prefix reaper / background job that sweeps orphaned objects independent of a specific failed commit.
  - Multi-instance / per-user-identity writes (already tracked as a separate, larger deferred item in the persistence design §8).

## Decisions

### A. Best-effort cleanup on commit failure, backed by a scoped DELETE grant

- Decision: track which output keys were successfully uploaded in `commit`'s loop; on any exception (upload or manifest write), attempt to delete those keys before re-raising `CommitFailedError`. A delete failure is caught, logged server-side (same redaction discipline as the existing error path — no Supabase URL/object path in the agent-facing message), and never replaces or masks the original error.
- New primitive: a bulk-delete helper added alongside the existing five storage helpers (`upload_file`, `download_file`, `write_json`, `read_json`, `list_prefix`) in `bloom_mcp.supabase_client`, delegating to `bloom_mcp.storage_backend.active_backend()` exactly like its siblings. `SupabaseStorageBackend` implements it via `storage3`'s existing `Bucket.remove(paths: list[str])` (already bulk-capable — no new dependency; confirmed present in the installed `storage3==2.31.0`). `LocalStorageBackend` implements it via `Path.unlink(missing_ok=True)` inside the existing root-containment guard, mirroring `download_file`'s key-resolution. The `StorageBackend` Protocol (`storage_backend.py:52-63`) gains this sixth method, and its docstring ("the five object-storage operations...") is updated to six.
- **Required companion migration — bloom_agent currently cannot delete anything.** `supabase/migrations/20260605000000_create_bloommcp_data_bucket.sql:26-29,61` deliberately grants `bloom_agent` only `INSERT, UPDATE` on `storage.objects` ("DELETE intentionally NOT granted... cleanup is admin-only"). Without a grant, `delete_files` 403s against real Supabase on every call; because the delete is best-effort (caught and logged), gap A would appear closed in unit tests against the fake boundary while never actually closing in a deployed environment. This change therefore adds a new migration granting `bloom_agent` DELETE, scoped **more narrowly than the existing INSERT/UPDATE policies**: `bucket_id = 'bloommcp-data' AND name LIKE 'bloommcp_output/%'` — i.e. bloom_agent can delete objects under the output prefix only, never under `bloommcp_input/` (source CSVs), even though INSERT/UPDATE already cover the whole bucket. Sketch (final SQL lands in `supabase/migrations/` at implementation time, following the same idempotent `DROP POLICY IF EXISTS` pattern as `20260605000000`):
  ```sql
  DROP POLICY IF EXISTS agent_delete_bloommcp_output ON storage.objects;
  CREATE POLICY agent_delete_bloommcp_output
    ON storage.objects
    FOR DELETE TO bloom_agent
    USING (bucket_id = 'bloommcp-data' AND name LIKE 'bloommcp_output/%');

  GRANT DELETE ON storage.objects TO bloom_agent;
  ```
  **This reverses part of a deliberate prior security decision and needs explicit sign-off from whoever owns Supabase RLS review**, not just OpenSpec approval — see "Disclosed risk" below.
- **Disclosed risk (deliberately chosen, not hidden).** RLS/GRANT is a *capability*, not a *call site*: once `bloom_agent` can delete under `bloommcp_output/`, that capability exists for the whole role, not just for the commit-failure cleanup path — a bug elsewhere in bloommcp (or a compromised process holding `BLOOM_AGENT_KEY`) could delete *any* object under that prefix, including already-committed, manifest-referenced runs, not only its own orphans. The original migration's "cleanup is admin-only" stance was a deliberate hedge against exactly this. This change accepts that widened blast radius as the cost of actually closing gap A in production (the alternative — logging orphans for an admin to clean up manually — was the other option surfaced to and rejected by the proposal owner in favor of a real fix). The prefix scoping (output-only, never input) is the mitigation actually shipped; a tighter scoping (e.g., only objects with no manifest reference, checked via a Postgres function) was considered and deferred as more moving parts than this pass justifies (see Open Questions).
- Alternatives considered: a standalone reaper that periodically lists object prefixes with no manifest entry and prunes them (admin-identity, no `bloom_agent` grant change needed). Rejected for this pass — the issue lists it as an *or*, not an *and*, and it's strictly more moving parts (a scheduled job, a bucket-wide listing) to solve the same failure the try/except already observes synchronously. Left as a future option if the DELETE-grant risk above is judged unacceptable on review.

### B. Duplicate-id guard: finalize id/version_dir/keys before any upload

- Decision: `commit` performs two manifest reads, one before any upload and one right before the write, so `version_id`/`version_dir`/every derived key are always chosen *together* and never rewritten independently after bytes have moved:
  1. **Pre-upload check.** At the start of `commit`, re-read the manifest fresh. While the current `version_id` already has an entry in that fresh read, re-allocate via `next_version_id` and recompute `version_dir` via `version_dir_name` — together — bounded (e.g. 3 attempts). Nothing has been uploaded yet, so exhausting the bound here is a cheap failure: raise `CommitFailedError` with no cleanup needed.
  2. **Hash + upload** using the finalized `version_id`/`version_dir` for `key_for`, hashing, and the upload loop — exactly as today, just against the (possibly reallocated) values.
  3. **Pre-write check.** Immediately before `write_manifest`, re-read the manifest one more time. If the finalized `version_id` *now* has an entry (a third writer's commit landed with that same id during this commit's upload window — rare, since step 1 already excluded every id visible before uploading started), treat it exactly like any other commit failure: best-effort `delete_files` what this attempt just uploaded (reusing Decision A's cleanup path) and raise `CommitFailedError`. The caller's existing retry-the-handle contract (already established by `test_commit_failure_is_retryable_and_does_not_leak`) then re-enters `commit()`, which redoes step 1 against a now-current manifest and is guaranteed a genuinely free id/path.
  - This guarantees a committed entry's `id`, `version_dir`, and `output_keys`/`output_sha256` are always mutually consistent with each other and with the bytes actually stored — never independently patched after the fact.
- **CAS mechanism — why the adapter-side guard, not storage-api conditional writes.** The persistence design (§8) proposed a real conditional-upload primitive "via the Supabase Storage API's conditional-upload support." Inspecting the installed `storage3` SDK (`storage3/_sync/file_api.py`) shows `upload`/`update` only expose `x-upsert` (all-or-nothing overwrite, not a version/ETag precondition) — there is no typed conditional-write parameter, and confirming whether the self-hosted `storage-api` service backing it enforces arbitrary conditional headers (`If-Match` on a stored ETag/version) is out of scope for this repo (it is a separate deployed service, not vendored here) and unverified. Rather than build on an unverified external primitive, this change ships the adapter-side guard above, which is fully implementable and testable in-process today.
- **Residual limitation (documented precisely, not silently relied upon).** The guard closes the case that actually happens under bloom-mcp's current single-process topology: two `create_run → commit` cycles whose commits execute *sequentially* — the realistic shape of "interleaved" when there is exactly one process handling one request at a time. It does **not** protect against a genuinely simultaneous multi-instance write whose upload window overlaps another writer's byte-for-byte between this commit's step 1 and step 3 landing at the exact same moment as a second collision — that residual needs either (a) a verified storage-api conditional-upload precondition, or (b) moving the `latest`/version-ledger pointer into a Postgres row updated inside a real transaction (true CAS). Both are larger changes than this medium-priority, non-blocking hardening pass justifies; the trigger for revisiting is unchanged from the design doc: bloom-mcp scaling past a single instance/process.
- Alternatives considered:
  - Checking only once, immediately before `write_manifest` (the earlier, unsound draft) — rejected per the Context note above: it lets uploads land under a colliding path before the collision is ever detected.
  - A `flock`-style in-process lock around `create_run`/`commit` — rejected, since it only serializes writers *within one process* (already effectively true today) and does nothing for the actual multi-instance scenario the issue is triggered by.

## Risks / Trade-offs

- The DELETE-grant widening (Decision A) is the largest trade-off in this change — see "Disclosed risk" above. It is a real, if narrowly-scoped, expansion of `bloom_agent`'s capability and should be reviewed as such, independent of the OpenSpec approval.
- Best-effort delete-on-failure adds a second failure surface (the delete call itself can fail, e.g. on the same network blip that failed the upload) — mitigated by catching and logging rather than propagating, so a doomed cleanup never hides the original, more actionable `CommitFailedError`.
- The two-read guard costs one extra `read_manifest()` call on every commit (pre-upload check) plus the pre-write check that already existed conceptually — two manifest reads per commit instead of one, even on the non-colliding path. Cheap (one JSON download each) relative to the upload(s) it brackets.
- The residual limitation (documented above) means this change should not be read as "solves multi-writer safety" for real multi-instance concurrency — it closes the sequential-interleaving case completely (id/version_dir/keys can no longer disagree with each other), and still needs the design's already-deferred bigger fix before bloom-mcp actually runs multiple *simultaneous* writers.

## Migration Plan

This change includes one real migration (Decision A's DELETE grant) alongside purely additive adapter code. The migration is additive/idempotent (`DROP POLICY IF EXISTS` + `CREATE POLICY`, matching `20260605000000`'s pattern) and reversible: `DROP POLICY agent_delete_bloommcp_output; REVOKE DELETE ON storage.objects FROM bloom_agent;` fully reverts to today's admin-only-cleanup posture with no data loss, if review determines the widened capability isn't acceptable. No manifest/data-shape migration — existing v2/v3 manifests are read and written unchanged when no collision/failure occurs. Roll out behind normal PR review (including explicit RLS sign-off per the Disclosed Risk note) — no feature flag, since the changed paths (failure and collision) are not on the happy path any existing golden/smoke test exercises today.

## Open Questions

- **Needs explicit RLS/migration-owner sign-off** (separate from OpenSpec approval): is the output-prefix-scoped DELETE grant an acceptable trade-off, or should gap A instead ship as detect-and-log-for-admin-cleanup with no grant change? The proposal owner's initial call is to add the scoped grant; flagging here so the sign-off is visible before implementation starts.
- Should the bounded retry count (proposed: 3, used identically at the pre-upload and effectively-once at the pre-write check) be a module constant or configurable? Leaning toward a private module constant — no caller has surfaced a need to tune it.
- Should the DELETE grant be scoped even tighter than "any object under `bloommcp_output/`" — e.g. only objects with no manifest reference, enforced via a Postgres function/trigger rather than a static prefix policy? Considered and deferred as more moving parts than this pass justifies; worth a fast-follow if the disclosed blast radius above is judged too wide.
- If a future spike confirms `storage-api` does support a conditional-write precondition, that would let gap B's residual multi-instance window close for real without moving to Postgres — worth a fast-follow spike, not blocking this change.
