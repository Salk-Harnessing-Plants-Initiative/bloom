## Why

Every real A4 sleap-roots pipeline run to date (most recently `sleap-roots-pipeline` PR
[#33](https://github.com/talmolab/sleap-roots-pipeline/pull/33), 2026-07-30) has been triggered by a
human manually running `argo submit`. There is no way for a user to click "Run" in Bloom and have
that turn into cluster execution, and no durable record of what was requested or what happened —
[bloom #11](https://github.com/Salk-Harnessing-Plants-Initiative/bloom/issues/11) and [bloom
#404](https://github.com/Salk-Harnessing-Plants-Initiative/bloom/issues/404) track this gap.

This proposal implements **Phase 1 of 3** (phasing + status-mechanism + dedup-scope decisions in
`design.md`): the migration for `cyl_pipeline_runs`/`cyl_pipeline_run_scans` (+ RLS + Realtime + a
`bloom_workflows`-scoped pgmq enqueue path) and `POST /workflows/pipeline` in `services/workflows/`,
covering enumerate → dedup preview → insert run/scan rows → chunk into batches → enqueue every
enumerated scan. Phase 1 has zero Argo/Kubernetes interaction — see `design.md` for the full
rationale (the K8s ServiceAccount Phase 2/3 need is still unapplied) and for why the dedup mechanism
is preview-only rather than a hard skip.

## What Changes

- **New tables** `cyl_pipeline_runs` (one row per trigger request; the Realtime subscription target)
  and `cyl_pipeline_run_scans` (one row per scan in a run), using this repo's universal
  `bigint GENERATED BY DEFAULT AS IDENTITY` PK convention (not the `uuid` PK sketched in the
  now-superseded original design draft) — see `design.md` §Data model.
- **New Supabase migration** granting `bloom_workflows` exactly what Phase 1 needs: column-scoped
  `SELECT`/`INSERT` on the two new tables (no `UPDATE` — deferred to Phase 2, see `design.md`), a new
  column-scoped `SELECT (scan_id, source_id)` on `cyl_scan_traits` and `SELECT (id, metadata)` on
  `cyl_trait_sources` (for the dedup preview's all-sources existence-check join — checks every one of
  a scan's sources, not only its most recent one), and `EXECUTE` on a new pgmq enqueue wrapper
  function (granted only to `bloom_workflows`, distinct from the write-back RPC's broader 4-role
  grant list). Standard 4-role RLS (`bloom_admin` ALL, `bloom_agent`/`bloom_user` read-only) plus
  Realtime publication for both tables. Adds `sleap-roots-contracts` as a new dependency of
  `services/workflows` (for `compute_param_hash`), regenerating its `uv.lock` — see tasks.md.
- **New pgmq queue** `cyl_pipeline_dispatch` with a `SECURITY DEFINER` `enqueue_cyl_pipeline_batch(...)`
  wrapper function — modeled on bloom PR [#469](https://github.com/Salk-Harnessing-Plants-Initiative/bloom/pull/469)'s
  pattern **as a reference only, not a code dependency** (that PR is still open/unmerged). Phase 1
  implements only the `enqueue` side; `claim`/`complete`/`fail` are Phase 2's job.
- **New route** `POST /workflows/pipeline` (external contract — the path Bloom web calls) registered
  internally as `@app.post("/pipeline")` in `services/workflows/main.py`, **not**
  `@app.post("/workflows/pipeline")` — Caddy's `handle_path /workflows/*` block already strips the
  `/workflows` prefix before proxying to this service (confirmed against `caddy/Caddyfile` and every
  existing route in `main.py`, none of which carry that prefix internally). Follows the service's
  thin-route/fat-module pattern: `Depends(require_supabase_user)` for auth, `enforce_rate_limit(user_id)`
  called explicitly, all logic in a new `pipeline.py` module. Validates
  `{target_level, target_id | scan_ids, params}`, enumerates scans via `cyl_scans_extended`, computes
  an **informational** dedup preview (`reused_count`), writes the run + per-scan rows (every scan
  starts `status = 'queued'` — see dedup decision below), chunks into `BATCH_SIZE` groups, and
  enqueues every batch. Returns `{pipeline_run_id, scan_count, reused_count}`.
- **Dedup is a preview, not a hard skip.** The Bloom-side pre-check computes `compute_param_hash`
  **once**, over the request's own resolved params, and checks whether that hash matches the
  already-stored `metadata->'params'->>'param_hash'` on **any** of a scan's recorded
  `cyl_trait_sources` rows (via the `cyl_scan_traits.scan_id → source_id → cyl_trait_sources` join) —
  not just its most recent one, and not by re-hashing the stored `metadata` envelope itself (that
  envelope also carries code shas/container digests/workflow ids that differ every run, so hashing it
  whole would almost never match — the comparison is against the pre-computed `param_hash` field
  already embedded in it). This purely populates `reused_count` for the response/UI preview.
  **Every enumerated scan is enqueued regardless** — the actual GPU-avoidance decision is made
  cluster-side (the predict loop's existing per-scan skip, which knows real current model versions
  and code shas, unlike Bloom). This reverses an earlier plan to hard-skip on a params-only match —
  see `design.md`'s "Decision: dedup preview is informational only" for why a hard skip would have
  silently and permanently suppressed recompute after a model-version bump with unchanged params, and
  why checking only the latest source (rather than all of them) would under-count matches.
- **Tests**: hand-rolled-fake unit tests for `pipeline.py` (matching `test_video.py`'s convention),
  plus a new `tests/integration/test_cyl_pipeline_dispatch.py` (live-compose-DB, rollback-wrapped,
  matching the pattern in the already-available `tests/integration/test_cyl_scan_intermediates.py` —
  **not** the unmerged PR #469's `test_cyl_video_queue.py`, which doesn't exist in this checkout)
  covering: run/scan row creation and defaults, RLS/grant boundaries (including a negative test
  proving `bloom_workflows` does **not** yet have `UPDATE`), Realtime publication idempotency, the
  new enqueue wrapper's negative-authorization guard, and an apply-then-rollback-then-verify test that
  actually exercises the companion rollback script rather than leaving it unexecuted.

**Out of scope for this proposal** (tracked as later phases of the same bloom #11/#404 work):
- Phase 2 — the pgmq dispatch worker (`claim` → `argo submit` subprocess → `complete`/`fail`), wiring
  an Argo `onExit` handler to push status back to Bloom, the `bloom_workflows` `UPDATE` grant those
  need, and closing the concurrent-duplicate-enqueue race (two overlapping requests can both enqueue
  the same scan today — cheap while Phase 1 never reaches Argo, see `design.md` Risks).
- Phase 3 — `GET /workflows/runs/{id}` (a plain DB read) and the stale-run reconciliation sweep.
- A full model-version-aware dedup pre-check (would need a cheap "current production models" signal —
  e.g. a wandb registry lookup — that isn't confirmed available to `services/workflows` today; a
  larger, separate effort if pursued).
- The Bloom web UI trigger/status panel (design doc §10).

## Impact

- **Affected specs**: new capabilities `cyl-pipeline-runs` (data model: tables, RLS, Realtime, pgmq
  enqueue) and `cyl-pipeline-trigger` (the `POST /workflows/pipeline` route's behavior).
- **Affected code**:
  - `supabase/migrations/<timestamp>_create_cyl_pipeline_runs.sql` (new — timestamp TBD at
    implementation time; re-verify against `origin/staging`'s actual latest migration, do not assume
    `20260730120000` is still after it)
  - `supabase/rollbacks/<timestamp>_create_cyl_pipeline_runs_rollback.sql` (new)
  - `services/workflows/main.py` (new route registered at `/pipeline`), `services/workflows/pipeline.py`
    (new module)
  - `services/workflows/pyproject.toml` (new `sleap-roots-contracts>=0.1.0a5` dependency, for
    `compute_param_hash`) and `services/workflows/uv.lock` (regenerated — CI's `--frozen` lock checks
    will fail otherwise)
  - `services/workflows/tests/test_pipeline.py` (new, unit)
  - `tests/integration/test_cyl_pipeline_dispatch.py` (new, integration)
  - `packages/bloom-fs/src/types/database.types.ts`, `packages/bloom-js/src/types/database.types.ts`,
    `packages/bloom-nextjs-auth/src/lib/database.types.ts`, `web/lib/database.types.ts` (regenerated
    via `make gen-types`)
  - `_WIKI/SUPABASE/README.md` (new grants + a new pgmq-queues subsection — none exists yet)
  - `services/workflows/README.md` (endpoint inventory, the "app user needs only" grant list, and the
    "on-demand vs queued generation" section — this is the service's first pgmq path, not a second
    instance of the existing `video_jobs` pattern)
- **Related, not modified here**: bloom PR #469 (unmerged pgmq video-queue precedent — referenced, not
  depended on), `talmolab/sleap-roots-pipeline#17` (credential — already resolved for staging,
  unrelated to this proposal), the K8s ServiceAccount (blocks Phase 2/3, not this phase).
