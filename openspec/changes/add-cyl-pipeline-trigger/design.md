## Context

bloom #11 ("Pipeline Trigger — Manual Execution via Bloom") and bloom #404 (`bloom_workflows` grants
for the trigger route) describe the full request-driven pipeline trigger: `POST /workflows/pipeline`
→ enumerate → dedup → insert tracking rows → chunk into batches → submit one Argo workflow per batch
→ poll for status. The canonical architecture is
[sleap-roots-pipeline's 2026-07-06 A4 design doc](https://github.com/talmolab/sleap-roots-pipeline/blob/main/docs/superpowers/specs/2026-07-06-a4-request-driven-pipeline-design.md)
(§3 end-to-end flow, §5 data model, §6 execution topology, §7 dedup, §9 concurrency, §10 UI).

This is a genuinely large feature spanning a Postgres migration, a new pgmq queue, and a new FastAPI
route. Building it as one change would mean the whole thing stays blocked on an external dependency
that has nothing to do with most of the code: the K8s ServiceAccount
(`bloom-pipeline-serviceaccount.yaml`, drafted 2026-07-22, sent to the cluster admin) that Bloom's own
backend needs to submit Argo Workflows is **still not applied/tested**, per the
`sleap-roots-pipeline` roadmap's own credential row (confirmed live 2026-07-30). Phasing at the exact
boundary where Argo/Kubernetes access becomes necessary lets the unblocked two-thirds of the work
(schema + enumerate/dedup-preview/enqueue) ship and be reviewed now.

## Goals / Non-Goals

**Goals (this phase):**
- A durable, queryable record of every pipeline-trigger request and its per-scan resolution.
- Correct enumeration for all four `target_level` values (`scan`/`wave`/`experiment`/`scan_ids`),
  reusing `cyl_scans_extended` — no new view.
- An accurate `reused_count` **preview** for the response/future UI, without ever silently suppressing
  real recomputation (see the dedup decision below — this took a wrong turn during review and was
  corrected before implementation).
- Correct batching: every enumerated scan is chunked into `BATCH_SIZE`-sized groups and each batch is
  durably enqueued (survives a `workflows`-service restart between insert and the eventual Argo
  submit).
- Zero new runtime dependency on Argo, Kubernetes, or the still-unapplied ServiceAccount.

**Non-goals (deferred to Phase 2/3, tracked here for continuity, not implemented in this change):**
- Actually submitting anything to Argo (Phase 2).
- Any hard skip / hard hold-back on enqueue based on Bloom-side dedup — see decision below.
- Updating `cyl_pipeline_runs.status` past `queued`, and the `bloom_workflows` `UPDATE` grant that
  requires (Phase 2 — see "Decision: defer the UPDATE grant to Phase 2").
- Closing the concurrent-duplicate-enqueue race (see Risks below) — acceptable while Phase 1 has zero
  Argo/GPU cost.
- `GET /workflows/runs/{id}` (Phase 3 — becomes a plain DB read per the status-mechanism decision).
- The Bloom web UI trigger/status panel (design doc §10).

## Decisions

### Decision: `bigint GENERATED BY DEFAULT AS IDENTITY` PKs, not `uuid`

The design doc's own §5 table sketch and the older, superseded draft
(`docs/issues/issue-2-pipeline-trigger.md`, kept in bloom #11 only as collapsed history) both use
`uuid` PKs. Every other `cyl_*` table in this repo (`cyl_waves`, `cyl_trait_sources`,
`cyl_scan_intermediates`, etc.) uses `bigint GENERATED BY DEFAULT AS IDENTITY`. Consistency with the
repo's actual, universal convention wins over the design doc's sketch.

- Alternatives considered: `uuid` (matches the design doc literally) — rejected because it breaks the
  repo's own convention for no benefit here.

### Decision: the internal FastAPI route is `/pipeline`, not `/workflows/pipeline`

`caddy/Caddyfile`'s `handle_path /workflows/*` block strips the `/workflows` prefix before proxying
to `services/workflows`, and every existing route in `main.py` (`/health`,
`/cyl/experiments/{experiment_id}/scans/{scan_id}/video`) is registered without that prefix — this was
verified directly against the actual Caddyfile and `main.py`, not assumed. Registering
`@app.post("/workflows/pipeline")` would require Bloom web to call
`bloom.salk.edu/workflows/workflows/pipeline` externally, breaking the established pattern. The
**external** contract (what bloom #11 and the A4 design doc call `POST /workflows/pipeline`, what a
user/browser actually calls) is unaffected — only the internal `@app.post(...)` path changes to
`/pipeline`.

### Decision: pgmq queue built independently of unmerged bloom PR #469

bloom PR #469 (`feat/workflows-cyl-video-queue`, migration `20260721000000_cyl_video_queue.sql`) is
the only precedent in this repo for a `bloom_workflows`-scoped pgmq queue with `SECURITY DEFINER`
wrapper functions. It is **not merged** (`gh pr view 469` → `state: OPEN`, `mergedAt: null`, confirmed
2026-07-30). Rather than block this proposal on someone else's open review, this migration writes its
own `cyl_pipeline_dispatch` queue and its own wrapper function(s), using #469's pattern as a reference
for the parts that are genuinely hard-won conventions worth repeating exactly:
- Explicit `REVOKE EXECUTE ... FROM PUBLIC, anon, authenticated` (not just `PUBLIC`) on every wrapper
  function, plus a negative integration test (`has_function_privilege`) proving it — #469's commit
  `0b91cd0` discovered that Supabase's default privileges grant new public-schema functions `EXECUTE`
  to `anon`/`authenticated` directly, so revoking only from `PUBLIC` is insufficient.
- `pgmq.create('cyl_pipeline_dispatch')` guarded by an existence check, since `pgmq` is already enabled
  repo-wide (`20260715000000_enable_pgmq.sql`).

Risk accepted: if #469 merges with a meaningfully different pattern before this proposal's Phase 2
lands, Phase 2's design should re-diff against whatever #469 actually shipped rather than assume this
proposal's reference-copy is still representative.

- Alternatives considered: (a) wait for #469 to merge — rejected, ties this proposal's timeline to an
  unrelated PR's review process; (b) ask Benfica to coordinate first — the user chose to proceed
  independently instead.

### Decision: defer the `bloom_workflows` `UPDATE` grant to Phase 2

An earlier draft of this proposal granted `bloom_workflows` `UPDATE` on both new tables in Phase 1,
reasoning that Phase 2's push-based status writer would need it and "shouldn't need a follow-up
migration." **This was reversed on review**: it directly contradicts this repo's own stated,
consistently-followed convention (`20260716000000_create_workflows_role.sql`'s header: *"expand
explicitly as new endpoints need it"* — every other `bloom_workflows` grant in this repo, including
`20260717000000_workflows_read_videos_policy.sql`'s own follow-up grant, was added on-demand, not
pre-emptively). Phase 1's route only ever `INSERT`s; it has no code path that updates a row. Granting
`UPDATE` now would widen an already-shared role's (`bloom_workflows` also backs the on-demand video
route and A4's cluster credential) blast radius for a capability nothing in this phase uses. Phase 2
adds its own small grant migration when the push/reconciliation write path is actually built — this
repo already has cheap precedent for that exact shape of follow-up (`20260717000000`,
`20260720000000_grant_bloom_workflows_writeback_rpc.sql`), so a second migration is not meaningful
friction.

### Decision: dedup preview is informational only — every enumerated scan is always enqueued

**This corrects a real bug found during review**, not just a design preference. The original plan (a
Bloom-side pre-check that hard-skips enqueue for scans whose latest recorded `cyl_trait_sources`
`params` match the request) was reasoned to be "safe" because "the cluster-side skip will still catch
a model-version bump" — but that reasoning is false as actually specified: a scan marked skipped is
**never enqueued**, so the cluster-side per-scan skip (which does know current model versions and code
shas, and would correctly force a recompute) never runs on it at all. A model-version bump with
unchanged params would silently and **permanently** suppress recomputation — exactly the opposite of
the explicit product requirement that users be able to rerun a scan with different params (or after a
model update) and get updated results.

The root cause: Bloom cannot compute the real `idempotency_key` (which hashes `params` + model
versions + code shas) before submission, because model versions/code shas are resolved cluster-side,
at predict time, via a wandb registry lookup — `services/workflows` has no such dependency today and
this proposal deliberately does not add one (see Non-goals). Bloom can only cheaply know `params`. The
canonical design doc's own §7 anticipated exactly this gap and gives explicit fallback guidance:
*"if that current-models signal is cheaply available... do the full short-circuit; otherwise rely on
the cluster-side skip above and skip the Bloom-side pre-check for v1."*

**Resolution:** the dedup pre-check computes `reused_count` (via the all-sources existence check
described below) **purely for the response/future UI preview** — matching the design doc's own §10 UI sketch,
"38/40 already have results for these params — 2 will run," which is itself framed as a *preview*, not
a backend gate. It never changes a scan's initial `status` (always `queued`) and never excludes a scan
from batching/enqueue. The actual, correct GPU-avoidance decision is made cluster-side by the
already-existing predict-loop skip-if-done check, which does know current models. Consequence: bloom
#11's literal "0 GPU pods scheduled" acceptance-criterion wording is not met by this phase alone (a pod
is still scheduled and loads models, then skips fast) — achieving true zero-pod avoidance would require
giving Bloom the current-models signal, which is explicitly out of scope (see proposal.md).

**Source join, spelled out — and a second bug caught during review.** There is no `scan_id` column on
`cyl_trait_sources` directly. The join is
`cyl_scan_traits.scan_id → cyl_scan_traits.source_id → cyl_trait_sources.id`. An earlier draft of
this section said to use the `cyl-trait-read` capability's `is_latest` = `max(source_id)` rule (its
single source of truth for "which source should a read display by default") to pick *the* source to
compare against. **This is wrong for dedup**: `is_latest` answers a display question, not an "has
this exact param combination ever been computed" question. A scan computed at `age=14` (an earlier
source) and later at `age=21` (now the latest source) would, under an `is_latest`-based check,
report "not reused" for a fresh `age=14` request — even though `source_id`'s `age=14` row is right
there, just not the newest one. The corrected check is an **existence check across all of a scan's
sources**, not a filter-to-max-then-compare.

**Comparison mechanism, spelled out — and a third bug caught during review.** An earlier draft of
this section described the comparison as `compute_param_hash(source.metadata) = :request_hash` —
i.e., re-hashing each stored source's entire `metadata` column and comparing to the request's hash.
**This is wrong**: `cyl_trait_sources.metadata` is the whole `Provenance` envelope (`contract_version`,
`scan_key`, `inputs`, `predict_models`, `predict_container_digest`, `*_code_sha`,
`argo_workflow_uid`, etc.) — hashing it whole would almost never match across two runs even with
identical params, since code shas/container digests/workflow ids differ every run. That would make
`reused_count` sit at (or near) zero always, defeating the preview's purpose. The correct comparison:
`compute_param_hash` (from the pinned `sleap-roots-contracts` package, a new dependency of
`services/workflows` — see proposal.md's Impact) is computed **once**, over the *request's own*
resolved params, producing a hash string. Each candidate source's *already-stored*
`metadata->'params'->>'param_hash'` (the producer already embeds this at write-back time, per the
contract's `ResolvedParams` model — nothing needs to be re-derived from the stored side) is compared
to that one request-side hash as a plain string equality. This is entirely a Python-side comparison
in `pipeline.py` (`compute_param_hash` is a Python function, not a Postgres one) — the SQL side only
needs to fetch `scan_id` + the stored `param_hash` string per source, which the grant above already
supports via the whole `metadata` column (no separate generated column needed for this phase).

**Query shape — avoid N+1.** The all-sources check must be one batched query across every enumerated
scan (e.g. `cyl_scan_traits.select(...).in_("scan_id", scan_ids)` joined/filtered in Python against
`cyl_trait_sources`), not a per-scan round trip — an experiment-level trigger can enumerate hundreds
of scans, and a naive per-scan loop would mean hundreds of PostgREST calls per request. This is an
implementation requirement for `pipeline.py` (task 4.1), not a schema change.

- Alternatives considered: (a) keep the hard-skip, document the staleness risk — rejected, directly
  undermines the stated product goal of being able to get updated results on rerun; (b) add a cheap
  model-version signal (wandb registry lookup or a published manifest) so the pre-check can be fully
  correct and literally achieve zero-pod avoidance — a legitimate future improvement, but real new
  scope/dependency, deliberately deferred rather than folded into Phase 1 (see proposal.md's
  "Out of scope").

## Risks / Trade-offs

- **Migration-timestamp collision risk** — mitigated by re-checking the latest migration on `staging`
  immediately before implementation, not just at proposal time.
- **Concurrent-duplicate-enqueue race, documented not fixed here.** Two overlapping concurrent
  `POST /workflows/pipeline` requests for the same scan (e.g. two people triggering overlapping
  experiments) each get their own `run_id`, so `UNIQUE(run_id, scan_id)` does not prevent both from
  enqueuing that scan. Given the dedup-preview decision above, this is true regardless of whether the
  two requests share the same `params` or not. **Bounded and acceptable in Phase 1**: nothing here
  reaches Argo yet, so the cost today is duplicate DB rows and duplicate pgmq messages, not duplicate
  GPU pods. **Phase 2 must decide the real fix** once real GPU cost is on the line — candidates: a
  partial unique index on `(scan_id, param_hash)` scoped to non-terminal statuses (matching bloom PR
  #469's `cyl_video_jobs_one_active_per_scan` precedent, generalized with a `param_hash` column since,
  per the dedup decision above, two different-params requests for the same scan are legitimate and
  must NOT collide — only same-scan-same-params concurrent duplicates should); or a `SELECT ... FOR
  UPDATE`-based per-target serialization; or accepting the waste and letting the cluster-side
  first-writer-wins idempotency key absorb it. Not decided here — deliberately deferred.
- **Sharing `bloom_workflows` across three call sites** (the on-demand video route, A4 cluster
  stage-in/write-back pods, and now this route) — already an accepted, reviewed tradeoff from PR #470;
  this proposal's new grants widen that shared role's blast radius further, kept as narrow as possible
  (column-scoped `SELECT`, no `UPDATE` yet — see decision above).

## Migration Plan

Forward-only migration `<timestamp>_create_cyl_pipeline_runs.sql` (both tables, RLS, Realtime, pgmq
queue + wrapper function, `bloom_workflows` grants) plus a companion manual rollback script under
`supabase/rollbacks/`, matching this repo's established pattern (e.g.
`20260625120000_create_cyl_scan_intermediates_rollback.sql`). No data migration — both tables are new.

## Open Questions

- Exact `BATCH_SIZE` default and where it's configured — design doc says "~25-50, tune so model-load
  is a small fraction of batch runtime"; this proposal defaults to 25 as a module-level constant, not
  yet an env var — revisit if Phase 2 needs it configurable per-environment.
- Whether the model-version-aware dedup pre-check (the tightened version described above) becomes
  worth building once a "current production models" signal is cheaply available — not blocking, not
  scheduled, noted so it isn't lost.
- The concurrent-duplicate-enqueue race's real fix (see Risks) — left for Phase 2 to decide against
  real GPU-cost pressure, not decided speculatively here.
