## Context

Kong (`kong:2.8.1`) runs `KONG_DATABASE=off` (DB-less/declarative mode). Its service definition:

```yaml
volumes:
  - ./volumes/api/kong.yml:/home/kong/temp.yml:ro,z
environment:
  KONG_DECLARATIVE_CONFIG: /home/kong/kong.yml
entrypoint: bash -c 'eval "echo \"$$(cat ~/temp.yml)\"" > ~/kong.yml && /docker-entrypoint.sh kong docker-start'
healthcheck:
  test: ['CMD', 'kong', 'health']
  interval: 10s
  timeout: 5s
  retries: 5
  start_period: 30s
```

`~/temp.yml` (the bind mount) holds `${VAR}`-style placeholders (e.g. `$SUPABASE_ANON_KEY`). The custom `entrypoint:` does the env-substitution into `~/kong.yml` — the file `KONG_DECLARATIVE_CONFIG` actually points at — once, at container start, before handing off to the stock upstream `/docker-entrypoint.sh kong docker-start`. There is no vendored copy of that upstream script in this repo.

## Decision 1: Full restart, not `kong reload`

**Decision: use `docker compose restart kong`, not an in-place `kong reload`.**

Two independent reasons rule out `kong reload`:

1. **It wouldn't even see the new config.** `kong reload` (or an Admin API `/config` POST) only re-reads whatever is already at the path `KONG_DECLARATIVE_CONFIG` points to (`~/kong.yml`). It does not re-run the entrypoint's substitution step, so unless something else first re-generates `~/kong.yml` from the (updated, bind-mounted) `~/temp.yml`, a reload would just re-apply the _same stale config_ it already had.
2. **Even if we did the substitution manually first, `kong reload` in DB-less mode has a documented history of not reliably applying it.** Kong GitHub issues #4808 (1.2.1: DB-less reload changes the file but the running config doesn't pick it up — stale target still resolves), #5898 (2.0.4: declarative config loading is non-atomic, causing transient 404/503s and plugins that don't take effect on frequent reload), and #6447 (2.1.4: one node's `systemctl reload` "succeeded" but silently kept serving stale ACL data for one consumer) — spanning three different Kong versions — show this isn't a single fixed bug, but a recurring class of problem with DB-less hot-reload. There's no authoritative confirmation this is resolved in 2.8.1, and the failure mode when it silently doesn't work is exactly the bug this change exists to fix (config changes silently not taking effect) — adopting a second unreliable reload path would be a poor trade for the small (~1-3s) availability window a restart costs.

A full container restart sidesteps both problems: it re-runs the _entire_ entrypoint (substitution + `kong docker-start`), which is exactly what already happens correctly whenever `up -d` recreates Kong for an unrelated reason (e.g. an env var change) — a mechanism already proven to work, not a new one.

**Trade-off accepted:** deploys that change `kong.yml` content now cause a Kong unavailability window. On the fast/typical path this is a few seconds (container stop + start); PR review correctly flagged that the honest _worst_ case is up to the full health-poll bound (Decision 5, 120s) if Kong is legitimately slow to boot, and during that entire window Caddy is proxying real end-user requests (Auth/REST/Storage/Realtime, the whole application) to a Kong that is down or still starting — this is a real, user-visible outage window, not just a smoke-test timing nuisance. This is the same _category_ of trade-off `deploy.yml` already accepts for Caddy's reload, but larger in the worst case (Caddy's is zero-downtime because `caddy reload` re-reads its Caddyfile directly with no substitution step in between — Kong's extra indirection layer is what forces the difference). No maintenance-window/traffic-draining mechanism exists in this deploy pipeline for any service today, so this change doesn't invent a gap — it makes an existing class of gap (any restart-requiring config change) apply to Kong specifically. Operationally: prefer deploying `kong.yml` changes outside peak usage hours where practical, same as any other change that restarts a shared, stateful-in-memory service.

## Decision 2: Delta-based crash-loop check, not an absolute threshold

Caddy's crash-loop check reads `RestartCount` once, unconditionally, and fails if `> 2` — this works because a clean `caddy reload` never restarts the container, so `RestartCount` should not move at all during a normal deploy; any nonzero movement already indicates a problem accumulated (possibly from before this deploy).

**Round-3 review correction:** an earlier version of this decision claimed Kong's own deliberate restart moves `RestartCount` by exactly 1, and reasoned from that premise. That's factually wrong — verified empirically, a `docker compose restart` (or plain `docker restart`) does **not** increment `RestartCount` at all; that counter only increments when the container's own restart policy (`restart: unless-stopped`) retries it after an unexpected exit, never on an explicit, successfully-issued `restart` command. The happy-path delta from our own restart is `0`, not `1`. This was a documentation-only error — `check_kong_restart_delta.sh`'s actual arithmetic never added a "+1 baseline" for the deliberate restart, so no behavioral bug resulted — but it's corrected here (and in the script's header comment, this file's Decision-2 references elsewhere in `deploy.yml`, and `spec.md`'s matching scenario) because a future maintainer "correcting" the crash-loop threshold based on the false premise could make the check trip on a single benign restart.

Kong's fix restarts the container via `docker compose restart kong` as its normal, successful-path behavior — restarted (stopped/started), not recreated. The reason an absolute threshold doesn't fit Kong as well as it fits Caddy isn't that our own restart moves the count (it doesn't) — it's that Kong's container is comparatively long-lived and is never recreated by this restart, so any restarts accumulated over its **entire lifetime** (including ones unrelated to, and long predating, the current deploy) persist in `RestartCount` forever, until the container is next recreated for some unrelated reason (an image/env change). An absolute `RestartCount > 2` check would eventually and permanently fail every future `kong.yml`-changing deploy once Kong's lifetime count organically climbs past 2 — regardless of whether the current config is fine. A before/after delta for this specific restart stays meaningful no matter how large the historical count already is. Instead:

- The restart step captures `RestartCount` **immediately before** issuing `docker compose restart kong` (call it `before`).
- The crash-loop-check step captures `RestartCount` again **after** (`after`) and computes `delta = after - before`.
- `delta` should be `0` on a clean restart (our own restart doesn't move the count). A `delta > 2` (i.e., at least 2 unplanned restarts occurring around our own) means Docker's `restart: unless-stopped` policy is retrying a crashing container — a bad `kong.yml` that fails Kong's own declarative-config validation at boot. Reusing Caddy's `> 2` tolerance keeps the two checks' sensitivity comparable and allows for a couple of benign extra restarts (e.g., a slow-starting dependency causing an early healthcheck-driven restart) without false-positiving on it.
- Both steps are gated on the same `kongfile_changed == 'true'` condition — this check exists specifically to catch our own restart going bad, not to be a general-purpose Kong crash-loop monitor (which doesn't exist for any other service in this workflow today and is out of scope for this issue).

**Known limitation, shared with Caddy's existing check and not newly introduced here:** `RestartCount` only moves when the process actually exits. A `kong.yml` that is valid enough for Kong to start and stay up, but wrong in a way that serves incorrect routing (schema-valid but semantically broken — e.g. a typo'd upstream host, or a route path that silently doesn't match what's intended) would never trip this check. This check is a safety net against _crashes_, not a correctness check on _behavior_; it does not, by itself, re-verify that the specific routes a deploy intended to change are actually being served as expected. Closing that gap fully would mean an HTTP-level assertion per changed route, which is out of scope for this change (the existing `deploy-health-check` smoke test already covers a few fixed routes, not arbitrary ones a given deploy might add).

## Decision 3: Extract the crash-loop threshold logic into a script

Caddy's crash-loop check is inlined directly in `deploy.yml` and has no unit test coverage today (confirmed: no `tests/unit/` file references it). For Kong, the delta computation is genuinely new conditional logic (not a copy of an existing, already-informally-verified pattern), and the feature's own task brief calls for TDD coverage even though "there's no unit-testable code path in the usual sense" for a deploy workflow.

This repo already has a precedent for exactly this situation: `scripts/validate_env.sh` contains the actual conditional logic deploy.yml depends on, and `tests/unit/test_env_defaults.py` invokes it directly via `subprocess` against fixture files — so the workflow and the tests can never drift, and the logic is verified without needing a live deploy. One difference: `validate_env.sh` runs on the **GitHub Actions runner** (operating on a locally-assembled env file via `${{ github.workspace }}`), while the crash-loop check must run **on the deploy host itself**, over the existing SSH session, because it inspects the live `kong` container's real Docker state. It reaches the deploy host the same way every other script this workflow depends on does: the `Pull latest code` step's `git reset --hard origin/<branch>` syncs the full repo tree onto the deploy host, so a script committed at `scripts/check_kong_restart_delta.sh` is present there (at `$PROD_DEPLOY_PATH/scripts/...` / `$STAGING_DEPLOY_PATH/scripts/...`) as soon as this change reaches that branch — no separate copy/deploy step needed.

Signature:

```
scripts/check_kong_restart_delta.sh <before-count> <threshold> -- <docker compose command...>
```

- Everything after `--` is the exact `docker compose -f docker-compose.prod.yml --env-file .env.<env> [-p bloom_v2_staging]` prefix the calling job already uses for every other compose invocation — passed through so the script never hardcodes prod/staging-specific flags itself.
- Resolves the container via `"${compose_cmd[@]}" ps -q kong`. If empty (container doesn't exist), prints `::error::` and exits 1 without attempting `docker inspect` — mirrors Caddy's existing inline `if [ -z "$cid" ]` guard.
- Runs `docker inspect --format='{{.RestartCount}}' <container-id>` to get `after`. A non-numeric or empty result (a malformed/unexpected `docker inspect` output) is treated as a hard failure (exit 1 with a `::error::`), not silently coerced to 0 — a silent coercion could mask a real problem as `delta <= threshold`.
- Computes `delta = after - before-count`.
- If `delta > threshold`: prints a `::error::` annotation, runs `"${compose_cmd[@]}" logs --tail=100 kong` and `"${compose_cmd[@]}" stop kong`, and exits 1.
- Otherwise prints `kong restart delta: <delta>` and exits 0.
- Wrong argument count (usage error, e.g. missing `--` separator) exits 2, matching `scripts/validate_env.sh`'s existing usage-error convention (2 = caller error, 1 = the check itself failed).

The companion `Restart Kong config` step applies the same `ps -q kong` empty-result guard before capturing `before` — if Kong isn't running at all before we even attempt a restart, that's a pre-existing problem `--wait` should already have caught, and the step fails loudly rather than silently treating a missing container as `before=0`.

The companion `Restart Kong config` step captures `before` the same way (`"${compose_cmd[@]}" ps -q kong` then `docker inspect`) immediately before calling `"${compose_cmd[@]}" restart kong`, then waits for Kong to report healthy again (see Decision 5) before the crash-loop-check step runs — giving Docker's `restart: unless-stopped` policy a window to reveal a fast validation-failure crash loop before the check reads `RestartCount`. `before` is threaded from the restart step to the check step via a `GITHUB_OUTPUT` value, the same cross-step pattern already used for `caddyfile_changed`/`kongfile_changed`.

For unit testing without a real Kong container or SSH access, `docker` is stubbed as a single fake executable placed first on `PATH`: it dispatches on its first argument (`inspect` → prints a canned `RestartCount` from an env var; `compose` → matches `ps -q kong` / `logs --tail=100 kong` / `stop kong` against its remaining args, returning a canned container id and appending to a call-log file the test can assert against). This mirrors `test_env_defaults.py`'s technique of running the real script via `subprocess` against controlled fixtures rather than re-implementing its logic in Python.

The restart step itself (`docker compose restart kong --timeout 10` plus capturing the `before` count) is left inline, matching how Caddy's own reload step (`caddy reload --config ...`) is inline — it has no branching logic worth isolating. The explicit `--timeout 10` bounds the SIGTERM-then-SIGKILL grace period Compose gives the old process before starting the new one, so that window is a known, fixed quantity rather than Compose's default — it happens before the health-poll's own timeout starts counting, so it doesn't eat into that budget, but keeping it explicit avoids relying on an unstated default.

**Round-3 addition:** the health-poll loop that follows the restart (see Decision 5) was initially left inline too, duplicated four times (forward-path restart + rollback restart, each for prod and staging) — an asymmetry review flagged, since `check_kong_restart_delta.sh` was specifically extracted for testability but this loop wasn't, leaving it with zero execution-level test coverage (only text/string matching on the YAML). It's now extracted the same way, into `scripts/wait_for_kong_healthy.sh <container-id> [timeout-seconds] [poll-interval-seconds]`, tested the same way (subprocess against a stubbed `docker`), and called identically from all four sites.

## Decision 4: Extend the existing `Pull latest code` step, not a new step

`caddyfile_changed` and the new `kongfile_changed` both need the same pre-pull/post-pull `BEFORE`/`AFTER` SHAs, already computed once per job inside the existing `Pull latest code` step. Adding a second `git diff --quiet $BEFORE $AFTER -- volumes/api/kong.yml` line to that same step (with its own `KONGFILE_CHANGED=` marker line, parsed the same way as `CADDYFILE_CHANGED=`) avoids a duplicate SSH round-trip and duplicate `git fetch && git reset --hard` — the state that would need to be shared is already local to that one step.

## Decision 5: Wait for Kong to report healthy, not a flat sleep

An initial draft of this design used a flat `sleep 5` between the restart and the crash-loop check. Review caught that this is insufficient for two reasons: (1) Kong's own healthcheck has a `start_period: 30s` — a `sleep 5` gives Docker's `restart: unless-stopped` policy far too little time to reveal a slower crash loop (e.g. a config that fails validation only after some startup work); (2) more importantly, the very next steps after the crash-loop check are `Verify Caddy obtained a Let's Encrypt cert` and the HTTP `Smoke test` (`deploy-health-check` spec), which proxy real requests through Caddy to Kong. The smoke test's retry loop only retries on a curl connection failure (exit code `000`), not on a real HTTP status like 502/503/504 — exactly what Caddy returns while proxying to a Kong that's still booting. A `sleep 5` risks the smoke test hitting a not-yet-ready Kong and failing the whole deploy (triggering rollback) for a transient, self-inflicted condition, not a real problem.

**Decision:** replace the flat sleep with a bounded poll of `docker inspect --format='{{.State.Health.Status}}' <container-id>`, looping until it reports `healthy` or a timeout elapses. The crash-loop check step runs only after this wait resolves (healthy, or timeout). A timeout here is itself informative — it means Kong either crash-looped (RestartCount will already show it) or is stuck in `starting`/`unhealthy`, both of which the crash-loop check's own logic and log dump will surface.

**Poll interval: 3s.** Unlike the 120s bound, threshold `2`, and 60s external timeout wrapper (all explicitly derived/revised above and in Decision 2/3), the interval between polls has no similarly load-bearing derivation — it's a plain trade-off between polling overhead and worst-case latency added past the moment Kong actually becomes healthy (at most one interval's worth), and 3s comfortably sits below Kong's own 10s healthcheck `interval` without polling so frequently it'd be noisy in the job log.

**Timeout value — revised twice after review.** An initial version set the timeout at 45s ("comfortably above the 30s `start_period` plus one 10s `interval` cycle"). Review pointed out this doesn't match Docker's actual healthcheck semantics: failures _during_ `start_period` never count toward `retries`, so a Kong that's merely slow (not crashed) can legitimately still be `starting` well past 45s without anything being wrong — misclassifying that as a timeout would relocate the original race to the smoke-test step instead of closing it. A second revision raised it to 90s (`start_period + interval * retries`). A further review round then found that even 90s rests on an assumption worth not over-trusting: depending on exactly how Docker schedules healthcheck runs relative to each other (from the previous check's start vs. its completion, and whether a check's own `timeout` can extend the gap before the next one), independent reviewers derived worst-case-but-still-legitimately-starting estimates ranging from ~75s to ~105s for this exact healthcheck configuration — none of which is _wrong_ per se, but the exact figure depends on Docker daemon internals this proposal isn't going to pin down to the second.

**The timeout is `120s`.** Rather than chase an exact worst-case figure across dockerd versions, this is a deliberately round, comfortably-conservative bound that exceeds every estimate produced during review with real margin. Precision here isn't safety-critical: a timeout does not fail the step (see above) — the crash-loop check's `RestartCount` delta is what actually decides pass/fail, so over-provisioning this bound only costs a few extra seconds of polling on the rare slow-boot path, while under-provisioning it risks exactly the race this decision exists to close. When in doubt, round up.

**Known limitation, disclosed here for the first time (round-3 review):** this decision closes the race for the crash-loop check specifically, but doesn't fully close it for the smoke test one step further downstream. If Kong is genuinely slow (not crashed) and the 120s poll times out, the crash-loop check still passes (`RestartCount` delta stays low — a slow boot isn't a restart), so the deploy proceeds to `Verify Caddy obtained a Let's Encrypt cert` and the smoke test — both of which can still hit a Kong that's `starting`/`unhealthy` past the 120s bound and get a real 502/503/504 through Caddy, which the smoke test's connection-failure-only retry logic (see above) won't retry past. A still-booting-but-otherwise-healthy Kong could therefore fail the smoke test and trigger a rollback for a transient, self-resolving condition rather than a real problem. Fully closing this would mean either raising the smoke test's own retry logic to tolerate 5xx during a known post-restart window, or not gating the smoke test's timing on Kong's health at all — both are out of scope for this change, which only needed to close the race between the restart and the crash-loop check itself.

## Decision 6: Mask Kong's secret env vars before dumping crash-loop logs

Kong's compose service injects `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_KEY`, `BLOOM_AGENT_KEY`, `DASHBOARD_USERNAME`, and `DASHBOARD_PASSWORD` as environment variables, substituted verbatim into the generated `~/kong.yml` (credentials backing its `key-auth`/`basic-auth`/`acl` plugins). The crash-loop check's log dump (`"${compose_cmd[@]}" logs --tail=100 kong`) runs exactly when `kong.yml` is broken — the failure mode most likely to produce verbose Kong startup/validation output that could echo config fragments. GitHub Actions automatically redacts exact literal values of secrets referenced anywhere in the job, but that protection is brittle (it does not survive transformation, wrapping, or reformatting of the value).

**Second-round correction:** an initial version of this decision omitted `SUPABASE_ANON_KEY` (sourced from `ANON_KEY`) from the masked list. This workflow already treats that value as sensitive enough to explicitly mask — but only later, right before the `Smoke test` step. The crash-loop check runs _before_ that point in the job, so its log dump would print `ANON_KEY` unmasked by this workflow's own defense-in-depth (falling back to GitHub's automatic redaction alone) if omitted here. All five secrets Kong's environment block actually injects are now masked at this earlier point.

**Decision:** as defense-in-depth, the `Kong crash-loop check` step emits `::add-mask::` annotations for these secret values before running the log dump, mirroring the masking already applied before this workflow's smoke-test step. This costs nothing on the non-failure path (the annotations are inert if the log dump never runs) and closes the gap GitHub's automatic redaction doesn't fully cover.

## Decision 7: Rollback must restart Kong too, or it reintroduces this exact bug

PR review caught a real gap: `Rollback on failure`'s recovery mechanism is `git reset --hard $PREV` followed by `docker compose ... up -d --wait`. That `up -d` is the _identical_ mechanism whose blindness to bind-mount content changes is this entire proposal's premise — it does not detect that `kong.yml`'s content changed back to `$PREV`'s version any more than it detects a forward change. If a later step (the LE-cert check, smoke test, a migration, schema grants) fails _after_ `Restart Kong config` already succeeded, the reset restores every other file and re-applies `up -d`, but Kong keeps running the failed deploy's routing config indefinitely — rollback would silently leave the API gateway on the wrong config while believing it fully reverted.

**Decision:** the rollback step now runs the same restart-and-health-poll logic as the forward path, gated on the same `kongfile_changed` output for that job, positioned after its own `up -d --wait` succeeds (restarting Kong before the code/env files are even reverted would just restart it back onto the still-broken config). This is inlined directly in the rollback step rather than factored into a shared script/action, matching this file's existing convention — the rollback step already inlines a full duplicate of the forward path's `up -d --wait` invocation rather than calling a shared step, and the two existing `::warning::` annotations in this same rollback step (DB schema, bloommcp data-dir rename) show this file's established pattern for rollback-specific gaps is inline handling, not extraction.

**Second-round correction:** a subsequent review pass caught that the restart command itself was unguarded inside the rollback's `set -e` SSH block. By the time this runs, the critical work (`git reset --hard` and `up -d --wait`) has already succeeded — a Kong-restart hiccup here is a secondary, best-effort concern, not a reason for the whole rollback step to abort and report failure, which would mislead on-call into thinking the actual code/env revert failed. The restart is now an `elif ! timeout 60 ... restart kong ...; then <::warning::>` branch rather than a bare command, so its own failure can't mask the revert's success.

**Also fixed alongside this:** `before_restart_count`'s missing-marker fallback previously defaulted to `0` (`${before:-0}`), unlike `kongfile_changed`'s deliberate fail-toward-action default. Defaulting a missing/malformed restart-count reading to `0` would inflate the crash-loop check's computed delta and risk stopping a perfectly healthy Kong on a transient SSH/output glitch — a self-inflicted full-outage action based on absent data, not a real crash loop. The fallback is now no default at all (an empty value), which `check_kong_restart_delta.sh`'s own argument validation rejects with a clear usage error (exit 2) — the deploy still correctly fails, but without taking the destructive stop-kong action based on a guess.

**Also fixed:** `docker compose restart kong --timeout 10`'s `--timeout` flag only bounds Docker's own graceful-stop grace period, not the whole command's wall-clock time if the Docker daemon itself becomes unresponsive (e.g. host resource exhaustion). Both the forward-path and rollback-path restart invocations are now wrapped in an external `timeout 60`, giving a hard bound distinct from Docker's internal one.

**Third-round correction (BLOCKING):** a further review pass caught that the rollback step's success message was unconditional — it printed `Rollback complete — previous version restored and healthy` regardless of whether the Kong health-poll above it ever actually reported `healthy`. If `restart kong` succeeded but the poll then timed out (Kong stuck `starting`/`unhealthy`), the only output was an informational `kong health status after rollback restart: <status>` line — no `::warning::`, no non-zero exit — and execution fell straight through to the unconditional success line. During an active rollback (something has already gone wrong upstream), on-call would see a clean success message while the API gateway could still be down. Fixed: the rollback step now tracks a `kong_rollback_ok` flag (`true` by default, flipped to `false` by the container-not-found branch, the restart-failure branch, and now also a non-`healthy` poll result), and the final message is gated on it — `Rollback complete — previous version restored and healthy` only when `kong_rollback_ok` is still `true`; otherwise an `::warning::`-prefixed message that doesn't claim Kong is healthy. See the corresponding scenario added to `spec.md`.

## Rollback / verification limits

This environment has no SSH access to the staging or production deploy hosts. Correctness of the new steps' _shape_ (ordering, gating, exact `if:` conditions) is verified by the PyYAML-based test; correctness of `scripts/check_kong_restart_delta.sh`'s and `scripts/wait_for_kong_healthy.sh`'s _logic_ is verified by direct subprocess invocation against stubbed `docker`. Correctness of the _end-to-end_ behavior against a real Kong container (does `docker compose restart kong` actually pick up new routes; does the deployed staging Kong actually start serving `/auth/v1/.well-known/*` unauthenticated after this ships) can only be confirmed manually, post-merge, against the real staging host — tracked as an explicit manual task in `tasks.md`, not claimed as done by this change's automated tests.

**Forward-path health-poll timeout can still trigger an unnecessary rollback** — disclosed here for the first time (round-3 review); see Decision 5's "Known limitation" note for the full mechanism. In short: a genuinely slow (not crashed) Kong can time out the 120s poll without tripping the crash-loop check (which only looks at `RestartCount`), letting the deploy proceed to a smoke test that can then fail on a transient 5xx and trigger a rollback for a self-resolving condition. Not fixed by this change; tracked as a known gap, same spirit as the other limitations in this section.

**Recovery if the crash-loop check actually fires on a real deploy:** the check stops Kong (`"${compose_cmd[@]}" stop kong`) rather than leaving it crash-looping, which means the entire API surface is down until someone acts — a harder outage than Caddy's equivalent (same mechanism, but Kong fronts every Supabase-backed route, not just TLS termination). Two recovery paths, in order of preference: (1) fix or revert the `kong.yml` change and let the next deploy's `Restart Kong config` step bring it back up on its own; (2) if urgent and a fix isn't ready, SSH to the deploy host and run `docker compose -f docker-compose.prod.yml --env-file .env.<env> [-p bloom_v2_staging] start kong` manually to restore service on the last-known-bad-but-at-least-running config while a real fix is prepared — accepting that this restores whatever `kong.yml` is currently checked out, which may still be the broken one if not first reverted.
