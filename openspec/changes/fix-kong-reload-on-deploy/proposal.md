## Why

`volumes/api/kong.yml` is bind-mounted read-only into the `kong` container (`docker-compose.prod.yml:307-342`) and only gets translated into Kong's actual declarative config (`~/kong.yml`, env-substituted from `~/temp.yml`) by the container's custom entrypoint **at container start**. `deploy.yml`'s `docker compose ... up -d --build --remove-orphans --wait` (both `deploy-production` and `deploy-staging`) only recreates a container when its *service definition* changes (image/env/command/volume list) — editing the *contents* of a file behind an unchanged bind mount does not trigger that, so Kong silently keeps serving stale routing config after any `kong.yml`-only change.

`deploy.yml` already solves this exact class of problem for Caddy: a `caddyfile_changed` diff flag (computed in the `Pull latest code` step) gates a `Reload Caddy config` step (`caddy reload --config /etc/caddy/Caddyfile`), followed by a `Caddy crash-loop check` that stops Caddy and fails the job if it restarts more than twice (protecting Let's Encrypt's rate limit from a bad-config restart loop). Kong has no equivalent, in either the prod or staging job.

This was discovered when PR #613 added two new Kong routes (`auth-v1-open-well-known`, `auth-v1-open-oauth`) so external MCP OAuth clients could reach GoTrue's OIDC discovery/registration endpoints without an API key. After #613 merged and staging redeployed successfully, `GET /api/auth/v1/.well-known/openid-configuration` on staging still returned Kong's old gated `401 No API key found in request` — confirming Kong never picked up the new routes, while bloommcp's own discovery endpoint (served directly by the bloommcp container, which *did* rebuild/restart) returned the correct `200` at the same time. This currently blocks OAuth login from working end-to-end on staging despite #613 being merged and deployed, and will hit prod the day any Kong-routing change ships there.

## What Changes

- Extend the existing `Pull latest code` step (`id: pull_prod` / `id: pull_staging`) to also diff `volumes/api/kong.yml` between the pre-pull and post-pull SHAs (reusing the same `BEFORE`/`AFTER` variables already computed for the Caddyfile check) and emit a `kongfile_changed` output, mirroring `caddyfile_changed` exactly (including its fail-safe default of `true` if the marker line is ever missing from step output).
- Add a `Restart Kong config (production|staging)` step, gated on `if: steps.pull_<env>.outputs.kongfile_changed == 'true'`, immediately after the existing Caddy crash-loop check in each job. It runs `docker compose ... restart kong` — a full container restart, **not** `kong reload` — because Kong's declarative config requires the entrypoint's env-substitution step (`temp.yml` → `kong.yml`) to re-run, which only happens at container start, and because `kong reload` has a documented history of not reliably re-reading declarative config in DB-less mode across multiple Kong versions (see `design.md`). This step captures Kong's `RestartCount` immediately before issuing the restart, for use by the next step.
- Add a `Kong crash-loop check (production|staging)` step, gated on the same `kongfile_changed` condition, that captures `RestartCount` again after the restart and delegates the pass/fail decision to a new `scripts/check_kong_restart_delta.sh <container-id> <before-count>` script. Unlike Caddy's absolute `> 2` threshold (which assumes the container's restart count doesn't move at all during a clean reload), this check must be delta-based: our own step deliberately restarts Kong, so the baseline already includes that one restart, and only *additional, unplanned* restarts (Docker's `restart: unless-stopped` policy retrying a crashing container) indicate a bad `kong.yml`. On a delta `> 2`, the script dumps the last 100 lines of Kong logs and stops the container (mirroring Caddy's behavior), so a bad config fails the deploy loudly instead of looping silently.
- Extracting the delta/threshold logic into `scripts/check_kong_restart_delta.sh` (rather than inlining it, as Caddy's check is inlined) follows the existing `scripts/validate_env.sh` precedent in this repo: it is the only way to give this specific new conditional logic real unit test coverage (via subprocess, with `docker`/`docker compose` stubbed) instead of leaving it exercised for the first time on a real deploy.
- Add `tests/unit/test_deploy_kong_reload_on_config_change.py`: a PyYAML-based workflow-shape test (mirroring `tests/unit/test_deploy_data_dir_preflight_ordering.py`) asserting the `kongfile_changed` diff line, the gated restart step, and the gated crash-loop-check step all exist, are correctly ordered, and share the same `if:` condition, in both `deploy-production` and `deploy-staging`; plus behavioral tests that invoke `scripts/check_kong_restart_delta.sh` directly via subprocess against a stubbed `docker`/`docker compose` on `PATH`, covering pass (delta ≤ 2) and fail (delta > 2, including log-dump + stop) paths.
- No change to `docker-compose.prod.yml`, `volumes/api/kong.yml`, or Kong's existing Docker healthcheck (`deploy-health-check` spec) — this only adds the missing reload trigger.

## Impact

- Affected specs: new capability `deploy-config-reload` (ADDS requirements covering both Kong's new reload-on-change behavior and — since this is the first spec to describe this mechanism class — a retroactive description of Caddy's pre-existing, already-implemented reload/crash-loop behavior, so the capability documents the full pattern rather than only half of it).
- Affected code: `.github/workflows/deploy.yml` (`deploy-production` and `deploy-staging` jobs), new `scripts/check_kong_restart_delta.sh`, new `tests/unit/test_deploy_kong_reload_on_config_change.py`.
- Behavior change on real deploys: any deploy where `volumes/api/kong.yml` content changed now restarts the `kong` container, causing a brief (~1-3s) Kong unavailability window — a new, explicitly-accepted trade-off (see `design.md`), comparable in kind to the risk already accepted for Caddy's reload.
- Manual, non-automatable follow-up (documented in `tasks.md`, not performed as part of this change): once this ships and staging redeploys, confirm `GET /api/auth/v1/.well-known/openid-configuration` on staging returns `200` instead of the stale `401`, proving both this fix and PR #613's routes are live together. This environment has no SSH/deploy-host access to perform that check directly.
- Related: #613 (added the routes that exposed this bug), #634 (this issue).
